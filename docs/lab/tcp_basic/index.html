TCP 연결

연결을 맺는다는 것은 무엇이고, 연결 없이 보내면 어떻게 되는가

왜 생겼나 — 네트워크로 보낸 데이터는 도중에 없어지거나 차례가 뒤바뀌어 도착할 수 있다. TCP는 먼저 연결을 맺어 상대가 받을 준비가 되었는지 확인하고, 보낸 조각마다 받았다는 답을 받아 답이 없으면 다시 보내며, 조각에 붙인 번호로 차례를 맞춘다. 그래서 프로그램은 이런 확인을 직접 하지 않아도 된다.

지금 어디에 쓰나 — 브라우저가 8080번 포트의 스프링 부트 서버에 요청을 보내는 것, 자바 프로그램이 JDBC 드라이버로 MySQL의 3306번 포트에 붙는 것이 모두 TCP 연결 위에서 일어난다. 개발자가 Socket을 직접 쓰는 일은 드물지만, 이런 라이브러리가 하는 일의 바닥에는 이 실습의 연결 맺기와 주고받기가 있다. 그래서 Connection refused 오류가 나면 그 포트에서 기다리는 프로그램이 없는지부터 본다. 온라인 게임이나 영상 통화처럼 조금 없어지더라도 빨리 닿는 것이 중요한 곳에서는 UDP를 쓰기도 한다.

두 프로그램이 네트워크로 바이트를 주고받는 규칙에는 TCP와 UDP가 있고, 자바는 둘 다 java.net 패키지의 클래스로 줍니다. TCP는 ServerSocket과 Socket으로 씁니다. 받는 쪽은 new ServerSocket(9000)으로 9000번 포트를 열고 accept()로 연결을 기다리며, 보내는 쪽은 new Socket("localhost", 9000)으로 연결을 맺은 뒤 getOutputStream()으로 얻은 출력 스트림에 바이트를 씁니다. 연결은 받는 쪽 프로그램이 그 포트에서 기다리고 있을 때만 맺어지고, 맺어진 연결로 보낸 바이트는 보낸 차례대로 도착합니다. UDP는 DatagramSocket과 DatagramPacket으로 씁니다. 연결하는 줄이 없고, 글자마다 보낼 곳을 적은 DatagramPacket을 send로 그냥 내보냅니다. 이 실습은 보내는 방식을 TCP와 UDP로 바꾸고 받는 쪽 프로그램을 띄우거나 띄우지 않으면서, 두 프로그램이 무엇을 출력하는지 봅니다. 코드 칸은 프로그램마다 main 메서드 안의 줄만 보이고(클래스·main 선언과 import는 생략), 9000이라는 번호는 예시입니다. localhost는 이 컴퓨터 자신을 가리키는 이름입니다. 포트 번호와 연결 거부 자체는 "IP 주소와 포트" 실습에서 다루고, 이 실습은 연결을 맺고 보내는 TCP와 연결 없이 보내는 UDP의 차이를 봅니다.

실행으로 대조 · JDK 21(Windows 11)에서 화면의 ServerSocket·Socket·DatagramSocket 코드를 그대로 컴파일해 받는 쪽과 보내는 쪽을 별도 프로세스로 띄우고, 네 가지 조합을 조합마다 5번 localhost에서 실행해 대조

이 실습에 나오는 개념

TCP와 UDP
인터넷에서 데이터를 전송하는 두 가지 대표적인 방식이다. TCP는 통신 전에 연결을 맺고, 데이터가 빠짐없이 순서대로 도착하도록 보장하며, 문제가 생기면 다시 보낸다. UDP는 연결 없이 데이터를 보내며 도착 여부나 순서를 보장하지 않는 대신 가볍고 빠르다. HTTP/1.1과 HTTP/2, 데이터베이스 연결은 TCP를, 실시간 영상·음성이나 DNS는 UDP를 주로 쓴다.
TCP 연결
지금 어디에 쓰나 — HTTP/1.1에서 브라우저는 서버와 맺은 연결 하나로 여러 요청을 이어 보낸다. 스프링 부트 서버도 DB와 맺어 둔 연결 몇 개를 계속 다시 써서, 연결을 맺는 데 드는 시간을 아낀다.
TCP 연결은 TCP로 글을 주고받기 전에 보내는 쪽과 받는 쪽 사이에 먼저 맺는 것이다(실제로 선이 놓이는 것이 아니라 양쪽 운영체제가 서로의 상태를 기억해 두는 약속이다). 보내는 쪽이 상대의 IP 주소와 포트로 연결을 요청하고, 그 포트를 열고 기다리는 프로그램이 있으면 연결이 맺어진다. 연결을 맺는 절차는 3-way handshake이다(RFC 9293 3.5절). 연결이 맺어진 뒤에는 TCP가 바이트를 보낸 차례대로 빠짐없이 전해 주는 것을 맡는다(RFC 9293 2.2절은 TCP가 신뢰할 수 있고 순서가 지켜지는 바이트 스트림 서비스를 제공한다고 적는다). 연결이 없으면 글을 보낼 수 없고, HTTP/1.1도 이런 믿을 수 있는 연결 위에서 오가며 http 주소의 기본은 TCP이다(RFC 9112 9절). 자바에서는 ServerSocket의 accept()와 Socket의 생성자가 만나 연결 하나가 맺어진다.
ServerSocket과 Socket
지금 어디에 쓰나 — 개발자가 ServerSocket과 Socket을 직접 쓰는 일은 드물다. 스프링 부트의 내장 웹 서버, JDBC 드라이버, HTTP 클라이언트가 이 TCP 연결을 대신 맺고 주고받는다. 그래도 연결 거부 같은 오류를 읽을 때는 이 두 클래스가 하는 일을 알고 있으면 원인을 좁히기 쉽다.
ServerSocket과 Socket은 자바가 주는 TCP용 클래스다(java.net 패키지). 받는 쪽은 new ServerSocket(포트)로 그 포트를 열고, accept()를 부르면 연결이 하나 올 때까지 그 줄에서 기다린다. 연결이 오면 accept()가 그 연결로 주고받는 Socket 객체를 돌려준다. 보내는 쪽은 new Socket("localhost", 포트)처럼 상대의 주소와 포트를 주어 Socket을 만들고, 이 생성자가 연결까지 맺는다. 연결된 Socket에서 getOutputStream()으로 얻은 출력 스트림에 쓰면 상대에게 바이트가 가고, getInputStream()으로 얻은 입력 스트림에서 상대가 보낸 바이트를 읽는다. 연결을 맺을 때 상대가 정해지므로, 보낼 때마다 받는 곳을 적지 않는다. 다 쓴 Socket은 close()로 닫는다.
DatagramSocket과 DatagramPacket
지금 어디에 쓰나 — DNS 질의처럼 짧은 물음과 답을 빨리 주고받는 곳, 온라인 게임이나 영상 통화처럼 조금 없어지더라도 늦지 않는 것이 중요한 곳에서 UDP를 쓴다. 자바 애플리케이션 코드에서 DatagramSocket을 직접 쓰는 일은 드물다.
DatagramSocket과 DatagramPacket은 자바가 주는 UDP용 클래스다(java.net 패키지). DatagramSocket에는 accept()도 연결을 맺는 생성자도 없다. 받는 쪽은 new DatagramSocket(포트)로 포트를 열고 receive(packet)로 글이 하나 올 때까지 기다린다. 보내는 쪽은 new DatagramSocket()을 만든 뒤, 보낼 바이트와 길이와 보낼 곳(주소와 포트)을 함께 준 DatagramPacket을 send로 내보낸다. send 한 번에 보낸 글 하나가 receive 한 번에 하나씩 도착한다. API 문서는 패킷마다 따로 주소가 붙어 보내지고, 여러 패킷이 어떤 차례로든 도착할 수 있다고 적는다.
연결 거부 오류
연결 거부 오류는 TCP로 연결을 요청했는데 그 포트를 열고 기다리는 프로그램이 없을 때 보내는 쪽이 받는 오류이다. 자바에서는 new Socket 줄에서 java.net.ConnectException이 나고, Windows 11에서 실행한 검증에서는 메시지가 "Connection refused: connect"였다. ConnectException의 API 문서는 이 예외가 연결하다가 난 오류이며 보통 상대 주소와 포트에서 기다리는 프로세스가 없어 거절된 경우라고 적는다. 거절은 그 컴퓨터의 운영체제가 하고, 같은 컴퓨터 안에서는 기다림 없이 곧바로 온다. 연결이 맺어지지 않았으므로 글은 하나도 보내지지 않는다. TCP 표준은 연결이 없는 상태로 온 요청에 거부 신호(RST)를 보내도록 정한다(RFC 9293 3.5.2절).
UDP로 보내기와 도착 확인
UDP는 연결을 맺지 않고, 글을 보낼 때마다 보낼 곳(IP 주소와 포트)을 적어 그냥 내보낸다. UDP 표준은 이 방식에서 도착과 중복 방지가 보장되지 않는다고 적는다(RFC 768 소개). 그래서 자바의 DatagramSocket.send가 예외 없이 끝났다는 것은 글이 이 컴퓨터에서 나갔다는 뜻일 뿐, 상대가 받았다는 뜻이 아니다. 검증 실행에서는 받는 쪽 프로그램이 없어도 send가 예외 없이 끝났다. send의 API 문서는 소켓이 connect로 상대에 묶여 있을 때만 PortUnreachableException이 날 수 있고 그것도 보장되지 않는다고 적는다. 도착을 확인하려면 받는 쪽이 답을 돌려보내고 보내는 쪽이 그 답을 기다리는 코드를 프로그램이 직접 짜야 한다.

이렇게 바꿔 보세요

  • 처음 설정으로 — 받는 쪽의 accept()와 보내는 쪽의 new Socket으로 연결이 맺어지고, 보낸 A, B, C가 보낸 차례대로 도착해 받는 쪽이 "받은 글: ABC"를 출력합니다.
  • 받는 쪽이 기다리지 않으면 — new Socket 줄에서 java.net.ConnectException(Connection refused)이 곧바로 나고, 글자는 하나도 보내지지 않습니다.
  • UDP로 바꿔 보내면 — 연결하는 줄 없이 글자마다 send로 보내고, 받는 쪽은 receive 한 번에 글자 하나씩 받습니다. 보내는 쪽은 "보내기 끝"만 출력합니다.
  • 받는 쪽이 없는데 UDP로 보내면 — 보내는 쪽은 예외 없이 "보내기 끝"을 출력하고 끝납니다. 받는 쪽이 있을 때와 출력이 같아서, 글자가 닿았는지 보내는 쪽은 알 수 없습니다.

처음 설정으로 실행하면

  1. 받는 쪽 프로그램이 new ServerSocket(9000) 줄을 실행합니다. ServerSocket은 자바가 주는 클래스(java.net.ServerSocket)이고, 이 줄은 운영체제에 "이 컴퓨터의 9000번 포트로 TCP 연결이 오면 나에게 달라"고 맡겨 두는 것입니다. 보내는 쪽 프로그램은 아직 아무것도 하지 않았습니다.
  2. server.accept() 줄을 실행합니다. accept는 연결이 하나 올 때까지 기다리는 메서드여서, 받는 쪽 프로그램은 이 줄에서 멈춘 채 연결을 기다립니다. TCP의 받는 쪽은 글자보다 먼저 연결을 받습니다.
  3. 보내는 쪽 프로그램이 new Socket("localhost", 9000) 줄을 실행합니다. Socket은 자바가 주는 클래스(java.net.Socket)이고, 이 줄은 localhost(이 컴퓨터 자신, 검증 실행에서는 127.0.0.1)의 9000번 포트와 TCP 연결을 맺어 달라는 요청입니다. 연결이 맺어지거나 실패할 때까지 이 줄은 끝나지 않습니다. A, B, C는 아직 하나도 보내지 않았습니다.
  4. 9000번 포트에서 기다리는 프로그램이 있으므로 연결이 맺어집니다. 받는 쪽의 server.accept() 줄이 끝나며 이 연결로 주고받는 Socket 객체를 돌려주어, 변수 conn이 그 객체를 가리킵니다. 보내는 쪽의 new Socket 줄도 예외 없이 끝나 변수 socket이 연결된 Socket 객체를 가리킵니다. 이제 두 프로그램 사이에 TCP 연결이 하나 있습니다. 연결을 맺을 때 두 운영체제가 주고받는 확인 절차는 "세부 동작 실습: TCP 연결과 재전송"에서 다룹니다.
  5. 보내는 쪽이 socket.getOutputStream()으로 이 연결의 출력 스트림을 얻고, write 세 줄로 A, B, C를 차례로 씁니다. 받는 곳을 줄마다 적지 않습니다. 연결을 맺을 때 이미 상대가 정해졌기 때문입니다. 세 번 모두 예외 없이 끝났고, socket.close()로 연결을 닫은 뒤 "보내기 끝"을 출력합니다.
  6. 받는 쪽이 conn.getInputStream().readAllBytes()로 이 연결로 온 바이트를 읽습니다. readAllBytes는 상대가 연결을 닫을 때까지 온 바이트를 모두 읽는 메서드입니다. 읽은 글자는 보낸 차례 그대로인 ABC이고, "받은 글: ABC"를 출력합니다. TCP는 연결로 보낸 바이트가 빠짐없이 보낸 차례대로 도착하도록 맡아 주고, 중간에 없어진 조각은 다시 보냅니다(다시 보내는 모습은 이 실습에서 일으키지 않았습니다).
  7. 보내는 쪽에 나온 것은 "보내기 끝"입니다. TCP는 받는 쪽이 없으면 new Socket 줄에서 실패하므로, 이 줄이 예외 없이 끝났다는 것은 9000번 포트에서 받는 쪽 프로그램이 기다리고 있었다는 뜻입니다.

실행 결과

  • TCP는 ServerSocket과 Socket으로 씁니다. 받는 쪽의 accept()와 보내는 쪽의 new Socket("localhost", 9000)이 만나 연결이 하나 맺어졌고, 그 연결의 출력 스트림에 쓴 A, B, C가 보낸 차례대로 도착해 받는 쪽이 "받은 글: ABC"를 출력했습니다.
  • 웹 브라우저와 스프링 부트 서버가 주고받는 HTTP도 이런 TCP 연결 위에서 오갑니다(RFC 9112 9절). 대조 실행에서 Socket으로 연결해 HTTP 요청 글을 쓰자 JDK의 HTTP 서버가 HTTP/1.1 200 OK로 답했습니다.

코드

// 프로그램마다 main 메서드 안의 줄만 보임 (클래스·main 선언과 import는 생략)

// 받는 쪽 프로그램: 9000번 포트를 TCP로 열고 연결을 기다린다
ServerSocket server = new ServerSocket(9000);
Socket conn = server.accept();
String text = new String(conn.getInputStream().readAllBytes(), "UTF-8");
System.out.println("받은 글: " + text);

// 보내는 쪽 프로그램: localhost의 9000번 포트에 TCP로 연결한 뒤 보낸다
Socket socket = new Socket("localhost", 9000);
OutputStream out = socket.getOutputStream();
out.write("A".getBytes("UTF-8"));
out.write("B".getBytes("UTF-8"));
out.write("C".getBytes("UTF-8"));
socket.close();
System.out.println("보내기 끝");

이 모형의 전제

화면의 코드는 JDK 21.0.12.1(Windows 11)에서 그대로 컴파일해 실제로 실행했습니다(verify/net/TcpBasicProbe.java). 받는 쪽 프로그램과 보내는 쪽 프로그램은 서로 다른 자바 프로세스이고, 화면의 줄을 main 메서드 안에 그대로 두고 import java.io.OutputStream과 import java.net.*만 더했습니다. 받는 쪽에는 준비가 끝났음을 알리는 출력 한 줄을 더해, 받는 쪽이 포트를 연 뒤에 보내는 쪽을 띄웠습니다(이 줄은 결과에서 뺐습니다). 화면의 9000은 예시이고 실제 실행에서는 실행마다 TCP와 UDP 모두에서 비어 있는 다른 번호를 골랐으며, 시작 전에 그 번호로 TCP 연결해 보면 모두 거절되어 아무도 열지 않았음을 확인했습니다. 네 가지 조합을 조합마다 다섯 번씩 실행했고 다섯 번의 결과가 모두 같았습니다. 대조한 것은 보내는 쪽의 표준 출력과 표준 오류 첫 줄과 종료 코드, 받는 쪽의 표준 출력과 종료 코드입니다. localhost는 이 실행에서 InetAddress.getByName으로 127.0.0.1로 풀렸습니다. 연결 거부 예외의 메시지 "Connection refused: connect"는 Windows 11에서 본 것이고, 다른 운영체제에서 메시지 끝이 같은지는 확인하지 않았습니다. 같은 프로세스 안에서 아무도 열지 않은 포트로 new Socket("localhost", 포트)를 다섯 번 해 보니 ConnectException이 매번 1밀리초 안에 왔고, 같은 컴퓨터 안이라서 짧은 것입니다. 보내는 쪽이 받는 쪽이 있는지 아는가는 같은 방식에서 받는 쪽이 있을 때와 없을 때 보내는 쪽에 나온 것이 같은지 다른지로 정했습니다. TCP는 "보내기 끝"과 ConnectException으로 달랐고, UDP는 두 경우 모두 "보내기 끝"이어서 같았습니다. 다만 TCP에서 연결이 맺어졌다는 것이 보낸 글자를 받는 쪽 프로그램이 읽었다는 확인까지 뜻하지는 않으며, 화면의 칸은 받는 쪽이 있는지만 말합니다. 받은 글자가 보낸 차례대로였던 것은 두 방식 모두 검증 실행(한 컴퓨터 안)에서 본 것이고, 차례를 표준이 맡아 주는 것은 TCP뿐입니다. 글이 중간에 없어져 TCP가 다시 보내는 일은 이 실행에서 일으키지 않았습니다. 따로 확인한 것으로, JDK가 주는 HTTP 서버(com.sun.net.httpserver.HttpServer)를 띄우고 Socket으로 연결해 "GET /hello" 요청 글을 쓰자 서버가 요청을 하나 받아 HTTP/1.1 200 OK로 답했고, 같은 글을 DatagramSocket으로 같은 포트에 보내면 send는 예외 없이 끝났지만 서버는 요청을 받지 않았습니다. 이 실습의 옛 판은 같은 네 조합을 Node.js 24.18.0의 net·dgram으로 실행했고(verify/net/tcp_basic_probe.js), 그때도 TCP는 연결 거부 오류(ECONNREFUSED), UDP는 받는 쪽이 없어도 오류 없음으로 같은 결과였습니다. 운영체제가 연결을 거절할 때 실제로 거부 신호(RST)를 보냈는지와, UDP에서 받는 쪽이 없을 때 운영체제가 어떤 신호를 돌려보냈는지는 패킷을 잡아 보지 않아 확인하지 못했습니다. 문서로는 다음을 직접 열어 확인했습니다. JDK 21 소스의 API 문서에서 ConnectException은 연결하다가 난 오류이며 보통 상대 주소와 포트에서 기다리는 프로세스가 없어 거절된 경우라고 적고, DatagramSocket은 패킷마다 따로 주소가 붙어 보내지며 여러 패킷이 어떤 차례로든 도착할 수 있다고 적습니다. DatagramSocket.send는 소켓이 connect로 상대에 묶여 있을 때만 PortUnreachableException이 날 수 있고 그것도 보장되지 않는다고 적으며, 이 실습의 보내는 쪽은 connect를 부르지 않았습니다. RFC 9293(TCP)의 2.2절은 TCP가 연결을 맺는 방식이며 신뢰할 수 있고 순서가 지켜지는 바이트 스트림 서비스를 제공한다고, 3.5절은 연결을 맺는 절차가 3-way handshake라고, 3.5.2절은 연결이 없는 상태로 온 요청에 거부 신호(RST)를 보낸다고 적습니다. RFC 768(UDP)의 소개는 UDP에서 도착과 중복 방지가 보장되지 않는다고 적습니다. RFC 9112의 9절은 HTTP가 믿을 수 있는 순서 있는 전달을 전제로 하고 http 주소의 기본 연결이 TCP라고 적습니다. 이 실습은 TCP 연결 하나와 UDP 보내기만 다루며, 연결을 맺고 끊는 절차(3-way handshake, FIN), 글이 없어졌을 때의 재전송, 순서 맞추기, 흐름 제어와 혼잡 제어는 다루지 않았고 "세부 동작 실습: TCP 연결과 재전송"과 "세부 동작 실습: TCP와 UDP"에서 다룹니다. DatagramSocket에도 connect 메서드가 있지만 TCP처럼 연결을 맺는 것이 아니며 여기서는 쓰지 않았습니다.
