인터페이스

인터페이스는 코드에서 어떻게 생겼고 무엇을 정하는가

왜 생겼나 — 어떤 기능을 쓰는 코드가 특정 클래스 이름에 묶여 있으면, 그 기능을 다른 방식으로 바꿀 때마다 쓰는 쪽 코드도 함께 고쳐야 한다. 인터페이스는 "이런 메서드가 있다"는 것을 타입으로 정해 두어서, 쓰는 쪽은 그 타입만 보고 메서드를 부르고 실제로 어느 클래스의 객체가 오든 같은 코드로 다룰 수 있게 한다. 클래스는 extends로 하나만 물려받을 수 있지만 인터페이스는 여러 개를 implements할 수 있어서, 서로 관계없는 클래스들도 같은 인터페이스 타입이 될 수 있다.

지금 어디에 쓰나 — 자바의 List와 Map이 인터페이스여서, List<String> names = new ArrayList<>();처럼 변수는 인터페이스 타입으로 적고 실제 객체는 ArrayList나 LinkedList 가운데 골라 만든다. 직접 만든 클래스가 자바의 Comparable을 implements하면 Collections.sort가 그 클래스의 목록을 정렬할 수 있고, Runnable을 implements하면 스레드가 실행할 일이 된다. 스프링 데이터 JPA에서는 JpaRepository를 이어받은 인터페이스만 선언하면 스프링이 그 구현 객체를 만들어 준다.

인터페이스는 interface로 선언하는 타입으로, "이 타입이라면 이런 메서드가 있다"를 정해 둡니다. 가장 자주 만나는 인터페이스는 자바가 주는 것입니다. 목록을 다루는 List는 java.util 패키지의 인터페이스이고, ArrayList와 LinkedList는 implements List로 그것을 구현한 클래스입니다. 정렬 순서를 정하는 Comparable도 자바가 주는 인터페이스이고, Collections.sort는 Comparable을 구현한 원소의 목록을 정렬합니다. 이 실습은 자바가 주는 List와 Comparable을 쓰는 짧은 프로그램을 컴파일하고 실행하면서, 변수의 타입과 만드는 객체를 바꾸거나 implements를 지워 보고 컴파일러가 무엇을 알려 주는지, 무엇이 출력되는지를 봅니다. 마지막에는 인터페이스를 직접 선언하는 모양과, extends로 클래스를 물려받는 것과의 차이를 짧게 봅니다.

실행으로 대조 · JDK 21에서 화면의 코드 열일곱 가지 조합(List 목록 12, Comparable 정렬 3, 직접 선언 2)을 javax.tools로 컴파일하고 실행해 대조, List·ArrayList·LinkedList·Comparable·Collections.sort의 선언은 리플렉션으로 확인

이 실습에 나오는 개념

인터페이스
클래스가 구현해야 할 메서드의 목록(계약)을 정의한 타입이다. 인스턴스 필드를 가질 수 없고, 한 클래스가 여러 인터페이스를 구현할 수 있다. 사용하는 코드가 인터페이스에만 의존하면 구현 클래스를 바꾸거나 테스트용 가짜 구현으로 교체하기 쉽다.
List, Set, Map
자바 컬렉션의 세 가지 기본 유형이다. List는 순서가 있고 중복을 허용하며 인덱스로 접근한다. Set은 중복을 허용하지 않는다. Map은 키와 값의 쌍을 저장하며 키는 중복될 수 없다. 데이터의 성격(순서 필요 여부, 중복 허용 여부, 키로 찾는지)에 따라 고른다.
ArrayList
필드로 배열을 가리키고, 그 배열이 가득 차면 더 큰 배열을 새로 만들어 원소를 옮겨 적는 리스트다. 인덱스로 원소에 접근하는 속도가 O(1)로 빠르고, 끝에 추가하는 것도 분할 상환으로 O(1)이다. 중간에 삽입하거나 삭제하면 뒤의 원소들을 한 칸씩 옮겨야 해서 O(n)이 걸린다.
LinkedList
지금 어디에 쓰나 — 순회하면서 ListIterator의 add, remove로 중간 원소를 자주 넣고 지울 때나, null도 넣어야 하는 큐가 필요할 때(ArrayDeque는 null을 받지 않는다) 고른다. 그 밖의 목록과 큐는 대개 ArrayList와 ArrayDeque로 충분하다.
각 원소(노드)가 앞뒤 원소의 위치를 가리키는 방식으로 연결된 리스트다. 특정 위치를 알고 있으면 삽입과 삭제가 O(1)이지만, n번째 원소를 찾으려면 처음부터 따라가야 해서 O(n)이다. 노드마다 추가 메모리가 들고 메모리상에 흩어져 있어 실제 순회 성능은 배열 기반보다 떨어지는 경우가 많다.
Comparable과 Comparator
객체의 순서를 정하는 두 가지 방법이다. Comparable은 클래스가 스스로 구현하는 인터페이스로, compareTo 메서드 하나에 그 클래스의 기본 순서를 정해 둔다. Comparator는 클래스 바깥에서 따로 만드는 비교 방법으로, 같은 객체들을 그때그때 다른 기준으로 정렬할 수 있게 해 준다. 둘 다 앞의 것이 먼저면 음수, 순서를 가릴 수 없으면 0, 나중이면 양수를 돌려준다. 두 수를 뺀 값을 그대로 돌려주면 오버플로로 부호가 뒤집힐 수 있으므로 Integer.compare나 Comparator.comparingInt를 쓴다.
Collections.sort
지금 어디에 쓰나 — 목록을 이름순, 나이순처럼 그 클래스의 기본 순서로 정렬할 때 쓴다. 요즘은 list.sort(null)이나 list.sort(Comparator.comparing(...))처럼 List의 sort 메서드를 직접 부르는 코드도 흔하다.
Collections.sort는 자바가 java.util.Collections에 두는 정렬 메서드로, 목록(List)을 받아 그 원소를 순서대로 다시 놓는다. Collections.sort(list)의 선언은 public static <T extends Comparable<? super T>> void sort(List<T> list)이고, 원소의 타입이 Comparable을 구현해야 부를 수 있다. 정렬하면서 원소의 compareTo를 불러 두 원소의 앞뒤를 정한다. String, Integer는 자바가 Comparable을 구현해 두었으므로 바로 정렬되고, 직접 만든 클래스는 implements Comparable과 compareTo를 작성해야 한다. 그러지 않으면 no suitable method found for sort 컴파일 오류가 난다. Comparator를 함께 넘기는 Collections.sort(list, comparator)는 Comparable이 아니어도 쓸 수 있다. 같은 값끼리의 원래 순서를 지키는 안정 정렬이다.
implements
지금 어디에 쓰나 — 자바가 주는 인터페이스를 따르는 클래스를 만들 때 쓴다. 예를 들어 직접 만든 클래스가 Comparable을 implements하면 Collections.sort가 그 클래스의 목록을 정렬할 수 있고, Runnable을 implements하면 스레드가 실행할 일을 적을 수 있다.
implements는 클래스 선언에서 그 클래스가 어떤 인터페이스를 구현한다고 밝히는 키워드이다. 자바의 ArrayList가 class ArrayList<E> extends AbstractList<E> implements List<E>, RandomAccess, Cloneable, Serializable로 선언된 것처럼 클래스 이름 뒤에 쓰고, extends 뒤에는 클래스를 하나만 적을 수 있지만 implements 뒤에는 인터페이스를 쉼표로 여러 개 적을 수 있다. abstract가 아닌 클래스가 implements를 쓰면 그 인터페이스의 모든 추상 메서드를 직접 작성하거나 상위 클래스에서 물려받아야 하고, 하나라도 빠지면 컴파일 오류이다. implements를 쓰면 그 인터페이스가 클래스의 상위 타입이 되어, List 타입 변수가 ArrayList 객체를 가리킬 수 있다. 같은 이름의 메서드를 갖췄더라도 implements를 쓰지 않으면 그 인터페이스 타입이 되지 않는다.
추상 메서드
왜 생겼나 — 부모 쪽 메서드에 빈 본문 { }을 두면, 물려받는 클래스가 그 메서드를 작성하지 않아도 컴파일이 되어 아무 일도 하지 않는 메서드가 남는다. 추상 메서드는 본문을 두지 않아서, 작성을 빠뜨리면 컴파일 오류로 알려 준다.
지금 어디에 쓰나 — Comparable의 compareTo, Runnable의 run, Comparator의 compare가 추상 메서드여서, 이 인터페이스를 따르는 클래스는 그 메서드를 직접 작성한다. 람다로 적는 본문도 이런 추상 메서드 하나의 본문이다.
추상 메서드는 이름, 매개변수, 반환 타입만 선언하고 구현(본문)은 없는 메서드이다. 자바의 Comparable에 있는 int compareTo(T o);처럼, 인터페이스에서 본문 자리에 세미콜론만 쓰면 abstract를 따로 쓰지 않아도 추상 메서드이고 public이다. 본문이 세미콜론이 아니라 중괄호 블록이면 블록이 비어 있어도({ }) 구현한 메서드이다. 추상 메서드는 그것을 가진 인터페이스를 implements한 클래스가 작성해야 하며, abstract가 아닌 클래스가 작성하지 않으면 컴파일 오류이다.
extends
지금 어디에 쓰나 — 직접 예외 클래스를 만들 때 extends RuntimeException처럼 자바가 주는 예외 클래스를 적어 물려받고, 서블릿을 만들 때 extends HttpServlet을 적는다. 클래스가 인터페이스를 따를 때는 extends가 아니라 implements를 쓴다.
extends는 클래스 선언에서 그 클래스가 어느 클래스를 물려받는지 밝히는 키워드이다. class MemberNotFoundException extends RuntimeException처럼 클래스 이름 뒤에 쓰고, 뒤에 적은 클래스(자바가 주는 RuntimeException)가 부모 클래스, 선언하는 클래스(예시로 지은 MemberNotFoundException)가 자식 클래스가 된다. 클래스는 extends 뒤에 하나만 적을 수 있고, String처럼 final이 붙은 클래스는 extends로 물려받을 수 없다. extends를 쓰면 부모 클래스가 자식 클래스의 상위 타입이 되어, 부모 타입의 변수가 자식의 객체를 가리킬 수 있다. extends를 쓰지 않은 클래스는 Object를 부모 클래스로 한다.
타입
왜 생겼나 — 값의 종류를 정하지 않으면 글자에 곱셈을 하거나 없는 메서드를 부르는 실수가 프로그램을 실행해 그 줄에 닿아야 드러난다. 자바의 타입은 이런 실수를 실행 전, 컴파일할 때 찾아 준다.
지금 어디에 쓰나 — 변수, 매개변수, 메서드가 돌려주는 값을 선언할 때 적는다. 인텔리제이 같은 편집기는 타입을 보고 그 값에 부를 수 있는 메서드 목록을 보여 준다.
타입은 변수가 가리키거나 가질 수 있는 값의 종류를 정하는 이름이다. 자바의 타입은 기본형과 참조형으로 나뉘고, 참조형에는 클래스 타입, 인터페이스 타입, 타입 변수, 배열 타입이 있다. class나 interface 선언이 있어야 그 이름을 타입으로 쓸 수 있다. 자바가 주는 List(인터페이스)와 ArrayList(클래스)도 그렇게 선언된 타입이다. 컴파일러는 변수에 값을 넣는 줄마다, 그 값의 타입이 변수의 타입과 같거나 그 하위 타입인지 확인하고, 변수로 부를 수 있는 메서드도 변수의 타입에서 찾는다. 그래서 List 타입 변수로는 실제 객체가 ArrayList여도 ArrayList에만 있는 trimToSize를 부를 수 없다.

이렇게 바꿔 보세요

  • 처음 설정으로 — 자바가 주는 인터페이스 List 타입의 변수 names가 ArrayList 객체를 가리킵니다. add와 size는 List에 정해진 메서드여서 names로 부를 수 있습니다.
  • LinkedList로 바꿔 끼우면 — LinkedList도 List를 구현한 클래스여서 바꾼 곳은 new 오른쪽 하나뿐입니다. 뒤의 코드는 그대로 컴파일되고 같은 목록을 출력합니다.
  • new List<>()로 만들면 — List는 인터페이스라서 new로 객체를 만들 수 없습니다. 컴파일 오류가 납니다.
  • List 변수로 trimToSize()를 부르면 — 실제 객체가 ArrayList여도 컴파일러는 변수의 타입 List만 봅니다. List에는 trimToSize가 없어 컴파일 오류가 납니다.
  • ArrayList 변수가 LinkedList를 가리키게 하면 — ArrayList 타입 변수는 LinkedList 객체를 가리킬 수 없어 컴파일 오류가 납니다. 변수를 클래스 타입으로 적으면 그 클래스에 묶입니다.
  • Comparable을 구현하면 — 예시로 만든 Member가 자바의 Comparable을 implements하고 compareTo를 작성해서, Collections.sort가 나이순으로 정렬합니다.
  • implements 없이 compareTo만 있으면 — 이름이 같은 메서드가 있어도 implements가 없으면 Member는 Comparable 타입이 아닙니다. Collections.sort 줄에서 컴파일 오류가 납니다.
  • implements만 있고 compareTo가 없으면 — 인터페이스는 메서드의 본문을 물려주지 않습니다. compareTo를 직접 작성하지 않아 컴파일 오류가 납니다.
  • 인터페이스를 직접 선언하면 — 예시로 지은 interface Greeter는 greet의 이름만 정하고, Hello가 implements해서 본문을 작성합니다. extends로 클래스를 물려받으면 본문까지 물려받지만 하나만 물려받을 수 있습니다.

처음 설정으로 실행하면

  1. 컴파일러가 import 줄로 자바가 주는 List를 찾습니다. List는 자바 표준 라이브러리에 public interface List<E>로 선언된 인터페이스입니다. class가 아니라 interface로 선언되어 있고, add(목록 끝에 더하기), get(몇 번째 원소 꺼내기), size(개수) 같은 메서드가 있다는 것을 정해 둡니다. <String>은 이 목록의 원소가 문자열이라는 뜻입니다.
  2. 컴파일러가 = 오른쪽의 new ArrayList<>()를 확인합니다. ArrayList는 자바가 public class ArrayList<E> extends AbstractList<E> implements List<E>, RandomAccess, Cloneable, Serializable로 선언해 둔 클래스입니다. add와 size의 본문(실제로 하는 일)까지 작성된 클래스라서 new로 객체를 만들 수 있습니다. 선언을 보면 extends 뒤에는 클래스 하나(AbstractList)만, implements 뒤에는 인터페이스 넷을 적었습니다. 클래스는 하나만 물려받을 수 있지만 인터페이스는 여러 개를 구현할 수 있습니다.
  3. 컴파일러가 List<String> names = new ArrayList<>(); 줄을 확인합니다. ArrayList가 List를 구현했으므로 List 타입 변수 names가 ArrayList 객체를 가리켜도 됩니다. 변수의 타입은 인터페이스 List로, 실제로 만드는 객체는 클래스 ArrayList로 적은 것입니다.
  4. 컴파일러가 names.add(...)와 names.size()를 확인합니다. 컴파일러는 변수의 타입 List만 보고 부를 수 있는 메서드를 정합니다. add와 size는 List에 정해진 메서드여서 실제 객체가 ArrayList든 LinkedList든 같은 줄을 그대로 쓸 수 있습니다.
  5. 컴파일이 성공해 Main 클래스 파일이 만들어집니다.
  6. java Main으로 실행합니다. new ArrayList<>()가 ArrayList 객체를 만들고 names가 그 객체를 가리킵니다. names.add를 부르면 실제로는 ArrayList에 작성된 add가 실행되어 목록에 세 이름이 차례로 더해집니다. 첫 줄에 [민수, 지은, 현우], 3명이 출력되고, 둘째 줄에는 getClass().getSimpleName()이 ArrayList를 출력합니다. getClass()는 모든 객체에 있는 메서드로, 실제로 만든 객체의 클래스를 알려 줍니다.

실행 결과

  • 인터페이스는 interface로 선언하는 타입으로, 이런 메서드가 있다는 것을 정해 둡니다. 자바가 주는 List가 인터페이스이고, ArrayList는 implements List로 그것을 구현한 클래스입니다. 그래서 List 타입 변수 names가 ArrayList 객체를 가리킬 수 있었습니다.
  • names로 부른 add와 size는 List에 정해진 메서드여서, 이 코드는 names가 ArrayList를 가리키는지 LinkedList를 가리키는지에 기대지 않습니다. 실행된 것은 ArrayList에 작성된 add와 size입니다.

코드

// 자바가 주는 것을 가져온다 (java.util 패키지)
import java.util.ArrayList;
import java.util.LinkedList;
import java.util.List;

public class Main {
    public static void main(String[] args) {
        // List는 자바가 주는 인터페이스, ArrayList와 LinkedList는 자바가 주는 클래스
        List<String> names = new ArrayList<>();
        names.add("민수");
        names.add("지은");
        names.add("현우");
        System.out.println(names + ", " + names.size() + "명");
        System.out.println("names가 가리키는 객체: " + names.getClass().getSimpleName());
    }
}

이 모형의 전제

컴파일러와 실행 환경은 JDK 21.0.12.1(javac 21)입니다. 설정의 조합을 모두(목록 12가지, 정렬 3가지, 직접 선언 2가지), 화면의 코드 함수가 만든 글을 그대로 파일로 써서 javax.tools로 컴파일하고, 컴파일에 성공한 것은 새 클래스 로더로 읽어 Main.main을 실행해 표준 출력을 잡은 결과와 대조했습니다. 대조한 것은 컴파일 성공 여부, 첫 번째 오류의 진단 코드와 영어 메시지(abstract.cant.be.instantiated, cant.resolve.location.args, prob.found.req, cant.apply.symbols, does.not.override.abstract를 화면의 다섯 가지 오류 설명으로 옮겼습니다), 오류의 개수와 오류가 난 줄, Main 클래스 파일이 만들어졌는지, 실행했을 때의 출력입니다. 같은 프로그램에서 리플렉션으로 List와 Comparable이 인터페이스인 것, ArrayList가 AbstractList를 물려받고 List, RandomAccess, Cloneable, Serializable을 구현한 것, LinkedList가 AbstractSequentialList를 물려받고 List, Deque, Cloneable, Serializable을 구현한 것, String이 Comparable을 구현한 것, trimToSize가 ArrayList에는 있고 List에는 없는 것, Comparable의 메서드가 compareTo 하나인 것을 확인했고, extends 뒤에 클래스를 둘 적으면 문법 오류(javac가 쉼표 자리에 { 가 와야 한다고 알림)이고 implements 뒤에 인터페이스를 둘 적으면 컴파일되는 것도 따로 컴파일해 확인했습니다. 화면에 옮긴 선언(public interface List<E>, Collections.sort의 <T extends Comparable<? super T>>)은 JDK 21의 API 문서와 대조했습니다. 문서는 Java Language Specification(Java SE 21)의 9.4절(본문 없이 세미콜론으로 끝나는 인터페이스 메서드는 추상 메서드), 8.1.4절(extends 뒤의 클래스는 하나), 8.1.5절(implements 뒤의 인터페이스는 여럿), 8.1.1.1절(추상 클래스가 아니면 구현한 인터페이스의 추상 메서드를 모두 갖춰야 함), 15.9.1절(인터페이스로는 new로 객체를 만들 수 없음), 5.2절(상위 타입 변수가 하위 타입의 객체를 가리킬 수 있음), 15.12.1절(부를 수 있는 메서드는 변수의 타입에서 찾음)을 따랐습니다. 오류의 종류, 개수, 어느 줄에서 나는지는 명세가 정한 것이 아니라 이 javac에서 관찰한 것이고, 오류가 여럿이면 표에는 첫 번째 것만 적었습니다. List에는 본문이 있는 default 메서드(sort, replaceAll 등)도 있지만 이 실습은 다루지 않았습니다. 인터페이스의 쓰임과 추상 클래스와의 차이는 "세부 동작 실습: 인터페이스와 추상 클래스"에서 다룹니다.
