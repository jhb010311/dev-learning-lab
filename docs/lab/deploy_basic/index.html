배포

코드를 고치면 실행 중인 서버는 언제 바뀌는가

왜 생겼나 — 자바 서버는 소스 파일을 그대로 실행하지 않는다. 소스 파일을 컴파일해 jar 파일로 만들고, java -jar로 그 jar를 실행한 프로세스가 요청에 답한다. 그래서 코드를 고친 뒤에도 jar를 새로 만드는 일과 서버를 끄고 다시 켜는 일이 남는데, 이것을 그때그때 손으로 하면 하나를 빠뜨리거나 사람마다 순서가 달라지기 쉽고, 지금 서버에서 어느 버전이 도는지도 헷갈린다. 배포 단계를 미리 정해 두고 그대로 따르면 매번 같은 순서로 새 버전을 돌리게 되어 빠뜨리는 것이 줄고, 언제부터 어느 버전이 도는지 알 수 있다.

지금 어디에 쓰나 — 새 기능을 내놓거나 버그를 고칠 때마다 배포한다. 스프링 부트 프로젝트는 보통 ./gradlew bootJar(Maven이면 ./mvnw package)로 jar 파일을 만들고, 서버에서 java -jar로 실행한다. 요즘은 코드를 저장소에 올리면 GitHub Actions나 Jenkins 같은 도구가 빌드와 테스트를 거쳐 서버에 올리는 일까지 이어서 하게 해 두는 경우가 많다. 서버가 여러 대이면 한 대씩 차례로 바꾸어, 한 대를 다시 켜는 동안에도 다른 서버가 요청을 받게 한다.

스프링 부트 서버는 소스 파일(.java)을 그대로 실행하지 않습니다. 소스 파일을 컴파일해 .class 파일을 만들고, 그것을 jar 파일 하나로 묶은 뒤, java -jar 명령으로 그 jar 파일을 실행합니다. 실행하면 프로세스(실행 중인 프로그램)가 하나 생기고, 이 프로세스는 켜질 때 jar 파일에서 클래스를 읽어 들여 그 코드대로 요청에 답합니다. 그래서 코드는 세 곳에 따로 있습니다. 사람이 고치는 소스 파일, 빌드로 만든 jar 파일, 그리고 돌고 있는 서버 프로세스입니다. 소스 파일을 고쳐도 jar 파일은 저절로 바뀌지 않고, jar 파일을 새로 만들어도 이미 돌고 있는 프로세스는 바뀌지 않습니다. 컴파일과 jar 만들기는 ./gradlew bootJar 명령(스프링 부트의 Gradle 플러그인이 주는 bootJar 작업)이 하고, 돌던 서버를 끈 뒤 java -jar로 다시 켜야 새 코드가 요청에 답합니다. 이렇게 새 버전을 실제로 돌아가게 하는 일을 배포라고 합니다. 코드 칸의 앞부분은 자바 파일 두 개이고, 뒷부분은 터미널에서 하는 일입니다(#으로 시작하는 줄은 번호가 붙은 할 일이고, 그 밑의 줄이 터미널에 치는 명령입니다). 이 실습은 예시로 만든 HelloController의 "버전 1"을 "버전 2"로 고친 뒤, jar 파일을 새로 만드는 일과 서버를 끄고 다시 켜는 일을 빼거나 순서를 바꿔 가며, 요청에 어느 버전이 답하는지를 봅니다.

실행으로 대조 · JDK 21과 스프링 부트 4.1.1에서 화면의 코드 열두 가지 조합을 그대로 실행해 대조: 자바 파일을 javac로 컴파일하고 jar 명령으로 app.jar를 만들고(./gradlew bootJar 대신, bootJar가 같은 일을 한다는 것은 스프링 부트·Gradle 공식 문서로 확인), java -jar로 켜고 끄며 curl로 요청해 응답·8080 포트를 연 프로세스·jar와 소스의 값을 기록

이 실습에 나오는 개념

배포
배포는 새 버전의 코드를 실제로 돌아가는 서버에 반영해, 사용자의 요청이 새 버전에 닿게 만드는 일이다. 자바 서버는 소스 파일이 아니라 소스를 컴파일해 만든 jar 파일을 실행하고, 이미 켜져 있는 서버는 켤 때 읽어 들인 코드로 돈다. 그래서 소스 파일을 고쳐 저장하는 것만으로는 배포가 되지 않고, 고친 소스로 jar 파일을 새로 만든 뒤 서버가 그 jar로 다시 켜져야 한다. 가장 단순한 방법은 서버를 끄고 새 jar로 다시 켜는 것이고, 이 방법은 서버가 한 대일 때 꺼져 있는 동안 요청이 실패한다. Kubernetes 문서는 이 일을 옛 Pod를 새 Pod로 바꾸는 것으로 설명하고, 기존 Pod를 모두 끝낸 뒤 새로 만드는 Recreate와 점진적으로 바꾸는 RollingUpdate를 구분한다.
서버 재시작
지금 어디에 쓰나 — 스프링 부트 서버는 보통 켤 때 설정 파일을 읽으므로, application.properties를 고친 뒤에도 다시 켜야 한다. 개발 중에는 Spring Boot DevTools가 클래스패스의 파일이 바뀔 때마다 애플리케이션을 저절로 다시 시작해 준다(JVM 프로세스는 그대로 둔 채).
서버 재시작은 실행 중인 서버 프로세스를 끝내고, 같은 서버 프로그램을 다시 실행해 새 프로세스를 만드는 일이다. 스프링 부트 서버라면 java -jar로 켠 프로세스를 끝내고(그 터미널에서 Ctrl+C 등) 다시 java -jar로 켠다. 끝난 프로세스가 읽어 들였던 코드는 함께 사라지고, 새 프로세스는 켜질 때 그 순간 디스크에 있는 jar 파일에서 클래스를 처음부터 읽어 들인다. 그래서 jar 파일을 새로 만들지 않고 재시작하면 옛 코드를 다시 읽을 뿐이다. 끄고 다시 켜기 전까지는 연결을 받는 프로세스가 없으므로, 그 사이에 온 요청은 연결 거부 오류로 실패한다.
실행 가능한 jar
왜 생겼나 — 서버를 돌리려면 내 클래스와 수십 개의 라이브러리 jar를 클래스패스에 모두 적어 java 명령을 쳐야 했고, 서버마다 라이브러리를 맞춰 두는 일도 번거로웠다. 실행 가능한 jar는 필요한 것을 파일 하나로 모아, 서버에 JDK만 있으면 java -jar로 켤 수 있게 했다.
지금 어디에 쓰나 — 스프링 부트 서버를 배포할 때 가장 흔한 꼴이다. CI 도구가 ./gradlew bootJar나 ./mvnw package로 만든 jar를 서버에 올리고 java -jar로 켜며, 컨테이너 이미지를 만들 때도 이 jar를 이미지에 넣고 java -jar를 실행 명령으로 적는 경우가 많다.
실행 가능한 jar는 java -jar 명령 하나로 바로 실행할 수 있게 만든 jar 파일이다. 스프링 부트의 bootJar 작업이 만드는 jar에는 내 클래스(BOOT-INF/classes)와 스프링·톰캣 같은 의존 라이브러리(BOOT-INF/lib), 그리고 어느 클래스의 main부터 실행할지가 적혀 있어서, 서버에 이 파일 하나만 옮기면 java -jar로 웹 서버까지 켤 수 있다. 실행 가능한 jar는 소스를 컴파일한 그 시점의 코드다. 소스 파일을 고친 뒤 jar를 새로 만들지 않으면 jar는 옛 코드 그대로이고, jar를 새로 만들어도 이미 그 jar로 켜져 있는 프로세스는 켜질 때 읽어 들인 코드로 계속 돈다.
./gradlew bootJar
지금 어디에 쓰나 — 스프링 부트의 Maven 플러그인을 쓰는 Maven 프로젝트에서는 ./mvnw package가 실행 가능한 jar를 만든다. 개발 중에 jar를 만들지 않고 바로 켜 보려면 ./gradlew bootRun을 쓴다.
./gradlew bootJar는 Gradle로 빌드하는 스프링 부트 프로젝트에서 실행 가능한 jar를 만드는 명령이다. ./gradlew는 프로젝트 폴더에 함께 두는 Gradle 실행 스크립트(Gradle 래퍼)이고, bootJar는 스프링 부트의 Gradle 플러그인이 주는 작업이다. 이 작업은 먼저 소스 파일을 컴파일하고, 그 클래스와 의존 라이브러리를 모아 build/libs 폴더에 jar 파일을 만든다(이름은 보통 프로젝트 이름-버전.jar). ./gradlew build를 쳐도 테스트와 함께 bootJar가 돈다. 이 명령은 jar 파일을 만들 뿐, 이미 켜져 있는 서버를 바꾸거나 다시 켜지는 않는다.
프로그램과 프로세스
프로그램은 디스크에 저장된 파일이고, 프로세스는 그 파일을 실행한 것이다. 자바에서 javac로 만든 Counter.class는 프로그램 파일이고, java Counter 명령을 쓰면 운영체제가 프로세스를 하나 만들어 그 파일을 실행한다. 파일은 1개여도 실행할 때마다 프로세스가 하나씩 생기므로, 같은 파일을 두 번 실행하면 프로세스가 둘이 된다. 프로세스는 실행하는 동안만 있고, 끝나면 사라진다. 이 프로세스는 자기만의 실행 환경을 가진다.
연결 거부 오류
연결 거부 오류는 TCP로 연결을 요청했는데 그 포트를 열고 기다리는 프로그램이 없을 때 보내는 쪽이 받는 오류이다. 자바에서는 new Socket 줄에서 java.net.ConnectException이 나고, Windows 11에서 실행한 검증에서는 메시지가 "Connection refused: connect"였다. ConnectException의 API 문서는 이 예외가 연결하다가 난 오류이며 보통 상대 주소와 포트에서 기다리는 프로세스가 없어 거절된 경우라고 적는다. 거절은 그 컴퓨터의 운영체제가 하고, 같은 컴퓨터 안에서는 기다림 없이 곧바로 온다. 연결이 맺어지지 않았으므로 글은 하나도 보내지지 않는다. TCP 표준은 연결이 없는 상태로 온 요청에 거부 신호(RST)를 보내도록 정한다(RFC 9293 3.5.2절).

이렇게 바꿔 보세요

  • 처음 설정으로 — 고친 소스로 새 jar 파일을 만들고, 돌던 서버를 끈 뒤 새 jar로 다시 켭니다. 새 프로세스가 "버전 2"로 답합니다.
  • 소스 파일만 고치면 — 소스 파일만 "버전 2"이고 jar 파일과 돌고 있는 서버는 그대로입니다. 서버는 "버전 1"로 답합니다.
  • jar만 새로 만들고 서버를 끄지 않으면 — jar 파일은 "버전 2"가 되었지만, 돌고 있는 프로세스는 켜질 때 읽어 들인 코드로 계속 "버전 1"을 답합니다.
  • jar를 새로 만들지 않고 다시 켜면 — 다시 켠 프로세스는 옛 jar 파일을 읽습니다. 소스 파일은 "버전 2"이지만 "버전 1"이 답합니다.
  • 끄고 다시 켜는 사이에 요청하면 — 그 포트에서 연결을 받는 프로세스가 없어 요청은 연결 거부 오류로 실패합니다. 다시 켠 뒤에 온 요청은 "버전 2"를 받습니다.
  • 고치지 않고 다시 만들고 켜면 — 같은 소스로 같은 jar를 만들고 같은 코드로 다시 켰을 뿐이어서 "버전 1"이 답합니다.

처음 설정으로 실행하면

  1. 1번: ./gradlew bootJar가 소스 파일을 컴파일해 .class 파일을 만들고, 그것을 jar 파일 build/libs/app.jar로 묶습니다. 이 jar 파일의 HelloController는 "버전 1"을 돌려주는 코드입니다.
  2. 1번: java -jar build/libs/app.jar가 jar 파일을 실행해 프로세스를 하나 만듭니다. 이 프로세스는 켜질 때 jar 파일에서 클래스를 읽어 들이고, 스프링 부트가 웹 서버를 켜서 8080 포트에서 요청을 기다립니다. 이제 GET /hello에는 "버전 1"로 답합니다.
  3. 2번: 사람이 HelloController.java를 열어 "버전 1"을 "버전 2"로 고쳐 저장합니다. 바뀐 것은 디스크의 소스 파일 하나뿐입니다. jar 파일은 여전히 "버전 1"이고, 돌고 있는 서버도 "버전 1"로 답합니다. 소스 파일을 저장해도 컴파일과 jar 만들기는 저절로 일어나지 않습니다.
  4. 3번: ./gradlew bootJar가 지금의 소스 파일로 jar 파일을 새로 만듭니다. 이제 jar 파일의 코드는 "버전 2"를 돌려줍니다. 하지만 서버를 켜 둔 채라서, 이때 요청을 보내 보아도 돌고 있는 프로세스는 "버전 1"로 답했습니다. 프로세스는 켜질 때 읽어 들인 클래스로 돌 뿐, 디스크의 jar 파일이 바뀐 것을 가져오지 않습니다.
  5. 4번: 서버를 켠 터미널에서 Ctrl+C를 눌러 서버를 끕니다. 프로세스가 끝나면서 그 프로세스가 읽어 들였던 코드도 함께 사라집니다. 디스크의 소스 파일과 jar 파일은 그대로 남습니다.
  6. 5번: java -jar build/libs/app.jar로 다시 켭니다. 새 프로세스가 생기고, 켜질 때 지금 디스크에 있는 jar 파일에서 클래스를 처음부터 읽어 들입니다. 그 jar 파일의 코드는 "버전 2"를 돌려주는 것입니다. 고친 코드가 이제 돌고 있는 서버의 코드가 되었습니다.
  7. 6번: 다른 터미널에서 curl이 GET /hello 요청을 보냅니다. 브라우저 주소창에 localhost:8080/hello를 입력하면 브라우저가 보내는 요청과 같은 것입니다.
  8. 돌고 있는 프로세스가 자기 코드대로 "버전 2"로 답하고, curl은 "버전 2"를 받습니다. 소스 파일, jar 파일, 돌고 있는 서버의 코드가 모두 "버전 2"로 같습니다. 고친 새 버전이 요청에 답했습니다.

실행 결과

  • 소스를 고치고(2번), jar 파일을 새로 만들고(3번), 돌던 서버를 끄고 다시 켜야(4~5번) 새 프로세스가 고친 코드로 "버전 2"를 답합니다. 이렇게 새 버전을 실제로 돌아가게 하는 일이 배포입니다.
  • 코드는 소스 파일, jar 파일, 돌고 있는 프로세스의 세 곳에 따로 있습니다. 소스 파일의 코드로 jar 파일을 만드는 것이 ./gradlew bootJar이고, jar 파일의 코드를 프로세스로 읽어 들이게 하는 것이 다시 켜는 일입니다.

코드

// 파일: src/main/java/com/example/demo/DemoApplication.java
// DemoApplication과 HelloController는 이 실습에서 예시로 만든 클래스
// @SpringBootApplication, SpringApplication, @RestController, @GetMapping은 스프링 부트와 스프링이 주는 것
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class DemoApplication {
    // java -jar로 jar 파일을 실행하면 이 main이 불리고, 스프링 부트가 웹 서버를 켠다
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}

// 파일: src/main/java/com/example/demo/HelloController.java
package com.example.demo;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {
    // GET /hello 요청이 오면 스프링이 이 메서드를 부르고, 돌려준 글자가 응답이 된다
    @GetMapping("/hello")
    public String hello() {
        return "버전 1"; // 아래 2번에서 "버전 2"로 고친다
    }
}

# 터미널에서 하는 일 (프로젝트 폴더에서, jar 이름은 짧게 app.jar로 적었다)
# 1. jar 파일을 만들고, 그 jar로 서버를 켠다
./gradlew bootJar
java -jar build/libs/app.jar
# 2. HelloController.java의 "버전 1"을 "버전 2"로 고쳐 저장한다
# 3. jar 파일을 새로 만든다 (서버는 켜 둔 채)
./gradlew bootJar
# 4. 켜 둔 서버를 끈다 (서버를 켠 터미널에서 Ctrl+C)
# 5. 새로 만든 jar로 다시 켠다
java -jar build/libs/app.jar
# 6. 다른 터미널에서 요청을 보낸다
curl http://localhost:8080/hello

이 모형의 전제

실행 환경은 JDK 21.0.12.1, 스프링 부트 4.1.1(스프링 프레임워크 7.0.9, 내장 톰캣 11.0.24), curl 8.21.0, Windows 11입니다. 열두 가지 조합마다 화면의 코드를 이 실습의 code 함수에서 그대로 꺼내, 앞부분의 자바 파일 두 개를 파일로 쓰고 뒷부분의 할 일과 명령을 줄마다 실제로 했습니다. java -jar build/libs/app.jar와 curl http://localhost:8080/hello는 화면의 명령 그대로 실행했고, 서버는 기본 포트 8080에서 켜졌습니다. ./gradlew bootJar는 Gradle 플러그인을 내려받아야 해서 실행하지 않았고, 같은 일을 JDK 명령으로 했습니다. javac로 src/main/java를 컴파일하고 jar 명령으로 build/libs/app.jar를 만들었는데, bootJar가 의존 라이브러리를 jar 파일의 BOOT-INF/lib에 넣는 것과 달리 이 jar는 매니페스트의 Class-Path로 라이브러리 jar 파일을 가리켰습니다. Windows에서는 켜 둔 java 프로세스가 연 app.jar를 jar 명령이 새로 쓰지 못해(파일을 다른 프로세스가 쓰고 있다는 오류), 서버를 켜 둔 채 jar를 새로 만드는 여섯 조합에서는 새 jar를 다른 이름으로 만든 뒤 그 내용을 app.jar에 그 자리에서 덮어썼습니다. 서버를 끄는 일은 Ctrl+C가 아니라 프로세스 강제 종료로 했습니다. 요청 때마다 curl의 출력, 그때 8080 포트를 열고 있던 프로세스 번호(netstat), javap로 읽은 app.jar의 HelloController가 돌려주는 글자, 디스크의 소스 파일에 적힌 글자를 기록해 결과 표와 대조했고, jar를 새로 만든 직후 켜 둔 서버의 답, 끄기 직전 서버의 답, 켠 횟수, jar를 만든 횟수, 끈 사이에 요청한 조합에서 다시 켠 뒤의 답도 대조해 열두 조합이 모두 맞았습니다(verify/net/cmp_deploy_basic.js). 연결 거부 오류는 curl이 종료 코드 7(Failed to connect … Could not connect to server)로 알린 것입니다. 문서로 확인한 것은 스프링 부트 Gradle 플러그인 문서의 Packaging Executable Archives(bootJar 작업이 실행 가능한 jar를 만들고 클래스와 의존 라이브러리를 BOOT-INF/classes와 BOOT-INF/lib에 넣으며 그 jar를 java -jar로 실행할 수 있다는 서술), 스프링 부트 레퍼런스의 Running Your Application(실행 가능한 jar를 java -jar로 실행한다는 서술), Gradle 문서의 Java Plugin(jar 작업이 classes에, classes가 compileJava에 기댄다는 서술)과 Base Plugin(jar가 기본으로 build/libs에 생기고 이름이 프로젝트 이름과 버전으로 정해진다는 서술)입니다. 화면의 app.jar는 짧게 적은 이름입니다. 다루지 않은 것: 리눅스 서버에서 켜 둔 서버의 jar를 덮어쓸 때의 동작, Ctrl+C로 끌 때 스프링 부트가 하는 정리 작업, 파일이 바뀌면 애플리케이션을 저절로 다시 시작하는 Spring Boot DevTools는 이 실습에서 실행하지 않았습니다. 서버를 끄고 다시 켜는 틈을 없애는 방법(여러 대를 차례로 바꾸는 롤링, 새 환경을 통째로 만드는 블루-그린 등)은 "세부 동작 실습: 배포 전략"에서, 코드를 고친 뒤 빌드와 테스트를 거쳐 서버에 올리는 자동화는 "세부 동작 실습: CI/CD 파이프라인"에서, 컨테이너로 포장해 쿠버네티스가 서버를 바꾸는 방식은 "세부 동작 실습: 쿠버네티스 자가 치유"에서 다룹니다.
