프록시 서버

서버를 직접 부르기와 nginx(프록시)를 거쳐 부르기는 무엇이 다른가

왜 생겼나 — 서버 프로그램을 인터넷에 바로 내놓으면, 서버를 여러 대로 늘리거나 바꿀 때 사용자가 접속하는 주소도 바뀌고, HTTPS 처리나 나쁜 접속 막기 같은 일도 서버 프로그램마다 따로 해야 한다. 리버스 프록시는 서버들 앞에 한 주소로 서서 요청을 받아 넘겨 주므로, 뒤의 서버가 바뀌어도 사용자는 같은 주소로 접속한다.

지금 어디에 쓰나 — 스프링 부트 서버 앞에 nginx를 두고, nginx 설정의 proxy_pass로 80번과 443번 포트에서 받은 요청을 8080번의 스프링 부트에 넘기는 구성이 흔하다. 이때 스프링 부트가 보는 연결 상대는 nginx이므로, 진짜 사용자의 IP 주소는 nginx가 proxy_set_header로 X-Forwarded-For 헤더에 적어 넘기게 해서 전해 받는다. 회사 안에서 바깥 사이트로 나가는 요청을 한곳에 모아 거르는 프록시(포워드 프록시)도 있다.

프록시 서버는 요청을 보내는 쪽(사용자)과 진짜 서버 사이에 서서 요청을 대신 넘겨 주는 서버입니다. 이 실습은 가장 흔한 구성인 nginx와 스프링 부트로, 서버를 직접 부를 때와 nginx를 거쳐 부를 때를 견줍니다. 코드 칸은 네 부분입니다. 첫째는 사용자가 부르는 주소입니다. 사용자는 다른 컴퓨터(203.0.113.7)에 있고, 192.0.2.10은 서버 컴퓨터의 주소입니다. 주소에 포트 번호를 적지 않으면 80번, :8080을 적으면 8080번으로 갑니다. 포트 번호는 한 컴퓨터에서 프로그램마다 나뉜 문의 번호입니다. 둘째는 nginx 설정입니다. listen 80은 80번에서 요청을 받는다는 줄이고, proxy_pass는 받은 요청을 같은 컴퓨터의 8080번(127.0.0.1:8080)에 넘긴다는 줄이며, proxy_set_header는 넘길 때 요청에 헤더를 적어 붙이는 줄입니다. 셋째는 스프링 부트의 설정 파일 application.properties이고, 넷째는 요청을 받는 컨트롤러입니다. 컨트롤러는 자신에게 연결한 상대의 주소(request.getRemoteAddr())와 X-Forwarded-For 헤더를 글로 돌려줍니다. 이 실습은 부르는 주소, server.address 줄, 켜 둔 프로그램을 바꿔 가며 사용자가 무엇을 받는지와 스프링 부트가 누구를 연결 상대로 보는지를 봅니다. nginx는 이 실습을 만든 컴퓨터에 없어서, 실행에서는 nginx 문서에 적힌 대로 움직이게 만든 작은 프로그램(Node.js)이 nginx 역할을 대신했고, 스프링 부트 쪽은 화면의 코드를 그대로 실행했습니다.

일부만 실행으로 확인 · 스프링 부트 쪽(화면의 HelloController와 application.properties)은 스프링 부트 4.1.1로 실제 실행해 열두 가지 조합을 대조(getRemoteAddr()·X-Forwarded-For·server.address의 효과, verify/net/cmp_proxy_basic.js). nginx는 이 컴퓨터에 없어, nginx 문서·소스대로 움직이게 만든 Node.js 프로그램이 대신함(proxy_pass·proxy_set_header·502는 문서와 소스 대조)

이 실습에 나오는 개념

프록시 서버
프록시 서버는 요청을 보내는 쪽(클라이언트)과 진짜 서버 사이에 서서, 받은 요청을 다른 서버에 대신 넘기고 그 응답을 클라이언트에 돌려주는 중간 서버다. 클라이언트는 프록시 서버에 연결하고, 프록시 서버가 진짜 서버에 따로 연결을 맺는다. 그래서 진짜 서버가 보는 연결 상대는 클라이언트가 아니라 프록시 서버다. 스프링 부트 앞에 두는 nginx가 대표적인 예다. RFC 9110 3.7절은 이런 중간 서버를 클라이언트가 설정으로 골라 거치는 proxy와, 서버처럼 보이면서 요청을 안쪽 서버로 넘기는 gateway(리버스 프록시)로 나누어 부른다. 프록시 서버가 꺼지면 그 주소로 접속하는 클라이언트는 뒤의 서버가 살아 있어도 응답을 받지 못한다.
리버스 프록시
왜 생겼나 — 느린 클라이언트가 애플리케이션 서버에 바로 붙으면, 큰 요청 본문을 천천히 올리거나 응답을 천천히 받아 가는 동안 요청 처리 스레드가 그 연결에 묶인다. Nginx 같은 리버스 프록시는 기본 설정에서 요청과 응답을 버퍼에 받아 두고 뒤쪽 서버와는 빠르게 주고받아, 뒤쪽 서버의 스레드가 느린 연결에 오래 묶이지 않게 한다.
지금 어디에 쓰나 — 정적 파일 요청과 /api 요청을 경로로 나눠 다른 서버로 보내거나, Nginx의 client_max_body_size로 너무 큰 업로드를 앞단에서 거절할 때 쓴다. 쿠버네티스에서는 Ingress 컨트롤러가 이 역할을 맡는다.
클라이언트의 요청을 대신 받아 내부의 서버로 전달하고 그 응답을 클라이언트에 돌려주는 서버다. 클라이언트는 실제 서버를 직접 알지 못한다. 여러 서버로의 요청 분산, TLS 처리, 캐싱, 내부 서버 보호 등의 역할을 한다.
nginx의 proxy_pass와 proxy_set_header
지금 어디에 쓰나 — 스프링 부트 앞에 nginx를 둘 때 server 블록에 listen 80;(또는 listen 443 ssl;)을 두고, location / 안에 proxy_pass와 proxy_set_header 몇 줄을 적는 것이 가장 흔한 설정이다.
proxy_pass와 proxy_set_header는 nginx 설정 파일의 location 블록에 쓰는 지시어다. proxy_pass http://127.0.0.1:8080;은 그 location으로 들어온 요청을 적은 주소의 서버에 넘기라는 뜻이고, 이때 nginx가 그 서버에 새로 연결을 맺는다. proxy_set_header는 넘기는 요청에 헤더를 적어 붙인다. proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;는 받은 X-Forwarded-For 뒤에 쉼표와 자신에게 연결한 상대의 주소($remote_addr)를 붙인 값을 적고, 받은 것이 없으면 그 주소만 적는다. proxy_set_header Host $host;는 클라이언트가 요청에 적은 이름을 Host 헤더로 넘긴다. 따로 적지 않으면 nginx는 Host에 proxy_pass에 적은 주소($proxy_host)를 넣고 Connection: close를 붙인다(ngx_http_proxy_module 문서).
X-Forwarded-For
지금 어디에 쓰나 — 접속 기록에 실제 사용자 IP를 남기거나, 한 IP에서 너무 많이 오는 요청을 막을 때 이 값을 읽는다. nginx에서는 proxy_set_header 설정으로 이 헤더를 붙여 넘기게 한다.
프록시가 요청을 넘길 때 원래 클라이언트의 주소를 적어 주는 요청 헤더다. 프록시 뒤의 서버가 보는 연결 상대는 프록시이므로, 실제 클라이언트의 주소는 이 헤더로만 전해진다. 프록시를 여러 대 거치면 각 프록시가 자신에게 연결한 상대의 주소를 쉼표로 뒤에 덧붙인다. 요청 헤더라서 클라이언트도 마음대로 써넣을 수 있으므로, 서버는 자신이 관리하는 믿을 수 있는 프록시가 붙인 값(뒤쪽 값)만 써야 하고 프록시 뒤에 있지 않다면 읽지 말아야 한다. 표준이 아닌 관례이며, 같은 일을 하는 표준 헤더로 Forwarded가 있다.
502 Bad Gateway
지금 어디에 쓰나 — nginx 뒤의 스프링 부트 서버가 꺼져 있거나 아직 시작 중일 때 브라우저에 nginx의 502 페이지가 뜬다. 이때는 뒤쪽 서버가 떠 있는지, proxy_pass에 적은 포트가 server.port와 맞는지부터 확인한다.
502는 서버가 게이트웨이나 프록시로 일하다가, 요청을 이루려고 접속한 안쪽 서버에게서 올바르지 않은 응답을 받았을 때 쓰는 상태 코드다(RFC 9110 15.6.3절). nginx는 뒤쪽 서버에 연결조차 하지 못했을 때(연결 거부)도 넘길 다음 서버가 없으면 502를 돌려준다(nginx 소스 ngx_http_upstream.c). 이 응답을 만들어 보내는 것은 클라이언트가 연결한 프록시 서버이고, 그 뒤의 진짜 서버가 아니다. 그래서 클라이언트가 502를 받았다는 것은 연결한 상대인 프록시 서버까지는 닿았고, 문제가 프록시 서버와 그 뒤쪽 서버 사이에 있다는 뜻이다.
server.address
지금 어디에 쓰나 — 스프링 부트와 nginx를 같은 컴퓨터에 두는 구성에서 server.address=127.0.0.1을 두면, 바깥 사용자가 8080번으로 스프링 부트를 직접 부르지 못하고 nginx를 거쳐서만 들어오게 할 수 있다. 방화벽으로 그 포트를 막는 방법도 있다.
server.address는 스프링 부트의 설정으로, 내장 서버(톰캣)가 어느 네트워크 주소에서 연결을 기다릴지 정한다. 적지 않으면 그 컴퓨터의 모든 주소(0.0.0.0)에서 기다리고, server.address=127.0.0.1로 적으면 127.0.0.1에서만 기다린다. 127.0.0.1은 컴퓨터가 자기 자신을 가리키는 주소라서, 이렇게 하면 같은 컴퓨터의 프로그램만 그 포트에 연결할 수 있고 다른 컴퓨터에서 오는 연결은 거부된다. 포트는 server.port(기본값 8080)로 정한다.
진짜 서버(원 서버)
진짜 서버는 요청받은 자원에 대해 최종적인 응답을 직접 만들어 낼 수 있는 프로그램으로, RFC 9110 3.6절은 origin server라고 부른다. nginx 뒤의 스프링 부트 애플리케이션이 이 자리에 있다. 프록시 서버는 요청을 넘길 뿐이어서, 응답의 내용을 만드는 쪽은 이 서버다. 프록시 서버가 있으면 클라이언트는 이 서버에 직접 연결하지 않을 수 있고, 이 서버는 연결해 온 상대로 프록시 서버를 보게 된다.

이렇게 바꿔 보세요

  • 처음 설정으로 — 스프링 부트에 연결한 것은 nginx(127.0.0.1)이고, 사용자의 주소 203.0.113.7은 nginx가 적어 넘긴 X-Forwarded-For 헤더로 옵니다.
  • 8080번으로 직접 부르면 — 스프링 부트가 켜져 있어도 사용자는 연결 거부 오류를 받습니다. 스프링 부트는 127.0.0.1로 오는 연결만 받기 때문입니다.
  • server.address 줄을 지우고 직접 부르면 — 연결 상대는 사용자 자신(203.0.113.7)이고, 사이에서 헤더를 적어 줄 nginx가 없으니 X-Forwarded-For는 null입니다.
  • 스프링 부트를 끄면 — nginx가 8080번에 연결하지 못하고, 사용자에게 502 Bad Gateway를 돌려줍니다. 이 응답은 nginx가 만든 것입니다.
  • 스프링 부트를 끈 채 직접 부르면 — 대신 답해 줄 nginx를 지나지 않으므로 502가 아니라 연결 거부 오류를 받습니다.
  • nginx를 끄면 — 스프링 부트가 멀쩡해도 사용자는 연결 거부 오류를 받습니다. 사용자가 쓰는 문은 nginx의 80번 하나입니다.

처음 설정으로 실행하면

  1. 사용자(203.0.113.7)가 코드 칸의 주소로 GET /hello 요청을 보냅니다. 주소에 포트 번호가 없으므로 서버 컴퓨터 192.0.2.10의 80번에 연결합니다. 80번에서 기다리는 것은 nginx입니다(listen 80). 사용자가 쓰는 주소에는 스프링 부트의 번호 8080이 없습니다.
  2. nginx가 요청을 받고, proxy_pass http://127.0.0.1:8080 줄에 따라 같은 컴퓨터의 8080번에 새로 연결해 같은 GET /hello를 넘깁니다. 이 연결은 사용자가 맺은 연결과 따로이고, 맺은 쪽은 nginx입니다. 넘길 때 proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for 줄에 따라, 자신에게 연결한 상대의 주소(203.0.113.7)를 X-Forwarded-For 헤더에 적어 붙입니다. Host $host 줄은 사용자가 요청에 적은 이름(192.0.2.10)을 Host 헤더로 넘기는 줄이고, 이 실습의 결과에는 쓰지 않습니다. nginx가 연결한 곳은 127.0.0.1이므로, server.address=127.0.0.1인 스프링 부트도 이 연결을 받습니다.
  3. 스프링 부트의 컨트롤러가 실행됩니다. request.getRemoteAddr()는 127.0.0.1입니다. 이 서버에 연결을 맺은 것은 사용자가 아니라 같은 컴퓨터의 nginx이기 때문입니다. 사용자의 주소 203.0.113.7은 request.getHeader("X-Forwarded-For")로 얻습니다. nginx가 적어 붙인 값입니다.
  4. nginx가 스프링 부트의 응답을 받아 사용자에게 돌려줍니다. 사용자가 받은 것은 상태 코드 200과 본문 "연결한 상대: 127.0.0.1, X-Forwarded-For: 203.0.113.7"입니다. 사용자는 자신이 연결한 nginx하고만 주고받았습니다.

실행 결과

  • nginx를 거치면 연결이 둘로 나뉩니다. 사용자는 nginx(80번)에 연결하고, nginx가 스프링 부트(8080번)에 따로 연결해 요청을 넘깁니다. 그래서 스프링 부트의 getRemoteAddr()는 사용자가 아니라 nginx의 주소(127.0.0.1)입니다.
  • 진짜 사용자의 주소는 nginx가 proxy_set_header로 적어 넘긴 X-Forwarded-For 헤더로 전해 받습니다. 스프링 부트가 이 헤더를 읽어 getRemoteAddr()에 반영하게 하는 설정(server.forward-headers-strategy)은 세부 동작 실습 "프록시와 리버스 프록시"에서 다룹니다.

코드

# 사용자(다른 컴퓨터 203.0.113.7)가 부르는 주소
# 포트 번호를 적지 않으면 http는 80번으로 간다
http://192.0.2.10/hello

# nginx 설정 (서버 컴퓨터 192.0.2.10에서 실행)
server {
    listen 80;
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

# application.properties (스프링 부트, 같은 컴퓨터에서 실행)
server.port=8080
# 127.0.0.1(이 컴퓨터 자신의 주소)로 오는 연결만 받는다
server.address=127.0.0.1

// HelloController.java
// HelloController는 예시로 지은 이름이다. @RestController와 @GetMapping은
// 스프링이, HttpServletRequest는 서블릿 API(jakarta.servlet)가 준다.
import jakarta.servlet.http.HttpServletRequest;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {
    @GetMapping("/hello")
    public String hello(HttpServletRequest request) {
        // 이 서버에 연결을 맺은 상대의 주소
        String peer = request.getRemoteAddr();
        // 요청에 붙어 온 X-Forwarded-For 헤더 (없으면 null)
        String xff = request.getHeader("X-Forwarded-For");
        return "연결한 상대: " + peer + ", X-Forwarded-For: " + xff;
    }
}

이 모형의 전제

검증 실행(verify/net/proxy_basic_probe_boot.js)은 열두 가지 조합을 모두 이 PC 안에서만 실행했고, 외부 네트워크는 쓰지 않았습니다. 스프링 부트 쪽은 실제로 실행했습니다. 화면의 HelloController에 package 줄 하나만 붙여 JDK 21로 컴파일하고, 화면의 application.properties 줄을 그대로 파일로 써서 스프링 부트 4.1.1(스프링 7.0.9, 내장 톰캣 11.0.24)로 띄웠습니다. 바꾼 것은 server.port의 8080을 빈 포트 번호로 바꾼 것뿐이고, 띄우는 Main 클래스와 /hello 요청 수를 세는 필터는 실행을 위해 덧붙였습니다(화면에는 없음). netstat으로 보니 server.address=127.0.0.1이면 127.0.0.1에서만, 그 줄이 없으면 0.0.0.0(모든 주소)에서 기다렸습니다. nginx는 이 컴퓨터에 없어 내려받지 않았고, 화면의 nginx 설정을 읽어 nginx 문서대로 움직이게 만든 Node.js 24.18.0 프로그램이 nginx 역할을 대신했습니다. 이 프로그램은 받은 요청의 Host와 Connection은 넘기지 않고 나머지 헤더는 그대로 넘기며, proxy_set_header 줄의 $host(요청의 Host에 적힌 이름)와 $proxy_add_x_forwarded_for(받은 X-Forwarded-For 뒤에 쉼표와 $remote_addr를 붙인 값, 받은 것이 없으면 $remote_addr)를 적용하고, 기본값 Connection: close를 붙여 HTTP/1.1로 뒤쪽에 넘깁니다. 뒤쪽에 연결하지 못하면 502와 nginx 소스에 적힌 502 페이지를 돌려줍니다. 그러니 nginx 쪽 동작은 실제 nginx로 실행한 것이 아니라 문서와 소스를 대조해 옮긴 것입니다. 문서로 확인한 것은 nginx.org의 ngx_http_core_module(listen의 기본값, server와 location, $host, $remote_addr), ngx_http_proxy_module(proxy_pass, proxy_set_header의 기본값 Host $proxy_host와 Connection close, 원래 요청의 Host와 Connection은 넘기지 않는다는 것, $proxy_add_x_forwarded_for의 정의, proxy_http_version이 1.29.7부터 기본 1.1이라는 것), nginx 소스 ngx_http_upstream.c(뒤쪽 연결 실패는 오류 갈래로 처리되고, 넘길 다음 서버가 없으면 502로 끝남)와 ngx_http_special_response.c(502 페이지 글), 스프링 부트 4.1.1 jar의 설정 설명(server.address는 서버가 묶일 네트워크 주소, server.port는 기본값 8080), RFC 9110 15.6.3절(502)입니다. nginx 문서에는 "뒤쪽 연결에 실패하면 502"라는 문장이 따로 없어서 소스로 확인했습니다. 502 페이지의 마지막 줄은 server_tokens 설정에 따라 nginx 뒤에 버전 번호가 붙을 수 있습니다. 화면의 사용자 주소 203.0.113.7과 서버 컴퓨터 주소 192.0.2.10은 문서용 예시 주소이고, 실행에서는 사용자를 127.0.0.10, 서버 컴퓨터의 바깥 주소를 127.0.0.2로 대신했습니다(둘 다 이 PC의 루프백 주소). 그래서 "다른 컴퓨터에서 8080번으로 부르면 거부된다"는 것은 127.0.0.1에서만 기다리는 스프링 부트에 127.0.0.2로 연결하면 거부되는 것으로 확인했고, 실제 다른 컴퓨터에서 실행하지는 않았습니다. 화면의 80과 8080도 실제로는 빈 포트 번호를 썼고, 꺼진 프로그램은 띄우지 않고 그 번호를 방금 닫은 빈 포트로 대신했습니다. 대조한 것(verify/net/cmp_proxy_basic.js, 13가지 모두 일치)은 사용자가 받은 것(상태 코드, 본문, 연결 거부), 컨트롤러가 돌려준 getRemoteAddr()와 X-Forwarded-For, nginx 역할 프로그램이 받은 요청 수와 붙인 헤더, 스프링 부트가 받은 /hello 요청 수, 화면의 코드가 실행이 읽은 글과 같은지입니다. 톰캣은 상태 줄에 OK 같은 글을 붙이지 않아서 표에는 상태 코드 200만 적었습니다. 이 실습은 HTTPS(443번)와 인증서, 스프링 부트가 X-Forwarded-For를 읽어 getRemoteAddr()에 반영하게 하는 server.forward-headers-strategy와 위조된 헤더, 응답이 늦을 때의 504는 다루지 않았습니다. 앞의 것들은 세부 동작 실습 "프록시와 리버스 프록시"에서, 서버를 여러 대로 나누는 것은 "로드밸런서와 스케일 아웃"에서, 응답 보관은 "CDN"에서 다룹니다.
