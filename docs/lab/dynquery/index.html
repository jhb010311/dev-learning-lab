동적 쿼리: Specification과 Querydsl

검색 조건이 있을 때만 where에 붙이려면

왜 생겼나 — 조건마다 JPQL 문자열을 이어 붙이면 where와 and의 자리, 띄어쓰기를 사람이 맞춰야 하고, 컴파일러는 그 문자열을 검사하지 못해 잘못 이은 조합은 그 요청이 실제로 들어올 때에야 드러난다. 값까지 문자열에 넣으면 SQL Injection의 통로도 된다. JPA 표준의 Criteria API는 조건을 객체로 만들어 넘기면 where와 and를 JPA가 붙여 주게 했고, 스프링 데이터 JPA의 Specification은 그 조건을 메서드 하나씩으로 나눠 이름을 붙이고 and나 or로 조합하게 했다. Querydsl은 엔티티를 보고 만든 Q클래스로 필드를 가리켜 필드 이름 오타까지 컴파일할 때 잡는다.

지금 어디에 쓰나 — 관리자 화면의 회원 검색, 쇼핑몰의 상품 필터처럼 입력한 항목만 조건이 되는 검색 기능에 쓴다. 스프링 데이터 JPA를 쓰는 프로젝트에서는 리포지토리에 JpaSpecificationExecutor를 더해 Specification으로 조건을 조합하거나, Querydsl을 함께 쓰는 경우가 흔하다. 조건이 늘 같은 쿼리라면 쿼리 메서드나 @Query로 충분하다.

회원 검색 화면에서 이름과 나이는 입력할 수도 있고 비워 둘 수도 있습니다. 입력된 조건만 where에 넣어야 하므로 쿼리의 모양이 요청마다 달라집니다. 이런 쿼리를 동적 쿼리라고 합니다. 스프링 데이터 JPA의 Specification, JPA의 Criteria API, Querydsl은 조건을 문자열이 아니라 객체로 조립하고, where와 and는 도구가 붙입니다.

실행으로 대조 · Specification, Criteria API, Querydsl, 문자열 직접 잇기의 스물네 조합을 스프링 부트 4.1.1, 스프링 데이터 JPA 4.1.1, Hibernate 7.4.5, H2, Querydsl 5.1.0에서 실행해 대조

이 실습에 나오는 개념

동적 쿼리
왜 생겼나 — 입력할 수 있는 조건이 여러 개이면 그 조합마다 쿼리를 미리 만들어 둘 수 없다(조건이 5개면 조합이 32가지다). 동적 쿼리는 실행할 때 들어온 조건만 골라 쿼리 하나를 조립해서, 조합마다 쿼리를 따로 두지 않게 한다.
지금 어디에 쓰나 — 목록 화면에서 정렬 기준이나 검색 칸을 사용자가 골라 쓰는 조회에 필요하다. MyBatis를 쓰는 프로젝트에서는 XML의 <if>, <where> 태그로 들어온 조건만 붙인다.
실행할 때의 입력에 따라 문장의 모양이 달라지는 쿼리다. 검색 화면처럼 입력된 조건만 where에 넣어야 할 때 필요하다. 문자열을 이어 붙여 만들면 조건이 하나도 없을 때 where만 남거나, and가 엉뚱한 자리에 가거나, 띄어쓰기가 빠지는 실수가 생기고, 이런 오류는 컴파일이 아니라 그 조합의 요청이 들어왔을 때에야 드러난다. 그래서 조건을 객체로 조립하는 스프링 데이터 JPA의 Specification, JPA의 Criteria API, Querydsl을 쓴다. 어떤 방식이든 값은 문자열에 직접 넣지 않고 파라미터로 바인딩한다.
Specification
왜 생겼나 — Criteria API로 동적 쿼리를 짜면 조건을 만드는 코드가 메서드 하나에 길게 늘어서고, 같은 조건을 다른 검색에서 다시 쓰기 어렵다. Specification은 조건 하나하나에 이름을 붙여 따로 두고, 필요한 것만 골라 조합하게 해 준다.
지금 어디에 쓰나 — 스프링 데이터 JPA 프로젝트에서 Querydsl 같은 라이브러리를 더하지 않고 검색 조건을 조합할 때 쓴다. 정렬이나 페이지를 함께 쓰는 findAll(spec, pageable)로 목록 화면을 만든다.
스프링 데이터 JPA가 주는 인터페이스로, 검색 조건 하나를 Criteria API로 만드는 방법을 메서드 하나(toPredicate)로 나타낸다. 보통 (root, query, cb) -> cb.equal(root.get("name"), name)처럼 람다로 쓰고, Specification.where(a).and(b)처럼 and, or로 조합한다. 리포지토리가 JpaSpecificationExecutor를 함께 상속하면 findAll(spec), count(spec)에 넘겨 실행할 수 있다. 람다가 조건 대신 null을 돌려주면 그 조건은 빠지고 남은 조건만 where에 들어가므로, 값이 없는 조건을 빼는 동적 쿼리에 맞다. 스프링 데이터 JPA 4.1.1에서는 where나 and에 Specification 자체를 null로 넘기면 IllegalArgumentException이 난다.
Criteria API
지금 어디에 쓰나 — Querydsl 같은 라이브러리를 더하지 않고 동적 쿼리를 만들어야 할 때 쓴다. JPA 표준이라서 Hibernate가 아닌 다른 JPA 구현으로 바꿔도 같은 코드가 돈다.
JPA 표준이 정한, 쿼리를 문자열이 아니라 자바 객체로 조립하는 API다. CriteriaBuilder로 조건 객체(Predicate)를 만들어 목록에 모은 뒤 where에 넘기면, 조건의 개수에 맞게 where와 and가 만들어진다. 조건이 0개이면 where 절이 생기지 않는다. 별도 라이브러리 없이 쓸 수 있지만 코드가 길어 어떤 쿼리인지 읽기 어렵다. 프로퍼티 이름을 문자열로 적으면 이름이 틀려도 컴파일은 되고 실행 중에 예외가 난다.
Querydsl
왜 생겼나 — Criteria API로 짠 쿼리는 코드가 길어 어떤 SQL이 나갈지 한눈에 읽기 어렵다. Querydsl은 select, from, where를 SQL과 비슷한 순서의 메서드로 이어 적게 해서, 자바 코드로 쓰면서도 쿼리 모양이 읽히게 한다.
지금 어디에 쓰나 — 조건 조립뿐 아니라 조인, group by 집계, DTO로 바로 받는 조회처럼 JPQL 문자열이 길어지는 조회를 자바 코드로 쓸 때도 쓴다.
쿼리를 자바 코드로 조립하게 해 주는 라이브러리다. 엔티티 클래스를 보고 Q클래스(예: QMember)를 미리 만들어 두고, m.name.eq("김철수")처럼 프로퍼티와 조건을 메서드로 적는다. 프로퍼티 이름이나 타입이 틀리면 컴파일 오류가 나므로 실행 전에 잘못을 찾을 수 있다. where에 여러 조건을 넘기면 and로 묶이고 null인 조건은 건너뛰므로, 값이 없을 때 null을 돌려주는 조건 메서드를 만들어 동적 쿼리를 짧게 쓸 수 있다. BooleanBuilder에 조건을 하나씩 쌓는 방법도 있다. JPA 표준이 아니므로 의존성과 Q클래스를 만드는 빌드 설정을 따로 추가해야 한다.
SQL Injection
사용자 입력이 SQL 문의 일부로 해석되어 공격자가 의도한 쿼리가 실행되는 공격이다. 입력값을 문자열로 이어 붙여 SQL을 만들 때 발생한다. SQL 구조와 값을 분리하는 바인드 파라미터(PreparedStatement)를 쓰면 입력이 항상 값으로만 처리되어 막을 수 있다.

이렇게 바꿔 보세요

  • 처음 설정으로 — null을 돌려준 이름 조건은 빠지고 나이 조건 하나만 where에 들어갑니다.
  • 조건을 하나도 넣지 않으면 — 남은 조건이 없어서 where 절이 아예 생기지 않고 전체가 조회됩니다.
  • Criteria API로 조건 둘을 조립 — 조건 객체 두 개를 where에 넘기면 JPA가 and로 묶습니다. Specification의 람다가 받는 cb도 이 API의 CriteriaBuilder입니다.
  • Querydsl로 조립 — where가 null인 조건을 건너뛰어, 이름 조건만 남습니다. 나간 SQL은 Specification, Criteria API와 같습니다.
  • 이름 칸에 따옴표가 섞이면 — 값은 ? 자리에 따로 바인딩되므로 그냥 이상한 이름일 뿐이고, 0명이 조회됩니다.
  • 문자열을 직접 이어 붙이면 — where 바로 뒤에 and가 와서 문법 오류가 납니다. 조건을 둘 다 넣어 시험하면 놓치는 오류입니다.
  • 이어 붙인 문자열에 따옴표가 섞이면 — 넣은 따옴표가 문자열을 닫아 or 조건이 생기고, 회원 7명이 모두 조회됩니다.

처음 설정으로 실행하면

  1. 검색 조건: 이름은 입력하지 않아 null, 나이는 20입니다. null이 아닌 조건만 쿼리의 where에 넣어야 합니다.
  2. 1번째 줄 nameEq(name): 예시로 만든 메서드입니다. 조건을 바로 만들지 않고, 쿼리를 만들 때 불릴 람다(Specification)를 돌려줍니다. 이 람다는 name이 null이면 조건 대신 null을, 아니면 cb.equal(root.get("name"), name)을 돌려주도록 적혀 있습니다. Specification.where는 스프링 데이터 JPA가 주는 메서드로, 받은 Specification을 출발점으로 삼습니다.
  3. 2번째 줄 .and(ageGoe(age)): ageGoe도 예시로 만든 메서드이고 같은 모양의 람다를 돌려줍니다. and는 스프링 데이터 JPA가 주는 메서드로, 두 Specification을 and로 묶은 새 Specification을 돌려줍니다. 아직 SQL은 만들지 않았습니다.
  4. 3번째 줄 memberRepository.findAll(spec): JpaSpecificationExecutor가 주는 메서드입니다. 스프링 데이터 JPA가 CriteriaQuery를 만들고 두 람다를 부릅니다. nameEq는 null을, ageGoe는 조건 age >= ?를 돌려줍니다. null을 돌려준 조건은 빠지고, 남은 조건 하나만 where에 들어갑니다.
  5. SELECT 한 번이 DB로 나갑니다. SQL의 조건은 "where age >= ?"입니다. ? 자리에 바인딩된 값은 20입니다. 회원 7명 가운데 5명이 조회됩니다.

실행 결과

  • Specification으로 조립한 쿼리에 조건 1개가 남아 5명이 조회됐습니다. 이름과 나이 칸의 여섯 가지 조합이 모두 문법 오류 없이 실행됩니다.
  • where, and, 띄어쓰기를 사람이 쓰지 않습니다. 값이 없을 때 람다가 조건 대신 null을 돌려주면 스프링 데이터 JPA가 그 조건을 빼고 남은 것만 and로 묶습니다. 조건이 늘면 nameEq 같은 메서드를 하나 더 만들어 and로 잇습니다.
  • null은 람다가 조건 대신 돌려주게 합니다. Specification 자체를 null로 넘기면 안 됩니다. 스프링 데이터 JPA 4.1.1에서 Specification.where(null)이나 and(null)은 IllegalArgumentException을 던집니다.

코드

// 필요한 부분만 남김 (클래스 선언, memberRepository 필드, 예시로 만든 Member 엔티티, import는 생략)
// MemberRepository는 예시로 만든 리포지토리. JpaRepository, JpaSpecificationExecutor, Specification은 스프링 데이터 JPA가 주는 것
interface MemberRepository extends JpaRepository<Member, Long>, JpaSpecificationExecutor<Member> { }

// nameEq, ageGoe는 예시로 만든 메서드. 값이 없으면 조건 대신 null을 돌려준다
static Specification<Member> nameEq(String name) {
    return (root, query, cb) -> name == null ? null : cb.equal(root.get("name"), name);
}
static Specification<Member> ageGoe(Integer age) {
    return (root, query, cb) -> age == null ? null : cb.greaterThanOrEqualTo(root.get("age"), age);
}

List<Member> search(String name, Integer age) {
    Specification<Member> spec = Specification.where(nameEq(name))
            .and(ageGoe(age));
    return memberRepository.findAll(spec);
}

search(null, 20);   // 이름은 입력 안 함, 나이는 20 이상

이 모형의 전제

네 가지 방식과 이름 칸 세 가지, 나이 칸 두 가지를 곱한 스물네 가지 조합을 스프링 부트 4.1.1(자동 설정), 스프링 데이터 JPA 4.1.1, Hibernate 7.4.5, H2 데이터베이스, Querydsl 5.1.0(jakarta)에서 화면과 같은 구조의 코드로 실제로 실행해, 성공 여부, 예외의 종류와 오류 위치와 걸린 낱말, DB로 나간 SQL의 where, 바인딩된 값, 조회된 회원 수를 화면과 대조했습니다. Q클래스(QMember)는 컴파일할 때 querydsl-apt가 Member 엔티티를 보고 만든 것을 썼습니다. Specification, Criteria API, Querydsl은 같은 조건이면 나간 SQL이 글자까지 같았습니다. 스프링 데이터 JPA가 null을 돌려준 조건을 빼고 남은 조건만 and로 묶는다는 설명, Querydsl의 where가 null인 조건을 건너뛴다는 설명은 이렇게 나간 SQL에 근거합니다. Specification.where(null)과 and(null)이 IllegalArgumentException을 던진다는 것, Criteria API에서 m.get에 없는 프로퍼티 이름을 주면 컴파일은 되고 실행 중에 PathElementException이 난다는 것, 문자열이라도 조건을 목록에 모아 and로 잇고 값을 바인딩하면 여섯 조합이 모두 바르게 실행된다는 것도 실행으로 확인했습니다. 문법 오류의 위치와 걸린 낱말은 Hibernate 7.4.5가 낸 메시지 기준이고, 다른 버전이나 다른 JPA 구현에서는 다르게 나올 수 있습니다. "where and"에서 Hibernate가 and를 이름으로 읽고 넘어간다는 설명은, 오류가 and가 아니라 그다음 낱말에서 났다는 실행 결과에 근거한 해석입니다. 화면의 SQL where는 테이블 별칭을 걷어 내고 읽기 쉽게 줄인 것입니다. 실제 서비스에서는 조건이 훨씬 많고 or, like, 정렬이 섞이므로 문자열 방식의 실수가 여기보다 생기기 쉽습니다.
