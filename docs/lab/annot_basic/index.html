애너테이션

애너테이션은 무엇이고, 붙이면 누가 무슨 일을 하는가

왜 생겼나 — 애너테이션이 없던 때는 "이 메서드는 테스트다", "이 클래스의 객체는 스프링이 만든다" 같은 정보를 test로 시작하는 메서드 이름 같은 규칙이나 코드와 떨어진 XML 설정 파일로 알려야 해서, 코드를 고치면 설정 파일도 따로 맞춰야 했다. 애너테이션은 그런 표시를 해당 코드 바로 위에 @로 적게 해서, 코드와 표시가 한자리에서 보이고 같이 고쳐지게 한다.

지금 어디에 쓰나 — @Override는 부모의 메서드를 제대로 다시 적었는지 컴파일러가 확인하게 한다. 스프링의 @Service, @Repository, @Controller, @Component는 그 클래스의 객체를 스프링이 만들어 빈으로 등록하게 하고, @GetMapping, @Transactional도 스프링이 읽어서 일한다. JUnit의 @Test는 그 메서드를 테스트로 실행하게 한다. 애너테이션을 직접 만드는 일은 드물고, 대개 자바와 프레임워크가 만들어 둔 것을 붙여 쓴다.

애너테이션은 @Service, @Override, @Test처럼 @로 시작해 클래스나 메서드 위에 붙이는 꼬리표입니다. 꼬리표 자체에는 실행되는 코드가 없고, 뜻은 그것을 읽는 쪽이 정합니다. @Override는 컴파일러가, @Service는 스프링이(컴포넌트 스캔으로 찾은 클래스의 객체를 만들어 빈으로 등록), @Test는 JUnit이 읽어서 일합니다. 이 실습은 세 애너테이션을 붙였다 뗐다 하고, 읽는 쪽(스프링, JUnit)을 거치거나 거치지 않으면서 같은 코드를 컴파일하고 실행해 무엇이 달라지는지 봅니다. 이어서 @Service와 @Override의 실제 선언에서 @Retention이 꼬리표를 어디까지 남기는지 보고, 마지막으로 애너테이션과 그것을 읽는 코드를 직접 만들어 봅니다. 코드에 나오는 OrderService, Order, OrderTest, Job은 이 실습에서 예시로 만든 클래스입니다.

실행으로 대조 · JDK 21, 스프링 7.0.9, JUnit 6.0.3으로 화면 코드 열일곱 조합을 컴파일·실행(실제 컴포넌트 스캔, JUnit Launcher, javap)해 결과 표와 예외·컴파일 오류 문구, 빈 이름, @Service·@Override·@Test의 실제 선언까지 대조

이 실습에 나오는 개념

애너테이션
코드에 붙이는 메타데이터로, 그 자체로는 동작하지 않고 컴파일러나 프레임워크가 읽어서 처리한다. @Override처럼 컴파일러가 검사에 쓰는 것과 @Transactional, @Autowired처럼 프레임워크가 실행 중에 리플렉션으로 읽어 기능을 적용하는 것이 있다.
@Override
왜 생겼나 — 재정의는 이름과 매개변수가 맞으면 조용히 이루어져서, 부모 메서드의 이름이 나중에 바뀌면 자식 메서드는 아무 오류 없이 재정의가 아닌 별개의 메서드로 남는다. @Override는 재정의하려는 뜻을 코드에 적어 이런 어긋남이 컴파일 오류로 드러나게 했다.
지금 어디에 쓰나 — toString, equals, hashCode를 재정의하거나 인터페이스의 메서드를 구현할 때 붙인다. 개발 도구(IDE)가 재정의 코드를 만들어 줄 때도 함께 적어 준다.
바로 아래 메서드가 상위 클래스나 인터페이스의 메서드를 재정의한 것임을 나타내는 애너테이션이다. 컴파일러가 이 표시를 읽고 실제로 재정의가 맞는지 확인하며, 아니면 컴파일 오류를 낸다. 메서드 이름이나 매개변수를 잘못 적어 재정의가 아닌 새 메서드를 만들어 버리는 실수를 잡아 준다. 붙이지 않아도 재정의는 되고 프로그램의 동작도 달라지지 않지만, 실수를 막기 위해 재정의하는 메서드에는 항상 붙인다. 소스 코드까지만 남는 애너테이션이라 class 파일에는 적히지 않는다.
@Service와 @Repository
왜 생겼나 — 모든 빈에 @Component만 붙이면 클래스가 무슨 역할인지 코드에서 드러나지 않고, 데이터 접근 클래스에만 예외 변환을 적용하는 것처럼 역할별로 다르게 다룰 근거도 없다. 그래서 스프링은 @Component를 바탕으로 역할 이름을 붙인 애너테이션을 따로 두었다.
지금 어디에 쓰나 — 스프링 웹 애플리케이션에서 업무 규칙을 처리하는 서비스 클래스에는 @Service를, DB를 다루는 클래스에는 @Repository를 붙인다. 스프링 데이터 JPA의 JpaRepository를 상속한 인터페이스는 스프링이 따로 찾아 등록하므로 @Repository를 붙이지 않아도 된다.
@Service와 @Repository는 스프링이 주는 애너테이션으로, 클래스 위에 붙이면 컴포넌트 스캔이 그 클래스를 찾아 객체를 만들어 빈으로 등록한다. 둘 다 선언에 @Component가 붙어 있어서(메타 애너테이션) @Component를 붙인 것과 같은 방식으로 찾아지며, @Controller도 그렇다. 이름이 다른 것은 클래스의 역할(업무 처리, 데이터 접근, 요청 처리)을 드러내기 위해서다. @Repository는 하나가 더 있어서, PersistenceExceptionTranslationPostProcessor가 등록되어 있으면(스프링 부트는 데이터 접근 모듈을 쓸 때 자동 설정으로 등록한다) 그 빈에서 나는 JPA 같은 기술의 예외를 스프링의 DataAccessException 계열로 바꿔 던지는 대상이 된다. 애너테이션 자체는 꼬리표일 뿐이어서, 스프링을 시작하지 않고 new로 객체를 만들면 아무 일도 하지 않는다.
컴포넌트 스캔
왜 생겼나 — 빈을 클래스마다 XML이나 @Bean 메서드로 하나씩 등록하면, 클래스를 만들 때마다 등록 목록도 함께 고쳐야 한다. 컴포넌트 스캔은 클래스에 애너테이션만 붙이면 스프링이 찾아 등록하게 했다.
지금 어디에 쓰나 — 직접 만든 서비스·리포지토리·컨트롤러는 보통 이 방식으로 등록한다. 그래서 @SpringBootApplication 클래스는 프로젝트의 가장 위 패키지에 두고, 그 밖의 패키지까지 찾게 하려면 scanBasePackages 속성으로 지정한다.
지정한 패키지 아래에서 @Component 계열 애너테이션(@Service, @Repository, @Controller 등)이 붙은 클래스를 찾아 자동으로 빈으로 등록하는 기능이다. Spring Boot에서는 @SpringBootApplication이 붙은 클래스의 패키지와 그 하위 패키지가 기본 대상이다.
@Test
왜 생겼나 — JUnit 3까지는 이름이 test로 시작하는 메서드를 테스트로 보았기 때문에, 메서드 이름을 그 규칙에 맞춰 지어야 했다. @Test는 이름과 상관없이 붙은 표시만 보고 테스트를 찾게 해서, 이름을 확인하려는 내용대로 지을 수 있게 한다.
지금 어디에 쓰나 — 테스트로 돌릴 메서드마다 위에 붙이며, IntelliJ 같은 IDE는 @Test가 붙은 메서드 옆에 실행 단추를 보여 준다. 같은 테스트를 값만 바꿔 여러 번 돌릴 때는 @ParameterizedTest를 붙인다.
@Test는 메서드 위에 붙여, 그 메서드가 테스트 메서드라고 JUnit에 알리는 애너테이션이다. 문서에 따르면 @Test가 붙은 메서드는 private이거나 static이면 안 되고 값을 돌려주면 안 된다. JUnit은 @Test(또는 @RepeatedTest, @ParameterizedTest 같은 애너테이션)가 붙은 메서드를 테스트로 세므로, 내용이 테스트처럼 생겼어도 표시가 없는 메서드는 테스트로 세지 않는다. 실행한 JUnit 6.0.3에서는 @Test가 없는 메서드를 가진 클래스를 실행하면 찾은 테스트가 0개이고, 오류도 실패도 없이 그 메서드가 한 번도 실행되지 않았다.
@Retention과 @Target
왜 생겼나 — 애너테이션마다 붙일 자리와 남길 시점을 정할 방법이 없다면, 메서드용 표시를 필드에 잘못 붙여도 컴파일러가 잡지 못하고, 컴파일러만 보는 표시도 실행 중까지 남는다. @Target과 @Retention은 애너테이션을 만드는 쪽이 이 둘을 선언에 정해 두게 했다.
지금 어디에 쓰나 — 쓰는 쪽은 보통 직접 적지 않는다. 스프링·JUnit·자바가 주는 애너테이션의 선언에 이미 적혀 있어, 실행 중에 읽힐지(RUNTIME)와 어디에 붙일 수 있는지가 정해져 있다. 애너테이션을 직접 만들 때만 함께 적는다.
애너테이션의 선언에 붙여 그 애너테이션의 성질을 정하는 두 애너테이션이다. @Retention은 표시를 어디까지 남길지 정한다. SOURCE는 소스 코드까지만(@Override), CLASS는 class 파일까지(스프링의 @Contract), RUNTIME은 실행 중까지 남겨 리플렉션으로 읽을 수 있게 한다(@Transactional, @Test, @Deprecated). 적지 않으면 CLASS가 된다. @Target은 붙일 수 있는 곳(TYPE은 클래스 같은 타입 선언, METHOD는 메서드, FIELD는 필드 등)을 정하며, 맞지 않는 곳에 붙이면 컴파일 오류가 난다. @Transactional의 선언에는 @Target({ElementType.TYPE, ElementType.METHOD})와 @Retention(RetentionPolicy.RUNTIME)이 붙어 있다.
메타 애너테이션
왜 생겼나 — 애너테이션마다 "붙일 곳", "남길 곳", "스프링이 빈으로 다룰지" 같은 성질을 처리하는 코드를 따로 만들면, 새 애너테이션이 생길 때마다 읽는 쪽도 고쳐야 한다. 메타 애너테이션은 그 성질을 선언 위의 표시로 적게 해서, 읽는 쪽이 선언만 보고 다룰 수 있게 했다.
지금 어디에 쓰나 — 스프링의 @Service, @Repository, @Controller, @RestController, @SpringBootApplication이 모두 다른 애너테이션을 메타 애너테이션으로 묶어 만든 것이다. 여러 애너테이션을 자주 함께 붙인다면, 그것들을 메타 애너테이션으로 붙인 애너테이션을 직접 선언해 한 줄로 줄이기도 한다.
메타 애너테이션은 다른 애너테이션의 선언 위에 붙은 애너테이션이다. 자바가 주는 @Target, @Retention, @Documented가 대표적이고, 스프링의 @Service 선언에 붙은 @Component도 메타 애너테이션이다. 스프링은 클래스에 붙은 애너테이션의 선언까지 따라가 읽기 때문에, @Service가 붙은 클래스를 @Component가 붙은 클래스처럼 컴포넌트 스캔으로 찾는다. 자바의 리플렉션 메서드 isAnnotationPresent는 이렇게 따라가 읽지 않으므로, @Service가 붙은 클래스에 isAnnotationPresent(Component.class)를 물으면 false다.
@interface
왜 생겼나 — 자바가 미리 만들어 둔 애너테이션만 쓸 수 있다면 프레임워크나 우리 프로그램에 필요한 표시는 붙일 수 없다. @interface는 필요한 표시를 누구나 선언하게 해서, 스프링이나 JUnit 같은 도구가 자기 표시를 만들어 줄 수 있게 했다.
지금 어디에 쓰나 — 대개는 선언을 직접 쓰지 않고 자바·스프링·JUnit이 선언해 둔 것을 붙여 쓴다. 선언을 읽을 일은 @Service가 왜 빈이 되는지처럼 동작의 근거를 찾을 때다. 직접 선언하는 것은 "실행 시간을 잴 메서드"처럼 여러 곳에 같은 표시를 붙이고 스프링 AOP 같은 읽는 쪽과 함께 쓸 때다.
@interface는 애너테이션을 선언하는 문법이다. 일반 인터페이스 선언의 interface 앞에 @를 붙여 쓴다. 자바의 @Override, 스프링의 @Service, JUnit의 @Test도 모두 이렇게 선언되어 있고, 선언 위에 붙인 @Target(붙일 수 있는 곳)과 @Retention(어디까지 남길지)이 그 애너테이션의 성질을 정한다. 중괄호 안이 비어 있으면 값을 받지 않는 표시(마커 애너테이션)이고, 메서드 모양의 선언을 두면 @Service("이름")처럼 값을 받는 요소가 된다. 선언만으로는 실행되는 코드가 생기지 않으며, 표시를 읽고 일하는 쪽(컴파일러, 스프링, JUnit, 또는 직접 쓴 코드)이 따로 있어야 한다. 직접 선언할 때 @Retention을 적지 않으면 CLASS가 되어 실행 중에는 리플렉션으로 읽을 수 없다.

이렇게 바꿔 보세요

  • 처음 설정으로 — 스프링이 @Service를 읽고 OrderService의 객체를 만들어 빈으로 등록합니다. 그래서 getBean으로 받아 쓸 수 있습니다.
  • @Service를 떼면 — 스프링이 OrderService를 빈으로 만들지 않아, getBean이 NoSuchBeanDefinitionException으로 멈춥니다.
  • 스프링 없이 new로 만들면 — 읽는 쪽인 스프링이 없으니 @Service는 아무 일도 하지 않습니다.
  • @Override를 붙이고 이름을 잘못 적으면 — @Override를 읽는 컴파일러가 재정의가 아니라는 오류를 내고 컴파일을 멈춥니다.
  • @Test를 붙이고 JUnit으로 실행하면 — JUnit이 @Test를 읽고 total()을 테스트로 찾아 부릅니다.
  • @Retention: 꼬리표는 어디까지 남나 — @Service는 @Retention(RUNTIME)이라 class 파일에 남고, @Override는 @Retention(SOURCE)라 컴파일이 끝나면 버려집니다.
  • 직접 만든 @Run — @interface로 만든 @Run에는 정해진 뜻이 없어서, 읽고 일하는 코드도 우리가 써야 합니다.

처음 설정으로 실행하면

  1. OrderService는 이 실습에서 예시로 만든 클래스이고, 그 위의 @Service는 스프링이 주는 애너테이션입니다. 애너테이션은 @로 시작해 클래스나 메서드 위에 붙이는 꼬리표입니다. @Service라고 적는 것만으로는 객체가 만들어지지도, 메서드가 실행되지도 않습니다.
  2. javac가 두 파일을 컴파일합니다. 컴파일러는 @Service가 클래스에 붙일 수 있는 애너테이션인지만 확인하고 class 파일에 기록해 둡니다. @Service는 스프링이 @Retention(RetentionPolicy.RUNTIME)으로 선언해 두어서, 프로그램이 실행되는 동안에도 읽을 수 있는 꼬리표로 남습니다.
  3. main의 new AnnotationConfigApplicationContext("app")가 스프링을 시작합니다. 스프링은 app 패키지의 클래스를 훑으며 꼬리표를 읽습니다. 이것을 컴포넌트 스캔이라고 합니다. 스프링이 찾는 것은 @Component, 그리고 @Service처럼 선언에 @Component가 붙어 있는 애너테이션입니다.
  4. OrderService에 @Service가 붙어 있습니다. 스프링이 OrderService의 객체를 하나 만들어 빈(스프링이 만들어 관리하는 객체)으로 등록합니다. 빈의 이름은 클래스 이름의 첫 글자를 소문자로 바꾼 orderService입니다. 객체를 만든 것은 우리 코드의 new가 아니라 스프링입니다.
  5. context.getBean(OrderService.class)가 스프링에게 OrderService 빈을 달라고 합니다. 스프링이 만들어 둔 객체를 돌려주고, service.name()이 돌려준 "주문 서비스"가 출력됩니다.

실행 결과

  • 애너테이션은 코드에 붙이는 꼬리표이고, 그 뜻은 읽는 쪽이 정합니다. @Service를 읽은 것은 스프링의 컴포넌트 스캔이었고, 스프링이 OrderService의 객체를 만들어 빈으로 등록했기 때문에 getBean이 그 객체를 받아 올 수 있었습니다.
  • @Repository와 @Controller도 선언에 @Component가 붙어 있어서 같은 방식으로 빈이 됩니다. @Override는 컴파일러가, @Test는 JUnit이 읽는다는 것은 다음 물음들에서 봅니다.

코드

// 파일: app/OrderService.java
package app;

import org.springframework.stereotype.Service;

// OrderService는 예시로 만든 클래스, @Service는 스프링이 주는 애너테이션
@Service
public class OrderService {
    public String name() {
        return "주문 서비스";
    }
}

// 파일: app/Main.java
package app;

import org.springframework.context.ApplicationContext;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class Main {
    public static void main(String[] args) {
        // 스프링을 시작한다. app 패키지의 클래스를 훑는다(컴포넌트 스캔)
        ApplicationContext context =
                new AnnotationConfigApplicationContext("app");
        // 스프링이 만들어 둔 OrderService 객체를 달라고 한다
        OrderService service = context.getBean(OrderService.class);
        System.out.println(service.name());
    }
}

이 모형의 전제

컴파일러와 실행 환경은 JDK 21.0.12.1, 스프링 프레임워크 7.0.9(스프링 부트 없이 AnnotationConfigApplicationContext로 시작), JUnit Jupiter 6.0.3(JUnit Platform Launcher 6.0.3으로 실행)입니다. 물음에 쓰이는 열일곱 조합(@Service, @Override, @Test, 직접 만든 @Run마다 네 가지와 선언을 보는 물음 하나)의 화면 코드를 이 실습의 code 함수에서 그대로 꺼내 javax.tools로 컴파일했습니다. 컴파일에 성공한 것은 새 자바 프로세스로 실행하고(@Test를 JUnit으로 실행하는 조합은 Launcher로 실행), 표준 출력과 예외, JUnit이 찾은 테스트 수와 통과 수를 잡아 결과 표와 대조했습니다. 컴포넌트 스캔은 실제 스캔이며 OrderService를 손으로 등록하지 않았습니다. NoSuchBeanDefinitionException의 메시지, @Override의 컴파일 오류 문구, 빈 이름 orderService, @Service 자리에 @Repository, @Controller, @Component를 붙여도 getBean이 성공하는 것, 메서드 위에 @Service를 붙이면 컴파일 오류가 나는 것, javap -v로 본 OrderService.class에 Service만 RuntimeVisibleAnnotations로 남고 Override는 없는 것, @Override를 붙인 Order.class에도 Override가 남지 않는 것도 실행해 확인했습니다. 주석에 옮겨 적은 @Service와 @Override의 선언, 단계 문장의 @Test 선언(@Retention(RUNTIME))은 실행 중에 리플렉션으로 읽은 메타 애너테이션과 요소 이름으로 대조했고, 설명 주석은 옮기지 않았습니다. Object의 toString()이 돌려주는 Order@ 뒤의 16진수는 실행마다 다를 수 있어 형식만 대조했습니다. @Retention을 적지 않으면 CLASS가 되어 실행 중에 읽을 수 없다는 문장은 이번에 다시 실행하지 않았고, Java Language Specification(Java SE 21) 9.6.4.2절과 이 실습의 예전 실행 기록(직접 만든 애너테이션에 @Retention이 없으면 isAnnotationPresent가 false)에 기댑니다. 문서는 Java Language Specification 9.6절(@interface 선언), 9.6.4.1절(@Target), 9.6.4.2절(@Retention), 9.6.4.4절(@Override), 스프링 프레임워크 레퍼런스의 컴포넌트 스캔과 메타 애너테이션 절, JUnit 사용자 가이드의 @Test 설명을 확인했습니다. ./gradlew test나 IDE의 실행 단추가 JUnit을 부른다는 문장은 이 실습에서 실행하지 않았습니다. 스프링이 컴포넌트 스캔에서 꼬리표를 읽는 내부 방식, 직접 만든 애너테이션을 스프링 AOP와 함께 쓰는 방법은 다루지 않았고, 애너테이션의 세부 동작은 "세부 동작 실습: 애너테이션"에서 다룹니다.
