로드 밸런서

서버를 여러 대 두면 요청은 어느 서버로 가는가

왜 생겼나 — 서버가 한 대뿐이면 요청이 늘어도 그 한 대가 모두 받아야 하고, 그 서버가 꺼지면 서비스 전체가 멈춘다. 서버를 여러 대 띄우는 것만으로는 어느 요청을 어느 서버가 받을지, 꺼진 서버를 어떻게 피할지가 정해지지 않는다. 로드 밸런서는 요청이 들어오는 입구를 하나로 두고 살아 있는 서버들에 나눠 보내서, 서버를 늘리거나 한 대가 꺼져도 클라이언트가 같은 주소로 계속 쓰게 한다.

지금 어디에 쓰나 — 사용자가 많은 웹 서비스는 같은 스프링 부트 서버를 여러 대 띄우고 그 앞에 로드 밸런서를 둔다. 가장 흔한 것은 nginx이고, nginx 설정의 upstream 블록에 서버 주소들을 적고 proxy_pass로 그 묶음에 넘기면 된다. 클라우드 회사가 주는 로드 밸런서도 같은 일을 하고, 새 버전으로 바꿀 때 서버를 한 대씩 빼고 넣는 데도 쓴다. 로그인 상태처럼 요청 사이에 이어져야 하는 값은 서버 한 대의 메모리에만 두지 않고, 흔히 Redis나 DB처럼 여러 서버가 함께 보는 곳에 둔다.

서버 한 대가 감당하지 못할 만큼 요청이 많으면 같은 서버 프로그램을 여러 대 띄웁니다. 그런데 클라이언트(요청을 보내는 쪽)가 서버 주소를 여러 개 알아야 한다면 불편합니다. 그래서 클라이언트는 주소 하나로만 접속하고, 그 주소에서 요청을 받는 로드 밸런서가 요청을 서버들에 나눠 보냅니다. 이 실습은 서버 한 대에 직접 접속하는 구성과, 서버 두 대 앞에 로드 밸런서를 두는 구성을 견줍니다. 로드 밸런서로는 가장 흔히 쓰는 nginx를 둡니다. 코드 칸에는 세 가지가 있습니다. nginx 설정(upstream 블록에 서버 A, 서버 B의 주소를 적고 proxy_pass로 그 묶음에 넘긴다), 서버를 켜는 명령(같은 app.jar를 포트만 바꿔 두 번 켠다), 그리고 각 서버의 스프링 부트 컨트롤러입니다. #으로 시작하는 줄은 설명입니다. 컨트롤러는 자기가 받은 요청 수를 자기 메모리에 세어 "나는 A, 받은 요청 1번째"처럼 답합니다. 로드 밸런서를 빼 보고, 요청 3번 뒤에 서버 A를 꺼 보면서 클라이언트가 받는 답이 어떻게 달라지는지 봅니다.

일부만 실행으로 확인 · 스프링 부트 쪽은 실제 스프링 부트 4.1.1(내장 톰캣 11.0.24)에 화면의 HelloController를 그대로 컴파일해 화면의 java -jar 인자로 띄우고 네 가지 조합을 실행해 대조(verify/net/cmp_lb_basic.js). nginx는 실행하지 않았고 설정은 nginx 문서(ngx_http_upstream_module, ngx_http_proxy_module)와 대조, 실행에서는 화면의 nginx 설정을 읽어 문서대로 라운드 로빈과 실패한 서버 건너뛰기를 하는 Node 모형이 nginx 역할을 대신함

이 실습에 나오는 개념

로드밸런서
들어오는 요청을 여러 서버에 나눠 보내는 장치다. 서버의 상태를 주기적으로 확인(헬스 체크)해 문제가 있는 서버로는 요청을 보내지 않는다. 한 서버에 부하가 몰리는 것을 막고, 일부 서버에 장애가 나도 서비스를 유지하게 한다.
nginx upstream과 proxy_pass
왜 생겼나 — 서버를 여러 대 띄워도 클라이언트가 그 주소들을 하나하나 알고 고르게 하면, 서버를 늘리거나 뺄 때마다 클라이언트를 고쳐야 한다. upstream과 proxy_pass는 서버 주소 목록을 nginx 설정 한곳에 모아 두고, 클라이언트는 nginx 주소 하나로만 접속하게 해서 서버 구성이 바뀌어도 클라이언트는 그대로 두게 한다.
지금 어디에 쓰나 — 같은 스프링 부트 서버를 여러 대 띄우고 그 앞에 nginx를 두는 구성에서 쓴다. 서버를 한 대 늘리면 upstream에 server 줄을 하나 더하고 nginx 설정을 다시 읽게 한다. 서버마다 몫을 다르게 주려면 server 줄에 weight를, 처리 중인 연결이 적은 서버로 보내려면 upstream에 least_conn을 적는다.
nginx 설정에서 upstream 블록은 요청을 나눠 받을 서버들의 묶음에 이름을 붙이는 자리이고, proxy_pass는 받은 요청을 어디로 넘길지 정하는 줄이다. upstream app { server 127.0.0.1:8081; server 127.0.0.1:8082; }처럼 server 줄에 서버 주소를 하나씩 적고, location / { proxy_pass http://app; }처럼 proxy_pass에 그 묶음 이름을 쓰면 nginx가 받은 요청을 묶음의 서버들에 나눠 넘긴다. upstream은 nginx.conf의 http 블록에 두며, 나누는 방식을 따로 적지 않으면 가중치를 둔 라운드 로빈을 쓴다. proxy_pass에 http://127.0.0.1:8081처럼 주소 하나를 바로 적으면 나누지 않고 그 서버로만 넘긴다.
라운드 로빈
왜 생겼나 — 요청을 받을 서버를 고를 때마다 서버들이 얼마나 바쁜지 따지려면 그 상태를 계속 알아내야 한다. 라운드 로빈은 서버 상태를 보지 않고 정해 둔 순서대로 돌아가며 보내서, 단순한 규칙 하나로 서버마다 받는 요청 수를 비슷하게 맞춘다.
지금 어디에 쓰나 — 요청마다 처리 시간이 비슷한 웹 서버들 앞에 둘 때 흔히 쓴다. 오래 걸리는 요청이 섞여 한 서버에 일이 몰릴 수 있으면, 처리 중인 연결이 가장 적은 서버로 보내는 방식(NGINX의 least_conn)을 대신 쓴다.
라운드 로빈은 요청을 서버들에 차례대로 돌아가며 한 대씩 나눠 주는 방식이다. 서버가 A, B 두 대이면 요청이 A, B, A, B 순으로 간다. NGINX 문서는 서버들에 요청을 고르게 나누는 이 방식이 기본이며 따로 켜는 지시어가 없다고 적고, 서버마다 가중치를 줄 수 있다고 한다. 요청이 몇 번째로 어느 서버에 가는지가 정해진 순서를 따르므로, 서버가 늘 같은 상태일 때 요청은 서버들에 고르게 나뉜다.
실패한 서버 건너뛰기
왜 생겼나 — 꺼진 서버에도 차례대로 요청을 보내면, 그 서버 차례가 된 요청은 모두 오류로 끝난다. 실패한 서버 건너뛰기는 연결이 안 되는 서버를 빼고 다음 서버에 다시 보내서, 서버 한 대가 꺼져도 사용자가 오류를 덜 보게 한다.
지금 어디에 쓰나 — 서버 한 대가 갑자기 멈추거나 다시 켜지는 동안에도 요청이 남은 서버로 가게 하려고 쓴다. 꺼진 서버를 요청이 오기 전에 알아내려고, 서버에 주기적으로 확인 요청을 보내는 헬스 체크를 함께 쓰기도 한다(HAProxy, 클라우드의 로드 밸런서 등).
로드 밸런서가 어느 서버에 연결하려는데 오류가 나면, 그 서버를 쓰지 않고 같은 요청을 다음 서버에 보내는 동작이다. NGINX 문서에서 proxy_next_upstream의 기본값은 error와 timeout이고, error는 서버와 연결을 맺는 중 난 오류도 가리키므로, 연결이 거부되면 요청이 다음 서버로 넘어간다. 또 max_fails(기본 1)번 실패하면 fail_timeout(기본 10초) 동안 그 서버를 쓸 수 없는 서버로 본다. 이 덕분에 서버 한 대가 꺼져도 남은 서버가 있으면 새로 오는 요청은 살아 있는 서버가 받는다(처리 중이던 요청은 실패할 수 있다).
스프링 부트 실행 인자(--server.port)
왜 생겼나 — 같은 프로그램을 포트나 이름만 바꿔 여러 대 켜려고 설정 파일을 매번 고치거나 jar를 따로 만들면 번거롭고 실수하기 쉽다. 실행 인자로 설정을 넘기면 jar 하나를 그대로 두고 켤 때마다 다른 값을 줄 수 있다.
지금 어디에 쓰나 — 한 컴퓨터에서 같은 서버를 포트만 바꿔 여러 대 켤 때(java -jar app.jar --server.port=8081, --server.port=8082), 배포할 때 환경마다 다른 값을 넘길 때 쓴다. 컨테이너에서는 같은 일을 환경 변수(SERVER_PORT=8081)로 하기도 한다.
java -jar app.jar --server.port=8081처럼 프로그램을 켤 때 --이름=값 꼴로 붙인 인자는 스프링 부트가 설정 값으로 바꿔 읽는다. 스프링 부트 문서는 SpringApplication이 --로 시작하는 인자를 설정으로 바꿔 Environment에 더하고, 이 값이 application.properties 같은 설정 파일의 값보다 앞선다고 적는다. server.port는 스프링 부트가 정해 둔 설정 이름으로 내장 웹 서버가 열 포트이고, app.name처럼 직접 지은 이름도 같은 방법으로 넘겨 @Value("${app.name}")로 읽을 수 있다.
연결 거부 오류
연결 거부 오류는 TCP로 연결을 요청했는데 그 포트를 열고 기다리는 프로그램이 없을 때 보내는 쪽이 받는 오류이다. 자바에서는 new Socket 줄에서 java.net.ConnectException이 나고, Windows 11에서 실행한 검증에서는 메시지가 "Connection refused: connect"였다. ConnectException의 API 문서는 이 예외가 연결하다가 난 오류이며 보통 상대 주소와 포트에서 기다리는 프로세스가 없어 거절된 경우라고 적는다. 거절은 그 컴퓨터의 운영체제가 하고, 같은 컴퓨터 안에서는 기다림 없이 곧바로 온다. 연결이 맺어지지 않았으므로 글은 하나도 보내지지 않는다. TCP 표준은 연결이 없는 상태로 온 요청에 거부 신호(RST)를 보내도록 정한다(RFC 9293 3.5.2절).

이렇게 바꿔 보세요

  • 처음 설정으로 — upstream에 서버 두 대를 적고 proxy_pass로 넘깁니다. 요청이 A와 B에 번갈아 갑니다.
  • 서버 A를 끄면 — nginx가 연결이 거부된 서버 A를 건너뛰어, 클라이언트는 실패 없이 답을 받습니다.
  • 로드 밸런서 없이 서버 한 대만 두면 — 서버가 한 대뿐이라 모든 요청을 그 서버가 받습니다.
  • 서버 한 대뿐인데 그 서버를 끄면 — 받아 줄 서버가 없어 그 뒤의 요청이 모두 실패합니다.

처음 설정으로 실행하면

  1. 서버가 뜹니다. 같은 app.jar를 java -jar로 두 번 켜서, 같은 스프링 부트 프로그램이 서버 A(8081 포트, --app.name=A)와 서버 B(8082 포트, --app.name=B)로 따로 뜹니다. 두 서버의 HelloController는 각자 받은 요청 수를 자기 count 필드에 셉니다. 그 앞에 nginx가 listen 8080 줄대로 8080 포트에서 요청을 기다립니다. 클라이언트는 서버가 몇 대인지 모르고 localhost:8080 주소 하나만 압니다. 이 주소에서 요청을 받는 것은 nginx입니다.
  2. 클라이언트가 GET / 요청을 보냅니다(1번째). 8080 포트에서 이 요청을 받는 것은 스프링 부트 서버가 아니라 nginx입니다. location / 의 proxy_pass http://app; 줄에 따라 nginx는 upstream app에 적힌 서버 가운데 하나에 요청을 넘깁니다. 나누는 방식을 따로 적지 않았으므로 기본 방식인 라운드 로빈(차례대로 돌아가며 한 대씩)을 쓰고, 첫 요청은 목록의 첫 서버인 서버 A(8081 포트)로 갑니다.
  3. 서버 A의 hello() 메서드가 count를 1 올리고 "나는 A, 받은 요청 1번째"를 돌려줍니다. nginx가 이 답을 그대로 클라이언트에 돌려줍니다. 클라이언트가 받은 글에는 어느 서버가 답했는지가 적혀 있습니다.
  4. 클라이언트가 GET / 요청을 보냅니다(2번째). nginx는 차례대로 돌아가며 넘기므로 이번에는 서버 B 차례입니다. 서버 B가 count를 1 올리고 "나는 B, 받은 요청 1번째"를 돌려주고, nginx가 이 답을 돌려줍니다. 서버 A가 이미 1번 답했지만 서버 B의 수는 "1번째"부터 시작합니다. count는 서버마다 자기 메모리에 따로 있기 때문입니다.
  5. 클라이언트가 GET / 요청을 보냅니다(3번째). nginx는 차례대로 돌아가며 넘기므로 이번에는 서버 A 차례입니다. 서버 A가 count를 1 올리고 "나는 A, 받은 요청 2번째"를 돌려주고, nginx가 이 답을 돌려줍니다.
  6. 클라이언트가 GET / 요청을 보냅니다(4번째). nginx는 차례대로 돌아가며 넘기므로 이번에는 서버 B 차례입니다. 서버 B가 count를 1 올리고 "나는 B, 받은 요청 2번째"를 돌려주고, nginx가 이 답을 돌려줍니다.
  7. 클라이언트가 GET / 요청을 보냅니다(5번째). nginx는 차례대로 돌아가며 넘기므로 이번에는 서버 A 차례입니다. 서버 A가 count를 1 올리고 "나는 A, 받은 요청 3번째"를 돌려주고, nginx가 이 답을 돌려줍니다.
  8. 클라이언트가 GET / 요청을 보냅니다(6번째). nginx는 차례대로 돌아가며 넘기므로 이번에는 서버 B 차례입니다. 서버 B가 count를 1 올리고 "나는 B, 받은 요청 3번째"를 돌려주고, nginx가 이 답을 돌려줍니다.
  9. 요청 6번이 끝났습니다. 서버 A가 3번, 서버 B가 3번 답했고, 실패한 요청은 0번입니다. 서버 A의 count는 3, 서버 B의 count는 3입니다.

실행 결과

  • nginx 설정의 upstream app에 서버 두 대를 적고 proxy_pass http://app;으로 넘기면, nginx가 클라이언트가 접속하는 주소 하나(8080 포트)에서 요청을 받아 서버 A와 서버 B에 번갈아 보냅니다(기본 방식인 라운드 로빈). 요청 6번 가운데 서버 A가 3번, 서버 B가 3번 답했습니다.
  • 받은 요청 수는 서버마다 자기 메모리의 count에 따로 셉니다. 서버 B가 처음 받은 요청은 서버 A가 이미 답한 뒤였는데도 "1번째"였고, 두 서버의 count는 각각 3입니다. 서버 메모리에 적어 둔 값은 다른 서버가 모릅니다.

코드

# nginx 설정 (nginx.conf의 http { } 블록에 둔다. 8080 포트로 받아 서버 A, 서버 B에 나눠 보낸다)
upstream app {
    server 127.0.0.1:8081;    # 서버 A
    server 127.0.0.1:8082;    # 서버 B
}

server {
    listen 8080;

    location / {
        proxy_pass http://app;    # upstream app의 서버들에 나눠 넘긴다
    }
}

# 서버 A, 서버 B 켜기: 같은 app.jar를 포트와 이름만 바꿔 두 번 켠다
# --server.port는 스프링 부트가 정해 둔 설정(서버가 열 포트), --app.name은 예시로 정한 설정(서버 이름)
java -jar app.jar --server.port=8081 --app.name=A
java -jar app.jar --server.port=8082 --app.name=B

# 클라이언트: curl http://localhost:8080/ 요청을 6번 보낸다

// HelloController.java  (HelloController는 예시로 만든 컨트롤러다. @RestController·@GetMapping·@Value는 스프링이,
// AtomicInteger는 자바가 준다. @SpringBootApplication을 붙인 시작 클래스는 생략)
import java.util.concurrent.atomic.AtomicInteger;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {
    @Value("${app.name}")
    private String name;                                       // 켤 때 준 --app.name 값 (A 또는 B)

    private final AtomicInteger count = new AtomicInteger();  // 이 서버가 받은 요청 수 (이 서버의 메모리에만 있다)

    @GetMapping("/")
    public String hello() {
        return "나는 " + name + ", 받은 요청 " + count.incrementAndGet() + "번째";
    }
}

이 모형의 전제

서버 A와 서버 B는 실제 스프링 부트 4.1.1(스프링 7.0.9, 내장 톰캣 11.0.24, JDK 21)입니다. 화면의 HelloController를 그대로 컴파일하고, 화면의 java -jar 줄에 적힌 --server.port와 --app.name 인자를 그대로 주어 켰습니다. 다만 jar로 묶는 대신 컴파일한 클래스로 켰고, 화면에서 생략한 시작 클래스는 시험용으로 따로 두었습니다. nginx는 이 컴퓨터에 없어서 실행하지 않았습니다. 대신 nginx 역할을 하는 실행용 모형(Node.js 24.18.0으로 짠 작은 프로그램)이 화면의 nginx 설정에서 upstream의 server 줄, listen, proxy_pass를 읽고, nginx 문서에 적힌 동작대로 요청을 넘겼습니다. 같은 가중치의 라운드 로빈으로 서버를 고르고, 연결 오류나 타임아웃이 나면 같은 요청을 다음 서버에 넘기고(proxy_next_upstream 기본값 error timeout), max_fails(기본 1)번 실패한 서버는 fail_timeout(기본 10초) 동안 고르지 않습니다. 첫 요청이 목록의 첫 서버(서버 A)로 간다는 것은 문서에 적혀 있지 않아서, nginx 소스(ngx_http_upstream_round_robin.c)가 서버를 고르는 방식(가중치가 같으면 목록 앞의 서버)을 옮겨 정했습니다. 클라이언트는 GET / 요청을 요청마다 새 연결로 6번 차례로 보냈습니다. 서버 A를 끄는 것은 Ctrl+C 대신 서버 A 프로세스를 끝내는 것으로 했고, 끈 뒤에 연결하면 ECONNREFUSED(연결 거부 오류)가 났습니다. 화면의 8080, 8081, 8082 포트는 실행에서 다른 빈 포트(18270~18272)로 바꿨습니다. 네 가지 조합을 모두 실행해 서버 A와 서버 B가 답한 수, 실패한 요청 수, 요청 6번 각각을 어느 서버가 몇 번째로 답했는지와 클라이언트가 받은 글, 서버의 count, 연결을 거부당한 요청을 모형과 대조했습니다. 그러니 스프링 부트 서버의 답은 실제 실행 결과이고, 요청을 나누고 꺼진 서버를 건너뛰는 부분은 문서대로 짠 모형의 결과이며 진짜 nginx로 확인한 것은 아닙니다. nginx 설정은 nginx.org 문서와 대조했습니다. ngx_http_upstream_module: upstream은 http 블록에 두고, 기본 분배는 가중치를 둔 라운드 로빈이며, max_fails 기본값은 1, fail_timeout 기본값은 10초입니다. ngx_http_proxy_module: proxy_pass에 서버 묶음(upstream) 이름을 쓸 수 있고, proxy_next_upstream 기본값은 error timeout이며, error는 서버와 연결을 맺거나 요청을 넘기거나 응답의 머리를 읽는 중에 난 오류입니다. 라운드 로빈 차례는 nginx 작업 프로세스마다 따로 셉니다(worker_processes 기본값은 1이고, upstream에 zone을 두면 작업 프로세스들이 함께 셉니다). 작업 프로세스가 여럿이면 A, B, A, B 순서가 이 실습과 다를 수 있습니다. 다루지 않은 것: nginx 자신이 꺼지는 경우, 꺼진 서버가 다시 켜져 10초 뒤 돌아오는 경우, 서버 상태를 주기적으로 확인하는 헬스 체크, weight로 서버마다 몫을 다르게 주는 것, least_conn이나 ip_hash 같은 다른 나누는 방식, 답을 보내는 도중에 서버가 꺼지는 경우, 요청이 아주 많을 때 서버가 버티는 한계입니다. 로드 밸런서를 직접 프로그램으로 짤 수도 있습니다. 이 실습의 실행용 모형이 그런 예로, 수십 줄로 라운드 로빈과 실패한 서버 건너뛰기를 해 볼 수 있습니다. 하지만 실제 서비스에서는 nginx나 클라우드 로드 밸런서를 씁니다. 서버를 늘려 처리량이 어디까지 느는지는 "세부 동작 실습: 로드밸런서와 스케일 아웃"에서, 서버를 하나씩 바꿔 배포하는 방법은 "배포 전략"에서, 죽은 서버를 자동으로 다시 띄우는 일은 "쿠버네티스 자가 치유"에서 다룹니다.
