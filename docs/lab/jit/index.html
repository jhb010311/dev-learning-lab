JIT 워밍업

배포 직후의 첫 요청들은 왜 느린가

왜 생겼나 — 바이트코드를 한 명령씩 해석만 하면 어느 운영체제에서나 같은 파일이 돌지만 느리고, 처음부터 기계어로 컴파일해 두면 빠른 대신 운영체제와 CPU마다 따로 만들어야 한다. JIT 컴파일러는 실행 중에 많이 쓰이는 코드만 골라 그 기계에 맞는 기계어로 바꿔서, 같은 바이트코드를 쓰면서도 해석만 할 때보다 훨씬 빠르게 돌게 한다.

지금 어디에 쓰나 — HotSpot 같은 일반적인 JVM에서는 따로 켜지 않아도 늘 동작하므로, 개발자가 신경 쓰는 때는 주로 배포 직후와 성능 측정이다. 새 서버에 요청을 넘기기 전에 주요 API를 미리 호출해 두거나, 성능을 잴 때 처음 구간을 버리는 것이 그 예다. 기동 속도가 중요한, 잠깐 돌고 끝나는 프로그램에서는 GraalVM 네이티브 이미지처럼 미리 기계어로 컴파일하는 방식을 쓰기도 한다.

자바 코드는 바이트코드로 컴파일되어 JVM이 한 명령씩 해석하며 실행합니다. JVM은 자주 실행되는 메서드를 찾아내 기계어로 다시 컴파일하고(JIT), 그 뒤로는 훨씬 빨라집니다.

실행으로 대조 · JDK 21에서 실제로 잰 값

이 실습에 나오는 개념

JIT 컴파일러
프로그램 실행 중에 자주 실행되는 바이트코드를 기계어로 컴파일해 두고 이후에는 그 기계어를 직접 실행하는 JVM의 구성 요소다. 처음에는 인터프리터로 바이트코드 명령을 하나씩 해석해 실행하다가, 반복 실행되는 부분을 찾아 최적화한다. 그래서 자바 애플리케이션은 기동 직후보다 어느 정도 실행된 뒤에 더 빨라진다(워밍업).
바이트코드
지금 어디에 쓰나 — javap -c로 .class 파일의 바이트코드를 보면 컴파일러가 코드를 어떻게 바꿨는지 확인할 수 있다. 스프링과 Hibernate는 실행 중에 바이트코드를 직접 만들어 프록시 클래스를 생성한다.
자바 컴파일러(javac)가 소스 코드를 변환해 만든 중간 형태의 코드로 .class 파일에 담긴다. 특정 CPU나 운영체제의 기계어가 아니라 JVM이 이해하는 명령어라서 어느 플랫폼의 JVM에서든 실행된다.
JVM(자바 가상 머신)
지금 어디에 쓰나 — 자바뿐 아니라 Kotlin, Scala로 쓴 프로그램도 바이트코드로 컴파일되어 JVM에서 실행된다. 서버에서는 힙 크기(-Xmx)나 GC 종류 같은 실행 방식을 JVM 옵션으로 정해 프로그램을 띄운다.
자바 바이트코드를 읽어 실행하는 프로그램이다. 운영체제마다 그에 맞는 JVM이 있어서, 한 번 컴파일한 자바 프로그램을 수정 없이 여러 운영체제에서 실행할 수 있다. 클래스를 읽어 들이고, 메모리를 관리하고(가비지 컬렉션), 바이트코드를 기계어로 바꿔 실행하는 일을 맡는다.
클래스 로더
왜 생겼나 — 클래스를 어디서 어떻게 읽을지가 JVM에 고정되어 있으면, jar 파일에 묶인 jar나 웹 애플리케이션별 라이브러리 폴더처럼 다양한 위치를 다룰 수 없다. 클래스 로더는 읽는 방법을 따로 떼어 내, 필요하면 새 로더를 만들어 쓸 수 있게 했다.
지금 어디에 쓰나 — 톰캣은 웹 애플리케이션마다 클래스 로더를 따로 두어 같은 라이브러리의 서로 다른 버전을 함께 돌리고, 스프링 부트는 실행 jar에 묶인 라이브러리 jar를 읽는 전용 클래스 로더를 쓴다.
클래스 파일을 찾아 메모리로 읽어 들이는 JVM의 구성 요소다. 클래스는 프로그램 시작 때 전부 읽는 것이 아니라 처음 필요해지는 시점에 로딩된다. 읽어 들인 클래스는 JVM이 링킹(검증, 준비, 그리고 심볼릭 참조의 해석)과 초기화(static 초기화 실행)를 거쳐 사용할 수 있게 만든다.

  1. 자바 컴파일러(javac)는 소스를 기계어가 아니라 바이트코드로 바꿉니다. 프로그램이 시작되면 JVM의 인터프리터가 이 바이트코드를 한 명령씩 해석해 실행합니다. 어떤 CPU에서든 돌아가지만, 기계어를 직접 실행하는 것보다 훨씬 느립니다.
  2. 1번째 묶음: 5.3ms. 처음에는 인터프리터로 실행됩니다. JVM은 메서드가 몇 번 불렸는지, 반복문이 몇 번 돌았는지를 세고 있다가, 기준을 넘자 이 메서드를 기계어로 컴파일합니다. 이 묶음은 컴파일된 코드가 준비되기 전까지 해석 실행으로 돌았습니다(컴파일은 다른 스레드에서 진행).

실행 결과

  • 같은 코드인데 처음과 나중의 속도가 다릅니다. JVM은 모든 코드를 미리 컴파일하지 않고, 실제로 자주 실행되는 부분만 골라 실행 중에 컴파일합니다(Just-In-Time). 실행 정보를 보고 최적화하므로 충분히 달궈진 뒤에는 미리 컴파일한 언어에 가까운 속도가 납니다.
  • 배포 직후에는 JIT 컴파일 전인 데다 클래스 로딩, 커넥션 풀 채우기, 캐시가 비어 있는 것까지 겹쳐 첫 요청들이 유독 느립니다. 새 서버에 트래픽을 한꺼번에 넘기지 않고 조금씩 늘리는 이유이기도 합니다. 성능을 잴 때도 처음 구간은 버리고 충분히 달궈진 뒤의 값을 봅니다.

코드

public class JitWarmup {                       // 예시로 만든 클래스
    static long work(int n) {                  // 측정한 메서드(예시로 만든 이름)
        long s = 0;
        for (int i = 0; i < n; i++) s += (i * 31L) ^ (s >>> 3);
        return s;
    }

    public static void main(String[] args) {
        long sink = 0;                         // 결과를 써서 계산이 지워지지 않게 한다
        for (int batch = 1; batch <= 12; batch++) {
            long t = System.nanoTime();
            for (int k = 0; k < 2000; k++) sink += work(1000);   // 묶음 하나 = 2,000번 호출
            System.out.println(batch + "번째 묶음: " + (System.nanoTime() - t) / 1000 + "마이크로초");
        }
        System.out.println(sink);
    }
}

// 실행: java JitWarmup.java

이 모형의 전제

숫자는 검증 환경의 JDK 21에서 위 코드를 세 가지 방식으로 각각 다섯 번 실행해 잰 값 가운데 첫 번째 실행의 값입니다. 다섯 번 모두에서 기본 설정의 첫 묶음은 5.1~5.4ms, 그 뒤 묶음은 1.4~1.7ms였고, 미리 워밍업한 경우의 첫 묶음은 1.4~1.9ms, -Xint는 묶음마다 23~36ms였습니다. 수치는 CPU와 실행 시점에 따라 달라지지만, 첫 구간이 느리고 그 뒤로 빨라지는 모양은 같습니다. 기본 설정의 JVM은 가벼운 컴파일(C1)과 강한 최적화 컴파일(C2)을 단계적으로 적용합니다.
