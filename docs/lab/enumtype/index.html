열거형(enum)

@Enumerated(EnumType.ORDINAL)로 저장한 enum은 왜 다른 상수가 되어 돌아오나

왜 생겼나 — enum이 없을 때는 주문 상태 같은 값을 int 상수나 문자열로 나타냈다. 그러면 정해 두지 않은 숫자나 오타 난 문자열을 넘겨도 컴파일러가 막지 못했고, 같은 숫자를 쓰는 다른 종류의 상수와 섞여도 알아채기 어려웠다. enum은 가능한 값을 하나의 타입으로 묶어서, 그 밖의 값이나 다른 종류의 상수를 넘기는 코드를 컴파일 단계에서 막는다. 다만 DB의 컬럼에는 enum 객체를 그대로 넣을 수 없어서, JPA는 저장할 때 숫자나 글자로 바꾸고 읽을 때 되돌리는 방법을 @Enumerated와 AttributeConverter로 정하게 한다.

지금 어디에 쓰나 — 주문 상태, 결제 수단, 회원 등급처럼 종류가 미리 정해진 값을 나타낼 때 쓴다. JPA 엔티티의 enum 필드에는 @Enumerated(EnumType.STRING)을 붙여 상수의 이름을 저장하는 것이 보통이다. @Enumerated를 붙이지 않으면 기본값인 ORDINAL(선언 순서 번호)로 저장된다. DB에 P, S 같은 짧은 코드로 저장해야 하면 AttributeConverter를 만들어 @Convert로 지정한다.

enum은 주문 상태처럼 정해진 몇 가지 값만 가질 수 있는 타입입니다. JPA 엔티티의 enum 필드를 DB에 저장할 때는 @Enumerated로 저장 방식을 고릅니다. EnumType.ORDINAL은 상수의 선언 순서 번호를, EnumType.STRING은 상수의 이름을 저장합니다. 번호로 저장한 뒤 enum 선언의 순서를 고치면, DB의 숫자는 그대로인데 그 숫자가 가리키는 상수가 달라집니다. 이 실습은 Hibernate가 실제로 저장하고 다시 읽은 결과를 따라갑니다.

실행으로 대조 · Hibernate 7.4.5와 H2에서 마흔다섯 가지 조합을 화면의 코드로 컴파일·실행해 컬럼 정의, 저장된 값, 다시 배포한 뒤 읽은 상수와 예외를 대조

이 실습에 나오는 개념

열거형(enum)
정해진 몇 개의 값만 가질 수 있는 타입을 만드는 문법이다. enum Status { ORDERED, PAID }처럼 선언하면 ORDERED와 PAID가 각각 Status 타입의 객체가 되고, 이 객체들은 한 번만 만들어지며 new로 더 만들 수 없다. 상수마다 객체가 하나뿐이라 ==로 비교할 수 있고 switch에도 쓸 수 있다. enum도 클래스이므로 필드, 생성자, 메서드를 가질 수 있어서 상수마다 표시 이름이나 코드 값을 붙여 둘 수 있다. 문자열이나 숫자로 상태를 나타낼 때와 달리, 정해지지 않은 값을 쓰면 컴파일 오류가 나므로 상태나 종류를 나타내는 데 쓴다.
@Enumerated
왜 생겼나 — 자바의 enum 값은 JDBC로 바로 넘길 수 없어서, 저장할 때 숫자나 글자로 바꾸고 읽을 때 되돌리는 코드를 직접 써야 했다. JPA는 이 변환을 맡고, @Enumerated는 그 변환을 순서 번호로 할지 이름으로 할지 고르게 한다.
지금 어디에 쓰나 — 주문 상태, 회원 등급처럼 정해진 몇 가지 값 가운데 하나인 필드에 붙인다. DB에 이름 대신 P, D 같은 짧은 코드로 저장해야 하면 @Enumerated 대신 AttributeConverter를 만들어 쓴다.
enum 타입의 필드를 DB에 어떤 값으로 저장할지 정하는 애너테이션이다. EnumType.ORDINAL은 enum에 적힌 순서 번호(0부터)를 숫자로 저장하고, EnumType.STRING은 상수의 이름을 글자로 저장한다. 붙이지 않았을 때의 기본값은 ORDINAL이다. ORDINAL로 저장한 뒤 enum의 중간이나 앞에 상수를 추가하면 번호가 밀려서, 이미 저장된 값이 다른 상수로 읽힌다. 예외가 나지 않아 알아차리기 어려우므로 STRING으로 쓰는 것이 안전하다.
AttributeConverter
왜 생겼나 — @Enumerated는 enum을 순서 번호나 이름으로만 저장할 수 있어서, 예전부터 상태를 P, S 같은 코드로 적어 온 DB에 맞추거나 상수 이름을 자유롭게 바꾸기 어려웠다. JPA 2.1에서 AttributeConverter가 들어와, 필드 하나를 어떻게 바꿔 저장할지 클래스 하나로 정하게 되었다.
지금 어디에 쓰나 — enum을 짧은 코드 값으로 저장할 때, 불리언을 Y/N 글자로 저장할 때, 금액이나 전화번호 같은 값 객체를 컬럼 하나에 글자로 저장할 때 쓴다.
엔티티 필드의 값과 DB 컬럼의 값을 서로 바꾸는 방법을 정하는 JPA 인터페이스다. AttributeConverter<X, Y>를 구현하는 클래스를 만들어 두 메서드를 채운다. convertToDatabaseColumn은 저장할 때 필드 값(X)을 컬럼 값(Y)으로, convertToEntityAttribute는 읽을 때 컬럼 값을 필드 값으로 바꾼다. 클래스에 @Converter를 붙이고 필드에 @Convert(converter = 변환기 클래스)를 붙이면 그 필드에 쓰이고, @Converter(autoApply = true)로 두면 같은 타입의 필드 모두에 쓰인다. enum을 순서 번호나 이름이 아니라 P, S 같은 정해 둔 코드로 저장하면, 상수의 순서나 이름을 바꿔도 저장된 값이 흔들리지 않는다.
ordinal()과 name()
왜 생겼나 — enum 상수를 파일이나 DB에 남기려면 글자나 숫자로 바꿔야 하는데, 상수마다 바꾸는 코드를 짜면 상수를 늘릴 때마다 고쳐야 한다. name()과 ordinal()은 모든 enum이 java.lang.Enum에서 물려받는 메서드라서, 따로 짜지 않아도 이름과 순번을 얻게 한다.
지금 어디에 쓰나 — name()은 다른 시스템에 상수를 글자로 넘길 때처럼 정확한 이름이 필요할 때 쓰고, 로그에 보일 글은 toString()에 맡긴다. ordinal()은 API 문서가 EnumSet, EnumMap 같은 자료구조용이라고 밝혀 두어, 보통 코드에서 직접 쓸 일은 드물다.
모든 enum 상수가 가지고 있는 두 메서드다. ordinal()은 그 상수가 선언에서 몇 번째인지를 0부터 센 번호를 돌려주고, name()은 선언에 적은 상수의 이름을 문자열로 돌려준다. ordinal()은 선언 순서로 정해지므로 상수를 중간에 끼워 넣거나 순서를 바꾸면 값이 달라진다. 그래서 ordinal() 값을 DB나 파일에 저장해 두면 나중에 같은 숫자가 다른 상수로 읽힐 수 있다. JPA의 @Enumerated(EnumType.ORDINAL)이 DB에 적는 값이 ordinal()이고, EnumType.STRING이 적는 값이 name()이다. 그래서 저장할 때는 STRING이나, enum에 따로 만들어 둔 코드 값을 쓴다.
enum의 valueOf
왜 생겼나 — 글자로 들어온 값을 enum으로 바꾸려면 상수마다 if로 비교하는 코드를 짜야 하고, 상수를 늘릴 때마다 그 코드도 고쳐야 한다. valueOf는 컴파일러가 모든 enum에 만들어 주어, 이름만으로 상수를 바로 찾게 한다.
지금 어디에 쓰나 — 요청 파라미터나 설정 파일에서 읽은 글자, DB에 이름으로 저장해 둔 값을 enum 상수로 되돌릴 때 쓴다.
이름 문자열을 받아 그 이름을 가진 enum 상수를 돌려주는 static 메서드로, 모든 enum에 자동으로 만들어진다. Status.valueOf("PAID")는 Status.PAID를 돌려준다. 이름은 대소문자까지 정확히 같아야 하고, 그런 상수가 없으면 null을 돌려주는 것이 아니라 IllegalArgumentException을 던진다. 그래서 사용자가 입력한 문자열처럼 믿을 수 없는 값을 넘길 때는 예외에 대비해야 한다. 모든 상수를 선언 순서대로 늘어놓은 배열을 돌려주는 values()도 함께 만들어진다.

이렇게 바꿔 보세요

  • 처음 설정으로 — DB에는 숫자 1이 남아 있고, 지금 선언에서 1번은 CANCELED입니다. 결제 완료 주문이 취소 주문으로 읽힙니다.
  • 순서만 바꿔도 — 상수를 추가하지 않고 순서만 바꿔도 번호가 가리키는 상수가 달라집니다.
  • 맨 끝에 추가하면 — 기존 상수의 번호가 그대로라서 같은 상수가 읽힙니다.
  • 운 좋게 무사한 상수 — 같은 변경인데 맨 앞의 상수는 번호가 바뀌지 않습니다.
  • STRING으로 저장 — DB에 이름이 저장되므로 순서가 달라져도 같은 상수가 읽힙니다.
  • STRING인데 이름을 바꾸면 — DB의 "PAID"에 맞는 상수가 없어 em.find가 예외를 던집니다.
  • AttributeConverter로 코드 저장 — 저장된 것이 이름도 번호도 아닌 코드라서, 이름을 바꿔도 같은 상수가 읽힙니다.

처음 설정으로 실행하면

  1. 처음 배포: enum 선언은 ORDERED, PAID, SHIPPED 순서입니다. Hibernate가 Order 엔티티를 보고 orders 테이블을 만들었고, status 컬럼은 "status tinyint check ((status between 0 and 2))"입니다. EnumType.ORDINAL은 상수의 선언 순서 번호를 저장하는 방식이라 숫자 컬럼이 됩니다. 0부터 2까지만 받는 조건(check)은 Hibernate가 H2용으로 붙인 것입니다.
  2. em.persist(new Order(1L, OrderStatus.PAID))와 커밋: INSERT가 나가 status 컬럼에 1이 저장됩니다. Hibernate가 PAID.ordinal()의 값을 적은 것입니다. ordinal()은 모든 enum이 java.lang.Enum에서 물려받는 메서드로, 그 상수가 선언에서 몇 번째인지를 0부터 센 번호를 돌려줍니다.
  3. 그 뒤 enum 선언을 고쳐 다시 배포했습니다: 새 상수 CANCELED를 ORDERED와 PAID 사이에 끼워 넣었습니다. 지금의 순서 번호는 ORDERED(0), CANCELED(1), PAID(2), SHIPPED(3)입니다. 테이블은 다시 만들지 않았으므로 status 컬럼의 1은 그대로 남아 있습니다.
  4. em.find(Order.class, 1L) 실행: SELECT로 행을 읽고 status 컬럼의 1을 상수로 바꿉니다. ORDINAL이므로 Hibernate는 지금 선언에서 1번째 상수를 고릅니다. OrderStatus.values()[1]와 같은 결과입니다(values()는 모든 enum에 자동으로 만들어지는 메서드로, 상수를 지금 선언의 순서대로 늘어놓은 배열을 돌려줍니다). 1번 자리에 있는 것은 CANCELED입니다. 저장한 것은 PAID인데 다른 상수가 나왔습니다. 예외도 경고도 없습니다.
  5. System.out.println(order.getStatus()) 실행: 출력은 "CANCELED"입니다. enum의 toString()은 따로 고치지 않으면 name()과 같은 이름을 돌려줍니다.
  6. order.getStatus() == OrderStatus.PAID 실행: false입니다. enum 상수는 상수마다 객체가 하나뿐이어서, Hibernate가 읽어 온 것이든 코드에 적은 것이든 같은 상수면 같은 객체입니다. 그래서 equals 없이 ==로 비교해도 됩니다. false가 나온 것은 비교 방법 때문이 아니라, 읽어 온 상수가 정말로 다른 상수(CANCELED)이기 때문입니다.

실행 결과

  • EnumType.ORDINAL은 선언 순서 번호를 저장할 뿐이어서, 상수를 중간에 끼워 넣거나 순서를 바꾸면 이미 저장된 숫자가 다른 상수를 가리키게 됩니다. 예외가 나지 않으므로 "결제 완료" 주문이 "주문 취소" 주문으로 보이는 잘못된 데이터가 조용히 쓰입니다. @Enumerated를 붙이지 않았을 때의 기본값도 ORDINAL이므로, enum 필드에는 @Enumerated(EnumType.STRING)을 적어 둡니다.
  • enum 상수의 비교에는 ==를 씁니다. 상수마다 객체가 하나뿐이라 결과가 equals와 같고, 한쪽이 null이어도 예외가 나지 않습니다.

코드

// 파일: OrderStatus.java
// 주문 상태를 나타내려고 예시로 만든 enum. 저장할 때의 선언은 ORDERED, PAID, SHIPPED 순서였고, 저장한 뒤에 CANCELED를 ORDERED와 PAID 사이에 끼워 넣었다
public enum OrderStatus { ORDERED, CANCELED, PAID, SHIPPED }

// 파일: Order.java
// 예시로 만든 엔티티. @Entity, @Table, @Id, @Enumerated, EnumType은 JPA가 주는 것
import jakarta.persistence.*;

@Entity
@Table(name = "orders")
public class Order {
    @Id
    private Long id;

    @Enumerated(EnumType.ORDINAL)
    private OrderStatus status;

    protected Order() {
    }

    public Order(Long id, OrderStatus status) {
        this.id = id;
        this.status = status;
    }

    public OrderStatus getStatus() {
        return status;
    }
}

// 파일: OrderReader.java
// 다시 배포한 뒤 주문을 읽는 예시 클래스. EntityManager는 JPA가 주는 것
import jakarta.persistence.EntityManager;

public class OrderReader {
    // 예전 선언일 때 em.persist(new Order(1L, OrderStatus.PAID))로 저장해 둔 주문을 읽는다
    static void print(EntityManager em) {
        Order order = em.find(Order.class, 1L);
        System.out.println(order.getStatus());
        System.out.println(order.getStatus() == OrderStatus.PAID);
    }
}

이 모형의 전제

마흔다섯 가지 조합 모두를 실제 Hibernate 7.4.5와 H2 데이터베이스(2.4.240)에서 실행해 대조했습니다. 조합마다 화면의 코드를 그대로 컴파일해서, 예전 선언(ORDERED, PAID, SHIPPED)의 Order로 테이블을 만들고 주문 한 건을 persist한 뒤, 테이블은 그대로 두고 지금 선언의 클래스로 화면의 OrderReader.print를 실행했습니다. 대조한 것은 Hibernate가 만든 status 컬럼 정의, DB에 저장된 값(JDBC로 직접 읽음), 콘솔 출력 두 줄, 예외의 종류와 메시지입니다. 예외 메시지에 붙는 패키지 이름은 화면의 코드에 없으므로 빼고 적었습니다. Hibernate가 읽은 상수가 values()[번호], valueOf(이름)를 직접 부른 결과와 같다는 것도 조합마다 확인했습니다. 다음 사실도 같은 방법으로 실행해 확인했습니다: @Enumerated를 붙이지 않은 enum 필드는 ORDINAL과 똑같은 컬럼이 되고 숫자가 저장된다는 것, ORDINAL로 저장한 뒤 그 상수를 지워 번호가 범위를 벗어나면 em.find가 ArrayIndexOutOfBoundsException을 던진다는 것, 변환기가 모르는 코드를 받으면 PersistenceException(원인은 fromCode가 던진 IllegalArgumentException)이 난다는 것, 같은 상수는 어떻게 얻어도 같은 객체라는 것. 컬럼 정의는 DB 종류(방언)와 Hibernate 버전에 따라 다르며, 여기 적힌 tinyint와 check 조건, enum 타입 컬럼은 Hibernate 7.4.5가 H2용으로 만든 것입니다. 이 조건 때문에 Hibernate가 만든 테이블을 그대로 쓰면, CANCELED를 끼워 넣은 뒤 ORDINAL로 SHIPPED(이제 번호 3)를 저장하거나 STRING으로 CANCELED를 저장하는 일도 실패합니다(이것도 실행해 확인). 이 실습은 이미 저장된 행을 읽는 일만 다룹니다. 실제 서비스에서는 테이블을 Flyway 같은 도구로 따로 만드는 경우가 많아 이런 조건이 없을 수 있지만, 다시 배포할 때 저장된 값이 그대로라는 점은 같습니다. 스프링 부트 없이 Hibernate만으로 실행했으며, 스프링 데이터 JPA를 써도 저장과 읽기는 같은 Hibernate가 합니다.
