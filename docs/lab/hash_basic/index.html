해시

해시는 무엇이고, 비밀번호를 왜 해시로 저장하는가

왜 생겼나 — 비밀번호를 그대로 저장하면, DB가 새어 나가거나 관리자가 들여다보는 순간 모든 회원의 비밀번호가 드러나고, 같은 비밀번호를 쓰는 다른 사이트까지 위험해진다. 비밀번호를 해시로 저장하면 서버는 원래 비밀번호를 저장해 두지 않고도 "입력한 것이 맞는가"만 확인할 수 있고, 저장된 값을 훔쳐도 그 값으로 바로 로그인하지 못한다.

지금 어디에 쓰나 — 회원 가입과 로그인이 있는 서비스는 비밀번호를 해시해서 저장하는 것이 기본이다. 스프링으로 만든 서비스는 스프링 시큐리티가 주는 PasswordEncoder(흔히 BCryptPasswordEncoder)의 encode로 저장할 값을 만들고, 로그인할 때 matches로 확인한다. SHA-256처럼 빨리 계산되는 해시는 자바가 주는 MessageDigest로 계산하며, 내려받은 파일이 중간에 바뀌지 않았는지 확인할 때 쓴다.

해시 함수는 어떤 글자를 넣든 정해진 길이의 뒤섞인 값을 내놓는 계산입니다. 같은 글자를 넣으면 같은 값이 나오고, 한 글자만 달라도 전혀 다른 값이 나오고, 나온 값에서 원래 글자를 거꾸로 계산해 낼 수 없습니다. 그래서 서버는 가입할 때 비밀번호 자체가 아니라 해시한 값을 저장하고, 로그인할 때는 입력한 글자가 그 값과 맞는지만 확인합니다. 스프링으로 만든 서비스에서는 이 일을 스프링 시큐리티가 주는 PasswordEncoder가 합니다. 코드의 encoder.encode("pass1234")가 저장할 값을 만들고, encoder.matches(input, saved)가 입력이 맞는지 확인합니다. PasswordEncoder는 인터페이스이고, 여기서는 BCrypt라는 비밀번호 전용 해시로 구현한 BCryptPasswordEncoder를 씁니다. encode는 할 때마다 무작위 값(솔트)을 새로 만들어 비밀번호와 함께 계산하므로, 같은 pass1234도 encode할 때마다 다른 값이 나옵니다. 비교용으로 자바가 주는 MessageDigest로 SHA-256을 직접 계산해 저장하는 코드와, 비밀번호를 그대로 저장하는 코드도 둡니다. 세 가지 저장 방법에 맞는 비밀번호, 한 글자 다른 비밀번호, 저장된 값 자체를 입력해 보며 로그인이 어떻게 되는지를 봅니다. (saved, input, ok는 이 실습에서 지은 변수 이름입니다.)

실행으로 대조 · JDK 21과 스프링 시큐리티 7.1.1(BCryptPasswordEncoder)에서 열 가지 조합을 javax.tools로 컴파일하고 실행해 대조. encode 값의 모양, matches 결과, 예시 BCrypt 값, SHA-256 값은 표준 예시, Node.js, openssl과도 견줌

이 실습에 나오는 개념

해시 함수
왜 생겼나 — 두 데이터가 같은지 보려면 원래는 전부를 나란히 놓고 견주어야 한다. 해시 함수는 짧은 값만 견주면 되게 해서, 원본을 다시 받지 않고도 내 것이 바뀌었는지 알 수 있게 한다.
지금 어디에 쓰나 — 내려받은 파일의 SHA-256 값을 사이트에 적힌 값과 견주어, 받는 동안 파일이 바뀌거나 깨지지 않았는지 확인한다. Git이 커밋마다 붙이는 40글자 이름도 해시 함수로 만든 값이다.
해시 함수는 어떤 길이의 글자(데이터)를 넣든 정해진 길이의 뒤섞인 값을 내놓는 계산이고, 그 값을 해시 값 또는 다이제스트라고 한다. SHA-256은 입력이 1글자든 100글자든 256비트, 곧 16진수 글자 64개의 값을 낸다. 같은 입력에는 언제나 같은 값이 나오고, 입력이 조금만 달라져도 매우 높은 확률로 전혀 다른 값이 나온다. 이 용어는 SHA-256 같은 암호용 해시 함수를 가리키며, 자료구조 HashMap에서 쓰는 해시 코드와는 쓰임이 다르다.
단방향
해시 함수가 단방향이라는 것은 입력에서 값은 쉽게 계산하지만, 나온 값에서 원래 입력을 거꾸로 찾아내는 것은 현실적으로 불가능하도록 만들어졌다는 뜻이다. NIST의 표준은 이 함수들을 안전하다고 부르는 이유를, 주어진 해시 값에 맞는 입력을 찾는 것과 같은 해시 값을 내는 서로 다른 두 입력을 찾는 것이 계산상 불가능하기 때문이라고 설명한다. 이것은 수학적으로 증명된 것이 아니라 알려진 방법이 없다는 뜻이다. 단방향은 암호화와 다르다. 암호화는 열쇠가 있으면 원래대로 풀 수 있지만 해시에는 푸는 열쇠가 없다. 또 짧고 흔한 입력은 후보를 하나씩 해시해서 견주는 방법으로 찾아질 수 있다.
PasswordEncoder
왜 생겼나 — 비밀번호를 저장하는 코드를 개발자마다 직접 짜면 빠른 해시를 쓰거나 솔트를 빠뜨리기 쉽다. 저장할 값을 만드는 일과 확인하는 일을 한 인터페이스로 묶어 두면, 검증된 방식을 그대로 쓰고 나중에 방식을 바꾸기도 쉽다.
지금 어디에 쓰나 — 회원 가입 서비스에서 encode한 값을 DB에 저장하고, 로그인할 때 스프링 시큐리티가 matches로 확인한다. 스프링 부트 애플리케이션에서는 PasswordEncoder를 빈으로 등록해 쓰고, PasswordEncoderFactories.createDelegatingPasswordEncoder()가 만드는 것은 값 앞에 {bcrypt}처럼 방식 이름을 붙인다.
PasswordEncoder는 스프링 시큐리티가 주는 인터페이스로, 비밀번호를 저장할 값으로 바꾸는 encode와, 입력한 비밀번호가 저장된 값과 맞는지 확인하는 matches를 정한다. 구현 클래스도 스프링 시큐리티가 주며, 흔히 쓰는 BCryptPasswordEncoder를 인자 없이 만들면, encode는 솔트를 새로 만들어 $2a$10$로 시작하는 60자 값을 낸다. 솔트 때문에 같은 비밀번호도 encode할 때마다 다른 값이 나오므로, 저장된 값과는 equals가 아니라 matches(입력, 저장된 값)로 견준다. matches는 저장된 값에서 솔트를 읽어 입력을 같은 방법으로 계산하고, 맞는지(true나 false)만 돌려준다.
bcrypt
지금 어디에 쓰나 — 회원 비밀번호를 저장할 때 쓴다. Spring Security의 PasswordEncoderFactories가 만드는 기본 인코더도 새 비밀번호를 bcrypt로 저장하며, 같은 목적의 다른 선택지로 Argon2, scrypt, PBKDF2가 있다.
비밀번호 저장용으로 설계된 해시 함수다. 솔트를 자동으로 생성해 결과에 포함하고, 연산 비용(cost)을 설정해 일부러 계산을 느리게 만든다. 계산이 느리면 공격자가 수많은 후보를 대입해 보는 데 드는 시간이 크게 늘어난다. Spring Security의 BCryptPasswordEncoder가 이를 사용한다.
솔트
왜 생겼나 — 솔트 없이 해시하면 같은 비밀번호는 언제나 같은 값이 되어, 흔한 비밀번호의 해시 값을 미리 계산해 둔 목록과 맞춰 보는 것만으로 많은 비밀번호가 한꺼번에 드러난다. 저장할 때마다 다른 값을 섞으면 그 목록을 쓸 수 없다.
지금 어디에 쓰나 — 스프링 시큐리티의 BCryptPasswordEncoder는 encode할 때마다 솔트를 새로 만들어 저장할 값의 앞부분에 적고, matches는 그 솔트를 읽어 다시 계산한다. 개발자가 솔트를 따로 만들거나 저장할 일은 없다.
솔트는 비밀번호를 해시할 때 함께 섞는 무작위 값이다. 비밀번호마다(같은 비밀번호라도 저장할 때마다) 새로 만들기 때문에, 같은 비밀번호를 쓰는 두 회원의 저장된 값이 서로 다르다. 확인할 때 같은 솔트가 필요하므로 저장된 값과 함께 보관하며, BCrypt는 저장된 60자 값의 앞부분(cost 뒤의 22자)에 솔트를 적어 둔다. 솔트는 비밀이 아니고, 미리 계산해 둔 해시 목록으로 한꺼번에 찾아내는 것을 막는 데 쓴다.
MessageDigest
왜 생겼나 — 해시 알고리즘을 직접 구현하면 틀리기 쉽고 검증하기 어렵다. 자바가 표준 알고리즘의 구현을 이름으로 꺼내 쓰게 해 두어, 어느 환경에서나 같은 결과를 얻는다.
지금 어디에 쓰나 — 내려받은 파일이나 주고받은 데이터의 SHA-256 값을 계산해 적힌 값과 견주어, 중간에 바뀌거나 깨지지 않았는지 확인한다. 비밀번호 저장에는 계산이 빠르고 솔트가 없어서 맞지 않으므로 PasswordEncoder를 쓴다.
MessageDigest는 자바가 주는 해시 계산 클래스(java.security.MessageDigest)다. MessageDigest.getInstance("SHA-256")처럼 알고리즘 이름으로 객체를 얻고, digest(바이트 배열)를 부르면 해시 결과를 바이트 배열로 돌려준다. SHA-256은 바이트 32개이고, 이것을 HexFormat.of().formatHex로 바꾸면 0-9와 a-f 글자 64개가 된다. 솔트를 섞지 않으므로 같은 입력에는 언제나 같은 값이 나온다.
비밀번호 해시 저장
비밀번호 해시 저장은 가입할 때 비밀번호 자체가 아니라 그 해시 값을 저장하는 방법이다. 로그인할 때는 입력한 글자를 같은 방법으로 계산해, 저장된 값과 맞으면 입력이 가입 때의 비밀번호와 같다고 본다. 서버는 원래 비밀번호를 몰라도 맞는지 확인할 수 있고, 저장된 값이 새어 나가도 원래 비밀번호는 바로 드러나지 않으며 그 값을 비밀번호 칸에 넣어도 한 번 더 계산되어 다른 값이 되므로 로그인되지 않는다. 스프링에서는 스프링 시큐리티의 PasswordEncoder로 한다. encode로 저장할 값을 만들고 matches로 확인한다. OWASP는 SHA-256 같은 빠른 해시 함수를 그대로 쓰지 말고, Argon2id나 bcrypt 같은 느리게 만든 비밀번호 전용 함수에 사용자마다 고유한 솔트를 더해 쓰라고 한다.

이렇게 바꿔 보세요

  • 처음 설정으로 — encode가 $2a$10$로 시작하는 60자 값을 만들어 저장하고, 로그인할 때 matches가 입력이 그 값과 맞는지 확인합니다. 맞는 비밀번호라 true입니다.
  • 한 글자만 다른 비밀번호를 입력하면 — matches가 false를 돌려주어 로그인에 실패합니다.
  • 다시 encode해서 equals로 견주면 — encode는 할 때마다 솔트를 새로 만들어 다른 값을 내므로, 맞는 비밀번호인데도 false가 나옵니다. 저장된 값과 견주는 일은 matches로 합니다.
  • 저장된 값을 입력하면 — matches는 입력을 비밀번호로 보고 계산하므로, 저장된 값과 달라져 로그인에 실패합니다.
  • SHA-256을 직접 계산해 저장하면 — 솔트가 없어 같은 글자는 언제 계산해도 같은 64자 값입니다. 그래서 다시 계산해 equals로 견주면 되지만, 같은 비밀번호를 쓰는 회원은 저장된 값도 같습니다.
  • SHA-256에 한 글자 다른 비밀번호를 넣으면 — pass1235의 값은 pass1234의 값과 64자 가운데 61자가 다릅니다.
  • 그대로 저장한 값을 입력하면 — 저장된 값이 곧 비밀번호여서 그대로 로그인됩니다.

처음 설정으로 실행하면

  1. PasswordEncoder encoder = new BCryptPasswordEncoder(); 줄이 실행됩니다. 변수 encoder의 타입은 PasswordEncoder이고, 값은 BCryptPasswordEncoder 객체입니다. PasswordEncoder는 스프링 시큐리티가 주는 인터페이스이고, BCryptPasswordEncoder는 그것을 BCrypt라는 비밀번호 전용 해시로 구현한, 역시 스프링 시큐리티가 주는 클래스입니다.
  2. String saved = encoder.encode("pass1234"); 줄이 실행됩니다. 가입하는 순간, encode가 사용자가 정한 비밀번호 pass1234를 받습니다. encode는 먼저 무작위 값(솔트)을 새로 만들고, 그 솔트와 비밀번호를 함께 BCrypt로 계산합니다. BCrypt는 일부러 계산을 여러 번 되풀이해 느리게 만든 해시입니다.
  3. 나온 값은 60자이고 $2a$10$로 시작합니다. $2a$는 BCrypt로 만든 값이라는 표시, 10은 계산을 얼마나 되풀이할지 정하는 cost 값이고, 그 뒤 22자가 솔트, 나머지 31자가 해시 결과입니다. 이번 실행에서 나온 값은 $2a$10$rlL85YF/J1.aZXD3Bv0GWekFKyqt/OrhKPdwFShdqxkvr3HaDO/4a입니다. 솔트를 매번 새로 만들므로 실행할 때마다 다른 값이 나옵니다.
  4. 서버는 이 60자 값만 saved에 저장합니다. 원래 비밀번호 pass1234는 저장하지 않습니다. 솔트는 이 값의 앞부분에 적혀 있으므로 따로 저장하지 않습니다.
  5. String input = "pass1234"; 줄이 실행됩니다. 이제 로그인입니다. 사용자가 비밀번호 칸에 pass1234를 입력합니다.
  6. encoder.matches(input, saved)가 실행됩니다. matches는 saved의 앞부분에서 cost와 솔트를 읽고, 입력한 글자를 가입 때와 같은 솔트로 BCrypt 계산합니다. 솔트를 새로 만들지 않는 것이 encode와 다른 점입니다.
  7. 계산한 값은 saved와 똑같은 60자입니다. 같은 비밀번호를 같은 솔트로 계산했기 때문입니다.
  8. matches가 계산한 값과 saved를 견주어 같으므로 true를 돌려주고, ok는 true입니다. 로그인에 성공합니다. matches는 계산한 값을 돌려주지 않고 맞는지(true나 false)만 돌려줍니다. 서버는 원래 비밀번호를 저장해 두지 않았는데도 맞는지 확인했습니다.
  9. System.out.println(saved)가 저장된 값 60자를, System.out.println(ok)가 true를 출력합니다. 다시 실행하면 saved는 다른 60자로 출력되지만 ok는 같습니다.

실행 결과

  • PasswordEncoder의 encode는 비밀번호를 $2a$10$로 시작하는 60자 값으로 바꾸고, 서버는 그 값만 저장합니다. 로그인할 때 matches(입력, 저장된 값)가 저장된 값의 솔트로 입력을 다시 계산해 맞는지 확인했고, 같은 pass1234라 true가 나와 로그인에 성공했습니다.
  • 서버는 원래 비밀번호를 저장하지 않았고, 확인하는 데 필요하지도 않았습니다. 저장된 값이 새어 나가도 그 값에서 pass1234를 거꾸로 계산해 낼 방법은 알려져 있지 않습니다. 흔한 비밀번호는 후보를 하나씩 계산해 견주면 찾아낼 수 있지만, BCrypt는 일부러 느리게 계산하므로 그 일에 시간이 많이 듭니다.

코드

// main 메서드 안의 줄만 보임 (import 줄과 클래스·main 선언은 생략)
PasswordEncoder encoder = new BCryptPasswordEncoder();

// 가입할 때: encode가 비밀번호를 해시한 값을 저장한다
String saved = encoder.encode("pass1234");

// 로그인할 때: 입력한 글자와 저장된 값을 matches에 넘겨 견준다
String input = "pass1234";
boolean ok = encoder.matches(input, saved);

System.out.println(saved);
System.out.println(ok);

이 모형의 전제

컴파일러와 실행 환경은 JDK 21.0.12.1(javac 21)이고, PasswordEncoder와 BCryptPasswordEncoder는 스프링 시큐리티 7.1.1(spring-security-crypto 7.1.1)의 것입니다. 열 가지 조합(PasswordEncoder로 저장 4가지, SHA-256으로 저장 3가지, 그대로 저장 3가지)을 모두, 화면의 코드를 import 줄과 클래스, main 메서드(throws Exception)의 틀로 감싼 소스로 만들어 javax.tools로 컴파일하고 새 클래스 로더로 읽어 main을 실행했습니다(verify/spring/src/HashBasicProbe.java). 대조한 것은 화면의 코드가 실행한 소스의 그 부분과 같은 글인지, 프로그램이 출력한 saved와 ok입니다. BCrypt의 saved는 실행할 때마다 다르므로, 실행에서 나온 saved가 $2a$10$와 53글자의 모양인지, ok가 결과 표의 로그인과 같은지를 대조했습니다. 화면과 결과 표에 보이는 BCrypt 값 두 개(B1, B2)는 encode("pass1234")를 실제로 두 번 불러 나온 값을 옮겨 적은 예이고, 두 값 모두 matches("pass1234", 값)가 true인 것과 두 값이 서로 다른 것을 확인했습니다. matches가 계산한 값은 matches가 돌려주지 않으므로, 스프링 시큐리티의 BCrypt.hashpw(입력, 저장된 값)로 계산해 보였습니다. javap로 보면 BCryptPasswordEncoder의 matches는 BCrypt.checkpw를 부르고, checkpw는 저장된 값의 cost와 솔트로 입력을 계산해 저장된 값과 견줍니다. 실행한 조합마다 hashpw로 계산한 값이 saved와 같은지와 matches의 결과가 같았습니다. 같은 비밀번호를 20번 encode하면 20개 값과 솔트가 모두 달랐고 모두 matches가 true였으며, 다시 encode한 값은 equals로 견주면 false였습니다. 잰 시간은 matches 한 번이 수십 ms(두 번 실행해 약 59ms와 78ms), SHA-256 한 번이 0.1ms보다 짧았습니다(CPU에 따라 다릅니다). BCryptPasswordEncoder를 인자 없이 만들면 cost는 10이고 값은 $2a$로 시작합니다. 스프링 시큐리티 문서(Password Storage)는 PasswordEncoder가 비밀번호를 한 방향으로 바꿔 안전하게 저장하게 한다고 설명하고, 저장 방식을 나중에 바꿀 수 있도록 PasswordEncoderFactories.createDelegatingPasswordEncoder()로 만드는 DelegatingPasswordEncoder를 소개합니다. 이것이 새로 만드는 값은 앞에 {bcrypt}가 붙은 BCrypt 값입니다(실행해서 {bcrypt}$2a$10$로 시작하는 것을 확인했습니다). 이 실습은 PasswordEncoder가 하는 일을 보이려고 BCryptPasswordEncoder를 직접 만들었습니다. 스프링 부트 애플리케이션에서는 보통 PasswordEncoder를 빈으로 등록해 씁니다. SHA-256 쪽은 계산이 표준대로인지 SHA-256의 표준 예시 두 가지(메시지 "abc"와 56글자 메시지)를 MessageDigest로 계산해 NIST의 예시 문서와 RFC 6234의 값과 견주었고, 7가지 입력(빈 글자, 1글자, 100글자 포함)을 Node.js의 crypto와 openssl dgst -sha256으로도 계산해 세 구현의 값이 같은 것을 확인했습니다. pass1234와 pass1235의 SHA-256 값은 64자 가운데 61자가 다르며(이 입력에서 관찰한 값입니다), 입력이 0글자, 1글자, 100글자여도 결과는 64자입니다. NIST FIPS 180-4(Secure Hash Standard)는 SHA-256을 메시지에서 다이제스트라는 값을 만드는 단방향 해시 함수로 정하고, 메시지가 조금이라도 바뀌면 매우 높은 확률로 다른 다이제스트가 나온다고 합니다. OWASP의 Password Storage Cheat Sheet는 비밀번호를 평문으로 저장하지 말고 해시해서 저장하라고 하고, SHA-256 같은 빠른 해시는 비밀번호 저장에 맞지 않다고 하며, 사용자마다 고유한 솔트를 더하고 Argon2id, scrypt, bcrypt, PBKDF2 같은 느린 비밀번호 전용 함수를 쓰라고 합니다. 이 실습에서 "거꾸로 계산해 낼 수 없다"는 것은 수학적으로 증명된 것이 아니라 현실적으로 알려진 방법이 없다는 뜻이고, 짧고 흔한 비밀번호는 후보를 하나씩 계산해서 저장된 값과 견주는 방법으로 찾아질 수 있습니다. 화면의 코드는 가입과 로그인을 한 번의 실행 안에 이어 적은 것입니다. 실제 서비스에서는 가입과 로그인이 서로 다른 요청이고 saved는 DB에 보관되며, 서버가 사용자가 입력한 비밀번호 글자를 받아 계산한다고 가정했습니다. BCrypt가 비밀번호의 앞 72바이트만 쓰는 것, cost를 고르는 법, 저장된 값을 더 강한 방식으로 바꾸는 일, 해시 충돌은 다루지 않았습니다(BCrypt의 자세한 동작은 "세부 동작 실습: 비밀번호 해시"에서 다룹니다). 이 실습의 해시 함수는 암호용 해시 함수이고, HashMap의 해시 코드와는 쓰임이 다릅니다.
