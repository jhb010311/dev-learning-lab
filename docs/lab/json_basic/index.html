JSON

JSON은 어떻게 생긴 글이고, 무엇이 틀리면 읽히지 않는가

프로그램끼리 데이터를 주고받을 때(예: 서버가 브라우저에 회원 정보를 보낼 때), 메모리 안의 객체를 그대로 보낼 수는 없습니다. 그래서 정해진 약속대로 글자로 적어 보내고, 받는 쪽은 그 글자를 읽어 다시 자기 언어의 객체로 만듭니다. JSON은 가장 널리 쓰이는 그 약속입니다. 코드 칸에 보이는 것이 JSON 글 그대로입니다. { } 안에 "이름": 값을 쉼표로 이어 적고, 이름과 글자 값은 큰따옴표로 감싸며, 숫자는 따옴표 없이 적습니다. [ ]는 값 여러 개의 목록입니다. 따옴표가 있고 없고가 값의 종류를 정해서 30은 숫자, "30"은 글자입니다. 이 실습은 이름의 따옴표, age의 값, 쉼표를 하나씩 바꿔 가며 같은 글을 두 가지 해석기(글을 읽어 객체로 만드는 프로그램), 곧 Node.js의 JSON.parse와 자바의 Jackson에 넣어, 읽히는지와 읽은 age가 어떤 종류인지를 봅니다. JSON에는 주석을 적는 문법이 없어서, 코드 칸에는 설명 없이 글만 보입니다.

실행으로 대조 · Node.js 24.18.0의 JSON.parse와 Jackson 3.1.5(기본 설정)에 열여덟 가지 조합의 글자를 그대로 넣어 대조

이 실습에 나오는 개념

JSON
JSON(JavaScript Object Notation)은 구조가 있는 데이터를 글자로 적어 주고받기 위한 텍스트 형식이다(RFC 8259 1절). 객체는 { } 안에 "이름": 값을 쉼표로 이어 적고, 목록은 [ ] 안에 값을 쉼표로 이어 적는다. 이름은 반드시 큰따옴표로 감싼 글자이고(4절), 쉼표는 값과 값 사이에만 둔다(4절과 5절의 문법). 서버가 브라우저에 데이터를 보낼 때처럼 프로그램끼리 데이터를 주고받는 곳에서 널리 쓰이며, 받는 쪽이 이 규칙에 어긋난 글을 받으면 보통 글 전체를 읽지 못한다.
JSON의 값의 종류
JSON의 값은 객체, 목록(배열), 숫자, 글자(문자열), 그리고 false, null, true라는 세 낱말 중 하나이다(RFC 8259 3절). 글자는 큰따옴표로 감싸고(7절), 숫자는 따옴표 없이 10진수 숫자로 적고(6절), false, null, true도 따옴표 없이 소문자로 적는다(3절). 따옴표가 있고 없고가 종류를 가르므로 30은 숫자이고 "30"은 글자이다. 읽은 뒤의 계산도 종류를 따라가서, 자바스크립트에서 숫자 30에 1을 더하면 31이지만 글자 "30"에 1을 더하면 글자 "301"이 된다.
파싱(parsing)
파싱은 글자로 적힌 데이터를 문법에 따라 앞에서부터 읽어, 프로그램이 다룰 수 있는 구조(객체 등)로 바꾸는 일이고, 그 일을 하는 프로그램을 해석기(파서)라고 한다. RFC 8259 9절은 JSON 해석기를 JSON 글을 다른 표현으로 바꾸는 것으로 설명하고, JSON 문법에 맞는 글은 모두 받아야 한다고 정한다. 문법에 어긋난 글을 만나면 해석기는 오류를 낸다. 같은 절은 해석기가 JSON이 아닌 형식이나 확장을 받아 줄 수도 있다고 하므로, 어떤 해석기는 설정에 따라 작은따옴표나 마지막 쉼표 같은 것을 받아 주기도 한다.
직렬화와 역직렬화
객체를 저장하거나 전송할 수 있는 형태(바이트열, JSON 등)로 바꾸는 것이 직렬화, 그것을 다시 객체로 복원하는 것이 역직렬화다. 웹 API에서는 객체와 JSON 사이의 변환(Jackson 등)이 대표적이다. 자바 기본 직렬화(Serializable)는 클래스 구조가 바뀌면 호환성 문제가 생기고 보안 위험이 있어 지금은 JSON 등의 형식을 주로 쓴다.

이렇게 바꿔 보세요

  • 처음 설정으로 — 규칙에 맞는 JSON 글. 해석기가 읽어 age가 숫자인 객체를 만듭니다.
  • 30에 큰따옴표를 붙이면 — 읽히지만 age가 글자가 되어, 1을 더하면 301이 됩니다.
  • 이름의 큰따옴표를 지우면 — 이름에 따옴표가 없어 글 전체를 읽지 못합니다.
  • 작은따옴표를 쓰면 — 작은따옴표는 JSON의 따옴표가 아니어서 글 전체를 읽지 못합니다.
  • 마지막 값 뒤에 쉼표를 붙이면 — 쉼표 뒤에 이름이 와야 하는데 끝(})이 와서 글 전체를 읽지 못합니다.
  • 쉼표를 빠뜨리면 — 값 사이에 쉼표가 없어 글 전체를 읽지 못합니다.

처음 설정으로 실행하면

  1. 서버가 브라우저에 회원 정보를 보내려 합니다. 서버의 메모리 안에 있는 객체(이름, 나이, 태그를 가진 것)는 그대로 보낼 수 없습니다. 그래서 정해진 약속대로 글자로 적어 보내는데, 그 약속이 JSON입니다. 보내는 쪽이 객체를 아래 글자로 적었습니다. 받는 쪽의 해석기가 이 글을 읽어 객체로 되돌립니다. 이 실습은 같은 글을 Node.js의 JSON.parse와 자바의 Jackson 두 해석기에 넣어 보았고, 모든 조합에서 두 해석기의 판단이 같았습니다.
  2. 받는 쪽 해석기가 글을 앞에서부터 차례로 읽습니다. 첫 글자는 {입니다. {는 "이름과 값의 묶음이 시작된다"는 뜻이어서, 해석기는 이제부터 "이름": 값이 쉼표로 이어지다가 }로 끝나리라고 기대합니다.
  3. 다음에 "name"이 나옵니다. 묶음 안에서 큰따옴표로 감싼 글자는 이름입니다. 뒤따르는 :는 "이 뒤가 이 이름의 값"이라는 표시입니다.
  4. : 뒤의 "김철수"는 큰따옴표로 감싸여 있으니 글자 값입니다. 이어서 쉼표가 있으므로 다음 "이름": 값이 이어집니다.
  5. 쉼표 다음 줄입니다. "age"는 큰따옴표로 감싼 이름이고, : 뒤의 값은 30입니다. 큰따옴표가 없고 숫자 모양이어서 숫자 값입니다. 뒤에 쉼표가 있어 다음 묶음이 이어집니다.
  6. 쉼표 다음 줄입니다. "tags"는 큰따옴표로 감싼 이름이고, 값은 [로 시작합니다. [ ]는 값 여러 개의 목록입니다. 안의 "vip"와 "new"는 둘 다 큰따옴표로 감싸여 글자 두 개이고, 사이의 쉼표로 나뉩니다. ]에서 목록이 끝납니다.
  7. 마지막으로 }를 만났습니다. 쉼표 없이 }가 나왔으니 {로 시작한 묶음이 여기서 끝납니다. 규칙에 어긋난 곳이 한 군데도 없이 끝까지 읽혔습니다.
  8. 읽기에 성공해, 받는 쪽이 자기 언어의 객체를 만들었습니다. name은 글자 "김철수", age는 숫자 30, tags는 글자 두 개의 목록입니다. 글자로 적어 보낸 것이 다시 객체가 되었습니다.
  9. 받는 쪽 프로그램이 읽은 객체에서 age를 꺼내 1을 더합니다(자바스크립트로 읽은 객체의 age + 1을 실행한 결과입니다). age가 숫자 30이라서 숫자끼리의 덧셈이고, 결과는 31입니다.

실행 결과

  • JSON은 객체를 글자로 적어 주고받는 약속입니다. { } 안에 "이름": 값을 쉼표로 이어 적고, 이름과 글자 값은 큰따옴표로 감싸며, 숫자는 따옴표 없이 적습니다. 받는 쪽 해석기는 이 글을 앞에서부터 읽어 객체로 만들었습니다.
  • age의 30은 따옴표가 없어 숫자이고, 1을 더하면 31입니다. 이 글은 규칙에 한 군데도 어긋나지 않았기 때문에 읽혔습니다.

코드

{
  "name": "김철수",
  "age": 30,
  "tags": ["vip", "new"]
}

이 모형의 전제

해석기는 두 가지입니다. 하나는 Node.js 24.18.0의 JSON.parse(자바스크립트의 표준 해석기)이고, 다른 하나는 자바 21.0.12.1에서 돌린 Jackson 3.1.5(jackson-databind와 jackson-core)의 기본 설정, 곧 JsonMapper.builder().build()로 만든 해석기의 readTree입니다. 열여덟 가지 조합을 모두, 화면의 코드와 같은 글자(줄 끝은 \n, 끝에 줄바꿈 없음)를 두 해석기에 그대로 넣어 실행했고, 성공과 실패 판단, 오류가 난 줄과 칸과 그 자리의 글자, 읽은 age의 종류(JSON.parse의 typeof, Jackson의 노드 종류), 읽은 이름들과 값을 모형과 대조했습니다. 두 해석기는 열여덟 조합 모두에서 성공/실패 판단이 같았고, 실패일 때는 오류 위치도 같았습니다. 실패할 때 두 해석기 모두 오류만 내고 읽은 부분을 돌려주지 않았으며, 글에 오류가 둘 이상이면 처음 만난 곳 하나만 알려 주었습니다. 오류 메시지 원문은 둘이 다르고(예: JSON.parse는 "Expected property name or '}' in JSON at position 4", Jackson은 "was expecting double-quote to start property name"), 화면에는 오류의 종류만 한국어로 적었습니다. 원문은 Probe 출력에 있습니다. 화면의 "자바스크립트로 읽은 객체의 age + 1"은 자바스크립트의 동작입니다. JSON.parse로 읽은 객체의 age에 1을 더한 값(typeof까지 확인했고, 숫자 30은 숫자 31, 글자 "30"은 글자 "301")이며, 자바의 동작이 아닙니다. 같은 글을 Jackson으로 읽으면 age가 글자 노드이고, 그 노드의 intValue()는 오류(JsonNodeException)를 냈으며, asInt()와 정수 필드를 가진 레코드로 읽기는 둘 다 30을 냈습니다. 이것은 Jackson의 변환 동작이어서 화면에는 쓰지 않았습니다. 일부 해석기는 설정에 따라 규칙에 어긋난 글도 받아 주는 옵션이 있습니다. 확인한 범위는 Jackson의 JsonReadFeature 세 가지(ALLOW_SINGLE_QUOTES, ALLOW_UNQUOTED_PROPERTY_NAMES, ALLOW_TRAILING_COMMA)를 켜면 작은따옴표로 감싼 이름, 따옴표 없는 이름, 마지막 값 뒤의 쉼표가 읽힌다는 것까지입니다(쉼표를 빠뜨린 글은 그래도 읽히지 않았습니다). 화면의 대조는 모두 기본 설정으로 한 것입니다. 다른 해석기와 JSON.parse의 설정은 보지 않았습니다. 주석을 넣은 글도 두 해석기가 기본 설정에서 모두 읽지 못했습니다. 문서로 확인한 것은 RFC 8259의 1절(JSON은 구조가 있는 데이터를 직렬화하는 텍스트 형식), 2절(문법. 구조 문자 둘레의 공백은 뜻이 없음), 3절(값은 객체, 배열, 숫자, 문자열 또는 false, null, true이고 이 낱말들은 소문자), 4절(객체의 문법: member를 쉼표로 이어 적고, 이름은 문자열), 5절(배열의 문법), 6절(숫자는 10진수 숫자로 적음), 7절(문자열은 따옴표로 시작하고 끝나며 따옴표는 큰따옴표 %x22 하나뿐), 9절(해석기는 문법에 맞는 글을 모두 받아야 하고, JSON이 아닌 형식을 받아 줄 수도 있음)입니다. 문서는 요약으로만 열려 원문 전체를 대조하지는 못했습니다. 마지막 쉼표와 작은따옴표가 안 된다는 말은 문서에 직접 없고, 4절과 5절의 문법에 쉼표 뒤에 값이 없는 모양과 작은따옴표 모양이 없다는 것과 위 실행 결과를 근거로 삼았습니다. 화면의 JSON은 값 네 종류 가운데 객체, 목록, 글자, 숫자만 다뤘고 true, false, null, 중첩 객체, 글자 안의 이스케이프(\n 등)는 다루지 않았습니다. 같은 주제의 세부 동작(서버가 객체와 JSON을 서로 바꾸는 과정)은 "세부 동작 실습: REST API와 메시지 컨버터"에서 다룹니다.
