AOP와 프록시

프록시는 무엇이고, 스프링은 어떻게 내 메서드 앞뒤에 끼어드는가

왜 생겼나 — 트랜잭션 시작과 커밋, 로그 남기기 같은 일을 메서드마다 직접 적으면 같은 줄이 여러 곳에 흩어지고, 빠뜨리거나 고칠 때 모두 찾아다녀야 한다. 스프링은 그런 일을 메서드 본문 밖에 두고, 빈 대신 등록한 프록시가 호출을 먼저 받아 앞뒤에 끼워 넣게 해서, 원래 메서드의 코드는 손대지 않게 했다.

지금 어디에 쓰나 — @Transactional(트랜잭션으로 묶기), @Cacheable(저장해 둔 결과 돌려주기), @Async(다른 스레드에서 실행하기) 같은 스프링 애너테이션이 이 프록시로 동작한다. 애너테이션을 붙였는데 동작하지 않으면 부른 객체의 클래스 이름에 $SpringCGLIB$가 있는지, new로 직접 만든 객체를 부르고 있지 않은지부터 본다. 직접 끼워 넣을 일이 있으면 @Aspect로 애스펙트 클래스를 만들어 실행 시간 재기나 호출 기록 남기기에 쓴다.

메서드 위에 @Transactional을 붙이면, 그 메서드를 부를 때 트랜잭션을 시작하고 끝내는 일이 우리가 쓰지 않았는데도 일어납니다. 스프링이 우리가 쓴 클래스의 객체를 그대로 빈으로 쓰지 않고, 그 객체 대신 호출을 먼저 받을 대리 객체(프록시)를 만들어 빈으로 보관하기 때문입니다. 이렇게 여러 메서드에 공통으로 필요한 일(트랜잭션, 로그 등)을 메서드 본문 밖에 따로 두고 호출 앞뒤에 끼워 넣는 방식을 AOP라고 합니다. 화면의 OrderService와 Caller는 이 실습에서 예시로 지은 클래스 이름이고, @Service, @Component, @Autowired, @Transactional, 그리고 TransactionSynchronizationManager 클래스는 스프링이 주는 것입니다. TransactionSynchronizationManager.isActualTransactionActive()는 그 줄이 실행되는 때에 트랜잭션이 진행 중이면 true를 돌려줍니다. 부르는 쪽 Caller의 orderService 칸에 @Autowired가 붙어 있으면, 스프링이 이 칸이 자기가 보관한 OrderService 빈을 가리키게 합니다. 이 실습은 @Transactional을 지우거나 그 칸이 new OrderService()로 직접 만든 객체를 가리키게 바꿔 가며, order()가 찍는 줄과 부른 객체의 클래스 이름을 봅니다. 스프링이 주는 @Transactional 대신, @Aspect를 붙여 직접 만든 클래스(예시로 지은 LogAspect)를 끼워 넣을 수도 있습니다.

실행으로 대조 · Spring 7.0.9, H2 2.4.240, AspectJ weaver 1.9.25.1에서 여섯 가지 조합을 실제 @Transactional 프록시(트랜잭션 매니저 + H2)와 @Aspect 프록시로 실행해 찍힌 줄, 부른 객체의 클래스, 트랜잭션 시작·커밋 횟수와 순서를 대조

이 실습에 나오는 개념

프록시(Proxy)
실제 객체를 대신해 호출을 받는 대리 객체다. 호출을 받으면 부가 작업을 수행한 뒤 실제 객체에 전달한다. 스프링은 AOP와 @Transactional 같은 기능을 적용할 빈을 프록시로 감싸 컨테이너에 등록하므로, 다른 빈이 주입받는 것은 실제 객체가 아니라 프록시다.
AOP(관점 지향 프로그래밍)
로깅, 트랜잭션, 권한 검사처럼 여러 곳에 반복해서 나타나는 부가 기능(횡단 관심사)을 핵심 비즈니스 코드에서 분리해 한곳에 모아 두는 프로그래밍 기법이다. 부가 기능을 한 번만 작성하고 "어디에 적용할지"를 따로 지정하므로, 핵심 코드가 깔끔해지고 부가 기능의 수정이 한곳에서 끝난다.
@Transactional
메서드나 클래스에 붙여 그 범위를 하나의 트랜잭션으로 실행하게 하는 애너테이션이다. 프록시가 메서드 실행 전에 트랜잭션을 시작하고, 정상적으로 끝나면 커밋, 예외가 발생하면 규칙에 따라 롤백한다. 트랜잭션을 시작하고 끝내는 코드를 직접 쓰지 않아도 되어 선언적 트랜잭션이라고 한다.
TransactionSynchronizationManager
왜 생겼나 — 트랜잭션을 시작하는 쪽(프록시와 트랜잭션 매니저)과 DB를 쓰는 쪽(JdbcTemplate, JPA 등)이 서로 다른 객체여서, 둘이 같은 트랜잭션의 같은 DB 연결을 쓰려면 지금 스레드의 트랜잭션 상태를 기록해 둘 곳이 필요했다.
지금 어디에 쓰나 — 업무 코드에서 직접 부를 일은 드물다. 테스트나 디버깅에서 @Transactional이 실제로 걸렸는지(프록시를 거쳤는지) 확인할 때 isActualTransactionActive()를 찍어 본다.
TransactionSynchronizationManager는 스프링이 주는 클래스(org.springframework.transaction.support 패키지)로, 트랜잭션에 쓰는 자원(DB 연결 등)과 트랜잭션 상태를 스레드마다 기록해 둔다. 정적 메서드 isActualTransactionActive()는 지금 이 줄을 실행하는 스레드에 실제 트랜잭션이 진행 중이면 true, 아니면 false를 돌려준다. 트랜잭션 매니저(예: DataSourceTransactionManager)가 트랜잭션을 시작할 때 이 상태를 기록하고, 끝낼 때 지운다. 스프링 API 문서는 이 클래스를 자원을 관리하는 코드가 쓰라고 만든 것이고 보통의 애플리케이션 코드가 쓸 것은 아니라고 적는다.
@Autowired
왜 생겼나 — 어느 자리에 어떤 빈을 넣을지를 설정 파일에 하나하나 적으면, 클래스를 고칠 때마다 설정 파일도 함께 고쳐야 한다. @Autowired는 넣어 받을 자리에 표시만 하면 스프링이 타입을 보고 맞는 빈을 골라 넣게 했다.
지금 어디에 쓰나 — 오래된 코드나 테스트 코드에서는 필드 위에 붙인 모양을 흔히 본다. 새로 짜는 코드는 필드 대신 생성자로 빈을 받는 방식을 더 많이 쓴다.
@Autowired는 필드나 생성자에 붙여, 스프링이 그 자리에 들어갈 타입에 맞는 빈을 컨테이너에서 찾아 넣어 주게 하는 애너테이션이다. 필드에 붙이면 그 필드에는 우리 코드가 값을 넣는 줄이 없어도 스프링이 객체를 채워 준다. 맞는 빈이 없으면 기본적으로 주입에 실패한다. 스프링이 찾는 곳은 컨테이너가 보관한 빈이므로, 코드에서 new로 직접 만든 객체는 컨테이너가 보관한 빈과 다른 객체다.
@Aspect와 @Before
왜 생겼나 — 끼워 넣을 일과 그 대상을 설정 파일에 따로 적으면, 코드만 보고는 무엇이 언제 끼어드는지 알기 어렵다. @Aspect와 @Before는 그것을 클래스와 메서드 위에 바로 적게 해서, 한 클래스만 보면 언제 무엇이 실행되는지 알 수 있게 했다.
지금 어디에 쓰나 — 메서드가 불릴 때마다 기록을 남기거나, 실행하기 전에 넘어온 값을 확인하는 일에 쓴다. 메서드가 끝난 뒤에 할 일은 @After나 @AfterReturning을, 앞뒤 모두에 할 일은 @Around를 대신 쓴다.
@Aspect는 클래스 위에 붙여, 그 클래스가 애스펙트(여러 메서드에 공통으로 끼워 넣을 일을 적어 둔 클래스)라고 표시하는 애너테이션이다. 애스펙트도 스프링이 관리하는 빈이어야 하므로, 클래스패스 스캔으로 찾게 하려면 @Aspect만으로는 부족하고 @Component 같은 애너테이션을 따로 붙여야 한다. @Before는 애스펙트의 메서드 위에 붙이고 괄호 안에 포인트컷 식을 적는다. 그 식이 고른 메서드가 실행되기 전에 이 메서드가 먼저 실행된다. 스프링이 어떤 빈에 애스펙트가 걸렸다고 판단하면 그 빈의 프록시를 자동으로 만든다(auto-proxying). 이 기능을 쓰려면 @AspectJ 지원을 켜야 하고 aspectjweaver 라이브러리가 클래스패스에 있어야 한다.

이렇게 바꿔 보세요

  • 처음 설정으로 — 스프링이 OrderService 대신 프록시(OrderService$SpringCGLIB$0)를 빈으로 보관했고, 프록시가 호출을 먼저 받아 트랜잭션을 시작한 뒤 order()를 부릅니다. order()가 본 트랜잭션은 진행 중(true)입니다.
  • @Transactional을 지우면 — 끼워 넣을 일이 없어 스프링이 프록시를 만들지 않습니다. 부른 객체는 OrderService 그대로이고 트랜잭션은 진행 중이 아닙니다(false).
  • new로 만든 객체로 부르면 — 스프링은 프록시를 만들어 보관했지만 부른 것은 직접 만든 객체라서 프록시를 거치지 않습니다. @Transactional이 붙어 있어도 트랜잭션은 시작되지 않습니다(false).
  • 직접 만든 애스펙트를 끼우면 — 직접 만든 애스펙트가 order()를 고르면 스프링이 같은 방식으로 프록시를 만듭니다. 프록시가 [로그] 줄을 먼저 찍고 order()를 부릅니다. 트랜잭션은 시작되지 않습니다(false).

처음 설정으로 실행하면

  1. 프로그램이 시작되면 스프링이 @Service나 @Component가 붙은 클래스를 찾아(컴포넌트 스캔) 그 클래스의 객체를 만들어 보관합니다. 이렇게 스프링이 만들어 보관하는 객체를 빈이라고 합니다. 스프링이 OrderService 클래스의 객체도 하나 만듭니다. 화면에서 생략한 설정 클래스에 적힌 트랜잭션 매니저(스프링이 주는 DataSourceTransactionManager, H2 DB에 연결)도 빈으로 만들어 둡니다.
  2. 스프링이 OrderService의 order() 위에 @Transactional이 붙은 것을 봅니다. 그래서 방금 만든 OrderService 객체를 그대로 빈으로 쓰지 않고, 그 객체 대신 호출을 먼저 받을 대리 객체(프록시)를 만들어 OrderService 빈으로 보관합니다. 프록시는 스프링이 프로그램이 도는 중에 만든 클래스 OrderService$SpringCGLIB$0의 객체입니다. 이 클래스는 OrderService를 상속했고, 프록시는 진짜 OrderService 객체를 참조로 갖고 있습니다. 둘은 서로 다른 객체입니다. 이 클래스도, 프록시를 만드는 줄도 우리가 쓴 코드에는 없습니다.
  3. 스프링이 @Component가 붙은 Caller 클래스의 객체도 만듭니다. orderService 칸에는 @Autowired가 붙어 있어서, 스프링이 OrderService 타입의 빈을 찾아 이 칸이 그 빈을 가리키게 합니다. 이 칸에 값을 대입하는 줄은 우리가 쓰지 않았습니다. 지금 이 칸이 가리키는 것은 스프링이 보관한 프록시입니다.
  4. Caller의 run()이 orderService.order()를 부릅니다. orderService 칸이 가리키는 것이 프록시이므로, 호출은 진짜 OrderService가 아니라 프록시에 먼저 도착합니다. 프록시는 order()에 @Transactional이 붙어 있다는 것을 압니다.
  5. 프록시가 진짜 order()를 부르기 전에 트랜잭션 매니저에게 트랜잭션을 시작하게 합니다. 트랜잭션 매니저는 H2 DB 연결을 하나 받아 트랜잭션을 시작합니다. 이 일을 하는 줄은 order()에 없습니다.
  6. 프록시가 참조로 갖고 있던 진짜 OrderService 객체의 order()를 부릅니다. order()가 isActualTransactionActive()로 지금 트랜잭션이 진행 중인지 묻고, true를 받아 "트랜잭션 진행 중: true"를 찍습니다.
  7. order()가 예외 없이 끝나 프록시로 돌아오면, 프록시가 트랜잭션 매니저에게 커밋하게 합니다. 트랜잭션은 여기서 끝납니다. order()가 런타임 예외로 끝났다면 커밋 대신 롤백합니다.
  8. run()의 다음 줄이 orderService 칸이 가리키는 객체의 클래스 이름을 찍습니다(getClass()와 getSimpleName()은 자바가 주는 메서드입니다). 찍힌 이름은 "OrderService$SpringCGLIB$0"입니다. 우리가 쓴 OrderService가 아니라 스프링이 만든 프록시 클래스입니다. 이름 가운데의 $SpringCGLIB$는 스프링이 CGLIB라는 라이브러리로 만든 클래스에 붙이는 표시입니다.

실행 결과

  • @Transactional이 붙은 OrderService는 스프링이 그대로 빈으로 쓰지 않고, OrderService를 상속한 프록시(클래스 OrderService$SpringCGLIB$0)를 만들어 빈으로 보관했습니다. order()를 부르자 프록시가 먼저 받아 트랜잭션을 시작하고, 진짜 order()를 부른 뒤 커밋했습니다. 그래서 order()가 물었을 때 트랜잭션은 진행 중(true)이었습니다.
  • order()에는 트랜잭션을 시작하거나 커밋하는 줄이 없습니다. 이렇게 공통으로 필요한 일을 메서드 밖에 두고 호출 앞뒤에 끼워 넣는 방식이 AOP이고, 그 일을 끼워 넣는 것이 프록시입니다.

코드

// … 설정 클래스(@EnableTransactionManagement, H2 DataSource, 트랜잭션 매니저 빈)와 import 줄은 생략

@Service
class OrderService {
    // 스프링이 주는 애너테이션: 이 메서드를 트랜잭션으로 묶는다
    @Transactional
    public void order() {
        // 스프링이 주는 메서드: 지금 트랜잭션이 진행 중이면 true를 돌려준다
        boolean active = TransactionSynchronizationManager.isActualTransactionActive();
        System.out.println("트랜잭션 진행 중: " + active);
    }
}

@Component
class Caller {
    // 스프링이 보관한 OrderService 빈을 이 칸이 가리키게 한다
    @Autowired
    OrderService orderService;

    void run() {
        orderService.order();
        System.out.println(orderService.getClass().getSimpleName());
    }
}

이 모형의 전제

Spring Framework 7.0.9(AspectJ weaver 1.9.25.1), H2 2.4.240, HikariCP 7.0.2를 JDK 21에서 AnnotationConfigApplicationContext로 실행해 대조했습니다. 여섯 가지 조합(@Transactional, 아무것도 없음, LogAspect × @Autowired로 받은 빈, new로 만든 객체)을 모두, 화면의 코드와 같은 소스(package와 import 줄만 더함)를 컴파일하고 자식 자바 프로세스를 조합마다 새로 띄워 확인했습니다. 화면에서 생략한 설정 클래스에는 @EnableTransactionManagement, @EnableAspectJAutoProxy, @ComponentScan, H2 메모리 DB에 연결한 DataSource, DataSourceTransactionManager 빈을 두었습니다(트랜잭션 매니저에는 시작·커밋·롤백 횟수와 순서를 세는 줄만 더했습니다). 스프링 부트에서는 이 설정을 자동 설정이 대신 해 주지만, 이 실습은 부트로 실행하지 않았습니다. 대조한 것은 run()이 찍은 줄과 그 순서, 부른 객체의 클래스 이름과 AopUtils로 잰 프록시 여부, 컨테이너에서 꺼낸 OrderService 빈의 클래스와 프록시 여부, 부른 객체와 그 빈이 같은 객체인지, 컨테이너 안의 프록시 개수, 트랜잭션 매니저가 트랜잭션을 시작하고 커밋한 횟수와 그 순서(시작, "트랜잭션 진행 중: true", 커밋)입니다. 단계 문장이 기대는 사실로, 프록시가 OrderService를 상속한 클래스이고 진짜 OrderService 객체 하나를 참조로 갖고 있다는 것, 트랜잭션을 시작할 때 연결한 DB가 H2라는 것, new로 만든 객체는 그 빈과 다르고 프록시가 아니라는 것도 실행으로 확인했습니다. 프록시의 클래스 이름 OrderService$SpringCGLIB$0는 이 검증 실행에서 실제로 찍힌 이름입니다. 문서가 정한 것은 스프링 프레임워크 7.0 문서 Data Access의 Using @Transactional 절(기본인 프록시 방식에서는 프록시를 거쳐 들어온 바깥 호출만 가로챈다는 것, 기본으로 RuntimeException과 Error에서 롤백한다는 것), Core의 AOP Proxies 절(인터페이스가 없는 객체는 CGLIB로 프록시한다는 것), Understanding AOP Proxies 절(호출이 프록시에 닿아야 어드바이스가 실행된다는 것), Declaring an Aspect 절(@Aspect만으로는 스캔되지 않고 @Component가 필요하다는 것), 그리고 TransactionSynchronizationManager의 API 문서(isActualTransactionActive()가 지금 스레드에 실제 트랜잭션이 진행 중인지 돌려준다는 것, 이 클래스는 보통의 애플리케이션 코드가 아니라 자원을 관리하는 코드가 쓰라고 만든 것이라는 것)입니다. "런타임 예외로 끝나면 롤백한다"는 문장은 이 실습에서 실행하지 않았고 문서와 "@Transactional" 실습의 실행 결과에 기댑니다. 이 실습의 OrderService는 인터페이스가 없는 클래스라서 CGLIB 프록시가 만들어졌습니다. 인터페이스를 구현한 클래스에서 JDK 동적 프록시가 쓰이는 경우, 같은 클래스 안에서 부르는 경우(자기 호출), @Transactional과 애스펙트를 함께 쓰는 경우는 다루지 않았고, 그림은 화면의 코드만 보여 주기 위해 줄였습니다. 커밋과 롤백이 DB에 남기는 결과는 "@Transactional" 실습에서, @Before의 실행 시점과 포인트컷 식의 규칙은 "AOP: 어드바이스와 포인트컷" 실습에서, 자기 호출과 프록시 방식(JDK 동적 프록시, CGLIB)은 "프록시와 자기 호출" 실습에서 다룹니다.
