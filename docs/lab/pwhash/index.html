비밀번호 해시

DB가 털렸을 때 비밀번호는 얼마나 버티나

왜 생겼나 — 비밀번호를 평문으로 두면 DB가 유출되는 순간 그대로 드러나고, SHA-256 같은 빠른 해시로 바꿔 저장해도 공격자는 흔한 비밀번호를 아주 빠르게 대입해 맞춰 본다. bcrypt는 회원마다 다른 솔트를 자동으로 붙이고 계산 비용(cost)을 일부러 높여, 한 번 맞춰 보는 데 드는 시간을 늘려 대입 공격을 느리게 만든다.

지금 어디에 쓰나 — 회원 가입과 로그인이 있는 서비스에서 비밀번호를 저장할 때 쓴다. 스프링 시큐리티에서는 PasswordEncoder로 바꿔 저장하고 로그인 때 matches로 비교하며, BCryptPasswordEncoder가 흔한 선택이다. 나중에 원래 값으로 되돌려 써야 하는 정보(외부 API 키 등)는 해시가 아니라 암호화해 저장한다.

회원 두 명이 우연히 같은 비밀번호(password123)를 씁니다. 비밀번호를 DB에 저장하는 방식에 따라, DB가 유출됐을 때 공격자가 원래 비밀번호를 알아내는 데 걸리는 시간이 크게 달라집니다. 해시는 원래 값으로 되돌릴 수 없게 계산해 낸 값입니다. 평문, 해시, 솔트를 넣은 해시, 일부러 느리게 만든 해시(bcrypt)를 비교합니다.

일부만 실행으로 확인 · SHA-256은 실제 계산, bcrypt는 재지 못함

이 실습에 나오는 개념

해시 함수와 솔트
해시 함수는 입력을 고정된 길이의 값으로 바꾸는 함수로, 결과에서 원래 입력을 되돌릴 수 없다. 비밀번호는 원문 대신 해시 값을 저장해 유출되더라도 원문이 드러나지 않게 한다. 솔트는 비밀번호마다 다르게 덧붙이는 무작위 값으로, 같은 비밀번호라도 다른 해시가 되게 해 미리 계산해 둔 해시 목록을 이용한 공격을 막는다.
bcrypt
지금 어디에 쓰나 — 회원 비밀번호를 저장할 때 쓴다. Spring Security의 PasswordEncoderFactories가 만드는 기본 인코더도 새 비밀번호를 bcrypt로 저장하며, 같은 목적의 다른 선택지로 Argon2, scrypt, PBKDF2가 있다.
비밀번호 저장용으로 설계된 해시 함수다. 솔트를 자동으로 생성해 결과에 포함하고, 연산 비용(cost)을 설정해 일부러 계산을 느리게 만든다. 계산이 느리면 공격자가 수많은 후보를 대입해 보는 데 드는 시간이 크게 늘어난다. Spring Security의 BCryptPasswordEncoder가 이를 사용한다.
대칭키 암호화와 비대칭키 암호화
지금 어디에 쓰나 — HTTPS(TLS)에서는 연결을 맺을 때 서버 인증서의 서명 확인과 키 교환에 비대칭키 방식을 쓰고, 이어지는 HTTP 데이터는 AES 같은 대칭키로 암호화한다. DB에 저장하는 카드번호 같은 값은 대칭키로 암호화하고, SSH 로그인에 쓰는 키 쌍은 비대칭키다.
대칭키 암호화는 암호화와 복호화에 같은 키를 쓰는 방식으로 빠르지만 키를 상대와 안전하게 공유해야 하는 문제가 있다(AES). 비대칭키 암호화는 공개키와 개인키의 쌍을 쓰는 방식으로, 공개키로 암호화한 것은 개인키로만 풀 수 있어 키 공유 문제가 없지만 느리다(RSA). 실제로는 비대칭키로 대칭키를 안전하게 교환한 뒤 대칭키로 데이터를 암호화한다.

이렇게 바꿔 보세요

  • 처음 설정으로 — SHA-256. 같은 비밀번호는 같은 해시가 됩니다.
  • 평문 저장 — 유출 즉시 전부 노출됩니다.
  • 솔트를 추가하면 — 같은 비밀번호도 해시가 달라집니다. 하지만 해시 자체가 빠릅니다.
  • bcrypt — 일부러 느리게 만든 해시입니다. 대입에 걸리는 시간이 달라집니다.
  • bcrypt cost 14 — 공격은 더 느려지지만 로그인 검증도 느려집니다.

처음 설정으로 실행하면

  1. 회원 김철수와 이영희가 가입하면서 둘 다 비밀번호를 password123으로 정했습니다. 서버가 SHA-256 방식으로 DB에 저장합니다.
  2. 두 회원의 저장값이 완전히 같습니다. DB를 본 사람은 두 사람의 비밀번호가 같다는 것을 바로 알 수 있고, 하나를 알아내면 같은 값을 가진 모든 회원의 비밀번호를 알게 됩니다.
  3. 사고: 공격자가 DB의 회원 테이블을 통째로 빼냈습니다.
  4. 해시는 거꾸로 계산할 수 없지만, 흔한 비밀번호의 해시를 미리 계산해 둔 표가 이미 존재합니다. 공격자는 저장값을 표에서 찾기만 하면 됩니다. password123의 SHA-256은 누구에게나 같은 값이기 때문입니다.
  5. 흔한 비밀번호 1억 개를 회원 한 명에게 모두 대입해 보는 데 걸리는 시간: 1초 미만. password123처럼 흔한 비밀번호는 사실상 즉시 찾아냅니다.

실행 결과

  • SHA-256 같은 일반 해시 함수는 파일 검증처럼 빨라야 하는 용도로 만들어졌습니다. 비밀번호 저장에는 "빠르다"는 것이 약점입니다.
  • 비밀번호는 암호화가 아니라 해시로 저장합니다. 암호화는 열쇠가 있으면 원래 값으로 되돌릴 수 있지만, 해시는 되돌릴 방법이 없고 서버도 원래 비밀번호를 알 필요가 없습니다.

코드

// 메서드 안의 줄만 보임 (선언과 import는 생략. member·rawPassword는 예시로 만든 변수)
MessageDigest md = MessageDigest.getInstance("SHA-256");
byte[] hash = md.digest(rawPassword.getBytes(UTF_8));
member.setPassword(HexFormat.of().formatHex(hash));

이 모형의 전제

SHA-256 값은 실제로 계산한 값입니다. bcrypt 저장값은 형식을 보이기 위한 예시 문자열입니다. 대입 속도는 대략적인 크기를 나타냅니다. 고성능 그래픽 카드 한 장 기준으로 SHA-256은 초당 수백억 번, bcrypt cost 10은 초당 수천 번 수준이라고 보았고, 공개된 벤치마크의 자릿수에 맞춘 값입니다. 로그인 검증 시간은 검증 실행에서 스프링 시큐리티 7.1.1의 BCryptPasswordEncoder로 matches 한 번에 걸린 시간을 잰 값(cost 10은 약 58ms, 12는 약 232ms, 14는 약 952ms)이며, cost가 2 오를 때 약 4배가 되어 cost를 1 올리면 두 배가 된다는 설명과 맞았습니다. 이 시간은 서버 CPU에 따라 달라집니다. 스프링 시큐리티의 BCryptPasswordEncoder 기본 cost는 10입니다. 검증 실행에서 openssl로 잰 SHA-256 속도는 CPU 코어 하나로 초당 약 3,200만 번이었습니다(화면의 초당 수백억 번은 그래픽 카드 기준의 공개 수치입니다). bcrypt를 공격하는 쪽의 속도(그래픽 카드 기준)는 직접 재지 않았습니다.
