프록시와 리버스 프록시

nginx 뒤의 스프링 부트는 누가 요청했는지 어떻게 아나

왜 생겼나 — 애플리케이션 서버가 인터넷에 바로 나서면 서버마다 인증서를 두고 HTTPS를 처리해야 하고, 여러 대로 늘렸을 때 요청을 나눠 줄 곳도 따로 없다. 리버스 프록시는 바깥 연결을 한곳에서 받아 HTTPS 암호화를 풀고 뒤의 서버들로 나눠 넘겨서, 인증서 관리와 요청 나누기를 서버들 앞의 한 자리로 모은다.

지금 어디에 쓰나 — 스프링 부트 서버 앞에 nginx나 클라우드 로드 밸런서를 두어 HTTPS 처리와 요청 나누기를 맡기는 구성이 흔하다. nginx는 proxy_set_header로 X-Forwarded-For와 X-Forwarded-Proto를 붙이고, 스프링 부트는 application.properties의 server.forward-headers-strategy로 그 헤더를 읽게 한다. 그러면 접속 기록, 주소별 요청 수 제한, https:// 리다이렉트 주소를 만드는 코드가 request.getRemoteAddr()와 request.getScheme()만 불러도 원래 클라이언트의 값을 얻는다.

프록시는 요청을 대신 받아 다른 곳으로 넘겨 주는 중간 서버입니다. 클라이언트 쪽에 서서 클라이언트를 대신하면 포워드 프록시, 서버 쪽에 서서 서버를 대신하면 리버스 프록시입니다. 이 실습은 리버스 프록시로 가장 흔히 쓰는 nginx를 스프링 부트 서버 앞에 둡니다. 서버와 실제로 TCP 연결을 맺는 것은 nginx라서 톰캣이 보는 연결 상대는 nginx의 주소입니다. 그래서 nginx가 원래 주소와 프로토콜을 X-Forwarded-For, X-Forwarded-Proto 헤더로 전하고, 스프링 부트는 server.forward-headers-strategy 설정에 따라 그 헤더를 읽어 request.getRemoteAddr()와 request.getScheme()의 값을 바꿉니다. 이 헤더는 클라이언트도 마음대로 써넣을 수 있다는 점이 함정입니다.

일부만 실행으로 확인 · 스프링 부트 쪽은 실제 스프링 부트 4.1.1(내장 톰캣 11.0.24)에 화면의 컨트롤러를 그대로 컴파일해 none·native·framework·설정 안 함으로 띄우고 32가지 조합을 실행해 다섯 열을 대조. nginx는 실행하지 않았고 설정은 nginx 문서(ngx_http_proxy_module)와 대조, 실행에서는 문서대로 헤더를 붙이는 Node 프록시가 nginx 역할을 대신함

이 실습에 나오는 개념

리버스 프록시
왜 생겼나 — 느린 클라이언트가 애플리케이션 서버에 바로 붙으면, 큰 요청 본문을 천천히 올리거나 응답을 천천히 받아 가는 동안 요청 처리 스레드가 그 연결에 묶인다. Nginx 같은 리버스 프록시는 기본 설정에서 요청과 응답을 버퍼에 받아 두고 뒤쪽 서버와는 빠르게 주고받아, 뒤쪽 서버의 스레드가 느린 연결에 오래 묶이지 않게 한다.
지금 어디에 쓰나 — 정적 파일 요청과 /api 요청을 경로로 나눠 다른 서버로 보내거나, Nginx의 client_max_body_size로 너무 큰 업로드를 앞단에서 거절할 때 쓴다. 쿠버네티스에서는 Ingress 컨트롤러가 이 역할을 맡는다.
클라이언트의 요청을 대신 받아 내부의 서버로 전달하고 그 응답을 클라이언트에 돌려주는 서버다. 클라이언트는 실제 서버를 직접 알지 못한다. 여러 서버로의 요청 분산, TLS 처리, 캐싱, 내부 서버 보호 등의 역할을 한다.
포워드 프록시
지금 어디에 쓰나 — 프록시를 거쳐야 밖으로 나가는 회사망에서는 Maven의 settings.xml이나 Gradle의 gradle.properties에 프록시 주소를 적어야 라이브러리를 받는다. 자바 프로그램은 https.proxyHost 같은 시스템 속성으로 정한다.
클라이언트 쪽에 서서 클라이언트의 요청을 대신 바깥 서버로 보내 주는 중간 서버다. 클라이언트는 프록시의 주소를 설정해 두고 일부러 그곳을 거치며, 서버가 보는 연결 상대는 클라이언트가 아니라 프록시가 된다. 회사나 학교에서 밖으로 나가는 요청을 한곳에 모아 기록하거나 막을 때, 또는 클라이언트의 주소를 가릴 때 쓴다. 서버 쪽에 서서 서버를 대신하는 리버스 프록시와는 누구를 대신하는지가 반대다.
X-Forwarded-For
지금 어디에 쓰나 — 접속 기록에 실제 사용자 IP를 남기거나, 한 IP에서 너무 많이 오는 요청을 막을 때 이 값을 읽는다. nginx에서는 proxy_set_header 설정으로 이 헤더를 붙여 넘기게 한다.
프록시가 요청을 넘길 때 원래 클라이언트의 주소를 적어 주는 요청 헤더다. 프록시 뒤의 서버가 보는 연결 상대는 프록시이므로, 실제 클라이언트의 주소는 이 헤더로만 전해진다. 프록시를 여러 대 거치면 각 프록시가 자신에게 연결한 상대의 주소를 쉼표로 뒤에 덧붙인다. 요청 헤더라서 클라이언트도 마음대로 써넣을 수 있으므로, 서버는 자신이 관리하는 믿을 수 있는 프록시가 붙인 값(뒤쪽 값)만 써야 하고 프록시 뒤에 있지 않다면 읽지 말아야 한다. 표준이 아닌 관례이며, 같은 일을 하는 표준 헤더로 Forwarded가 있다.
X-Forwarded-Proto와 TLS 종료
지금 어디에 쓰나 — nginx나 클라우드 로드 밸런서가 HTTPS를 받고, 뒤의 스프링 부트 서버는 HTTP로만 받는 구성에 쓴다. 스프링 시큐리티가 로그인 화면으로 보내는 주소가 https://로 나가려면 server.forward-headers-strategy로 이 헤더를 읽게 한다.
TLS 종료는 리버스 프록시나 로드밸런서가 클라이언트의 HTTPS 연결을 받아 암호화를 풀고, 뒤의 서버에는 암호화하지 않은 HTTP로 넘기는 구성이다. 인증서 관리와 암호화 연산을 한곳에 모을 수 있다. 이때 뒤의 서버는 HTTP 연결만 보게 되므로, 프록시가 X-Forwarded-Proto: https 헤더로 클라이언트가 원래 쓴 프로토콜을 알려 준다. 서버가 이 헤더를 읽지 않으면 리다이렉트할 주소를 http://로 만들거나 보안 쿠키 조건을 잘못 판단할 수 있다. X-Forwarded-For와 마찬가지로 믿을 수 있는 프록시가 붙인 값만 써야 한다.
server.forward-headers-strategy
왜 생겼나 — 서버가 nginx나 로드 밸런서 뒤에 서면서 TCP 연결 상대가 늘 프록시가 되자, 원래 주소와 https 여부를 헤더로 받아 복원하는 일을 애플리케이션마다 손으로 짜지 않도록 스프링 부트가 설정 하나로 묶었다.
지금 어디에 쓰나 — nginx 뒤의 스프링 부트에 server.forward-headers-strategy=native를 적어, 접속 기록과 요청 수 제한이 실제 사용자 IP를 쓰고 스프링 시큐리티의 로그인 리다이렉트 주소가 https://로 나가게 한다.
스프링 부트가 프록시가 붙인 X-Forwarded-* 헤더(또는 표준 Forwarded 헤더)를 누가 읽을지 정하는 application.properties 설정이다. native는 웹 서버가 직접 읽게 하며 톰캣이면 RemoteIpValve가 등록되고, framework는 스프링의 ForwardedHeaderFilter가 읽으며, none은 아무도 읽지 않는다. 읽게 하면 request.getRemoteAddr()가 원래 클라이언트의 주소를, request.getScheme()이 원래 프로토콜(https)을 돌려준다. 정하지 않으면 Kubernetes 같은 클라우드 플랫폼에서는 native, 그 밖에서는 none이다. 헤더를 읽게 하는 설정과 프록시가 헤더를 붙이거나 새로 쓰는 설정이 짝을 이뤄야 한다.
RemoteIpValve와 internal-proxies
왜 생겼나 — 헤더는 누구나 써넣을 수 있으므로, "누가 붙인 값인가"를 연결 상대의 주소로 가려 믿을 수 있는 프록시가 붙인 값만 쓰게 하려고 생겼다.
지금 어디에 쓰나 — 로드 밸런서나 nginx의 주소가 기본 사설 주소 범위 밖이면 server.tomcat.remoteip.internal-proxies에 그 주소를 적어 준다. 운영 서버에서 모든 프록시를 믿도록 비워 두지 않는다.
RemoteIpValve는 톰캣이 주는 밸브(요청을 컨트롤러보다 먼저 처리하는 톰캣의 부품)로, 스프링 부트에서 server.forward-headers-strategy=native이면 등록된다. TCP 연결 상대가 믿는 프록시 목록(server.tomcat.remoteip.internal-proxies)에 들 때만 X-Forwarded-For와 X-Forwarded-Proto를 읽고, X-Forwarded-For를 뒤에서부터 읽어 믿는 프록시가 아닌 첫 주소를 getRemoteAddr()의 값으로 정한다. 그래서 프록시가 받은 값 뒤에 덧붙이는 구성에서 클라이언트가 앞에 써넣은 가짜 주소에 속지 않는다. 스프링 부트 4.1의 internal-proxies 기본값은 10.0.0.0/8, 192.168.0.0/16, 127.0.0.0/8 같은 사설·루프백 주소 범위다. 연결 상대가 믿는 프록시가 아니면 헤더를 무시한다.
ForwardedHeaderFilter
왜 생겼나 — 웹 서버마다 다른 방식 대신 스프링이 Forwarded(RFC 7239)와 X-Forwarded-* 헤더를 한 가지 방식으로 처리하고, 링크를 만드는 코드가 원래 주소를 보게 하려고 생겼다.
지금 어디에 쓰나 — 웹 서버의 기본 처리로 부족할 때(X-Forwarded-Prefix로 경로 앞부분까지 바꿔야 할 때 등) framework를 고른다. 이때 nginx는 X-Forwarded-For를 $remote_addr로 새로 쓰게 한다.
스프링 프레임워크가 주는 서블릿 필터로, 스프링 부트에서 server.forward-headers-strategy=framework이면 등록된다. 컨트롤러보다 먼저 요청을 받아 Forwarded 또는 X-Forwarded-* 헤더의 값을 돌려주는 요청 객체로 바꿔 넘기고, 그 헤더들은 지운다. X-Forwarded-For는 맨 앞 값을 getRemoteAddr()의 값으로 쓰며, 연결 상대가 믿는 프록시인지는 따지지 않는다. 그래서 바깥과 맞닿은 프록시가 이 헤더들을 지우거나 새로 써야 안전하다고 스프링 문서가 밝힌다.
HTTPS와 TLS
HTTPS는 HTTP 통신을 TLS로 암호화한 것이다. TLS는 통신 내용을 제3자가 볼 수 없게 하고(기밀성), 중간에서 바꿀 수 없게 하며(무결성), 접속한 서버가 진짜인지 인증서로 확인한다(인증). SSL은 TLS의 전신인 프로토콜로, 지금은 폐기되어 실제로는 TLS만 쓰이지만 관습적으로 SSL이라는 이름이 함께 불린다.

이렇게 바꿔 보세요

  • 처음 설정으로 — 톰캣이 X-Forwarded-For를 뒤에서부터 읽어 nginx가 붙인 값을 고릅니다.
  • 설정하지 않으면 — 모든 요청이 nginx 한 대의 주소에서, http로 온 것으로 보입니다.
  • framework로 읽으면 — ForwardedHeaderFilter는 X-Forwarded-For의 맨 앞 값을 씁니다.
  • nginx가 새로 쓰면 — 클라이언트가 써넣은 값이 nginx에서 사라집니다.
  • nginx에 헤더 줄이 없으면 — nginx가 받은 헤더를 그대로 넘겨서, 톰캣은 클라이언트가 쓴 값만 받습니다.
  • 프록시 없이 framework를 켜면 — ForwardedHeaderFilter는 연결 상대가 누구인지 따지지 않습니다.
  • 직접 split해서 읽으면 — 속에서 하는 일을 손으로 하면 위조된 앞쪽 값을 믿기 쉽습니다.

처음 설정으로 실행하면

  1. 클라이언트(203.0.113.7)가 https://shop.example/whoami를 요청합니다. shop.example이 가리키는 곳은 nginx(10.0.0.5)입니다. 클라이언트는 nginx를 서버로 알고, 그 뒤에 스프링 부트 서버(app)가 따로 있다는 것을 모릅니다. 이 클라이언트는 요청에 X-Forwarded-For: 198.51.100.99 헤더를 직접 써넣었습니다. 요청 헤더는 보내는 쪽이 마음대로 적을 수 있는 글자입니다.
  2. nginx가 HTTPS 암호화를 풀고, proxy_pass http://app:8080에 따라 내부망의 스프링 부트 서버에 새 TCP 연결을 맺어 요청을 HTTP로 넘깁니다. proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for 줄에 따라, 받은 X-Forwarded-For 뒤에 자신에게 연결한 상대의 주소($remote_addr, 203.0.113.7)를 쉼표로 이어 붙입니다. 그래서 클라이언트가 써넣은 값이 앞에, nginx가 붙인 값이 뒤에 놓입니다. X-Forwarded-Proto $scheme 줄로 클라이언트가 쓴 프로토콜(https)도 적고, Host $host 줄로 클라이언트가 요청한 이름(shop.example)을 그대로 넘깁니다.
  3. 톰캣이 요청을 받습니다. TCP 연결 상대는 10.0.0.5, nginx의 주소입니다. 톰캣과 연결을 맺은 것은 nginx이기 때문이고, 받은 연결도 암호화되지 않은 HTTP입니다. 도착한 X-Forwarded-For는 "198.51.100.99, 203.0.113.7", X-Forwarded-Proto는 https입니다.
  4. 톰캣의 RemoteIpValve가 요청을 컨트롤러에 넘기기 전에 연결 상대(10.0.0.5)를 server.tomcat.remoteip.internal-proxies와 맞춰 봅니다. 기본값(10.0.0.0/8 같은 사설 주소 범위)에 드는 주소라 믿는 프록시로 보고 헤더를 읽습니다. X-Forwarded-For를 뒤에서부터 읽어, 믿는 프록시가 아닌 첫 주소(203.0.113.7)를 getRemoteAddr()의 값으로 정합니다. 그보다 앞의 값은 보지 않습니다. X-Forwarded-Proto: https로 getScheme()은 https가 됩니다.
  5. request.getRemoteAddr()는 203.0.113.7, 실제 클라이언트의 주소입니다. request.getScheme()은 https로, 사용자가 쓴 프로토콜과 같습니다.

실행 결과

  • native는 톰캣의 RemoteIpValve가 헤더를 읽습니다. 연결 상대가 믿는 프록시(internal-proxies)일 때만 헤더를 보고, X-Forwarded-For를 뒤에서부터 읽어 믿는 프록시가 아닌 첫 주소를 고릅니다. 맨 뒤 값은 nginx가 직접 붙인 것이라 클라이언트가 앞에 무엇을 써넣어도 속지 않습니다.

server {
    listen 443 ssl;
    server_name shop.example;
    # … 인증서(ssl_certificate) 설정 생략

    location / {
        proxy_pass http://app:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# application.properties (스프링 부트)
# 톰캣의 RemoteIpValve가 X-Forwarded-* 헤더를 읽는다
# 믿는 프록시 주소는 server.tomcat.remoteip.internal-proxies (기본값에 10.0.0.0/8 같은 사설 주소 범위가 있다)
server.forward-headers-strategy=native

// WhoAmIController.java  (WhoAmIController는 예시로 만든 컨트롤러다. HttpServletRequest와 getRemoteAddr()·getScheme()은 서블릿 API가 준다)
import jakarta.servlet.http.HttpServletRequest;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class WhoAmIController {
    @GetMapping("/whoami")
    public String whoami(HttpServletRequest request) {
        return request.getRemoteAddr() + " " + request.getScheme();
    }
}

이 모형의 전제

뒤쪽은 실제 스프링 부트 4.1.1(내장 톰캣 11.0.24, 스프링 프레임워크 7.0.9)로 실행했습니다. 화면의 WhoAmIController 글을 그대로 컴파일해 server.forward-headers-strategy를 none, native, framework로 바꿔 띄우고(직접 split하는 컨트롤러는 none으로), 32가지 조합에서 톰캣에 도착한 헤더와 컨트롤러가 돌려준 값을 기록해 다섯 열이 모두 모형과 같은 것을 확인했습니다. 설정을 아예 적지 않은 서버도 none과 같은 값을 돌려줬고, native일 때만 톰캣에 RemoteIpValve가, framework일 때만 ForwardedHeaderFilter가 등록된 것도 확인했습니다. 앞단의 nginx는 이 컴퓨터에 없어 실행하지 않았습니다. 대신 Node.js 24로 만든 작은 프록시가 nginx 문서(ngx_http_proxy_module)에 적힌 대로 헤더를 붙이게 해서 nginx 역할을 대신했습니다. $proxy_add_x_forwarded_for는 받은 X-Forwarded-For 뒤에 $remote_addr를 쉼표로 덧붙인 값이고 받은 헤더가 없으면 $remote_addr와 같다는 것, proxy_set_header 줄이 없으면 Host와 Connection만 바꾸고 나머지 요청 헤더는 그대로 넘긴다는 것은 문서 기준입니다. 실행은 한 컴퓨터의 루프백 주소(클라이언트 127.0.0.10, 프록시 127.0.0.20, 서버 127.0.0.30)로 했고, 화면의 주소(203.0.113.7과 198.51.100.99는 문서 예시용, 10.0.0.x는 사설망)는 그것을 바꿔 적은 것입니다. 스프링 부트 4.1.1의 internal-proxies 기본값은 10.0.0.0/8, 192.168.0.0/16, 127.0.0.0/8 같은 사설·루프백 주소 범위의 목록이라 루프백인 클라이언트도 믿습니다. 그래서 실행에서는 internal-proxies를 프록시 주소(127.0.0.20) 하나로 좁혀 "nginx(10.0.0.5)는 믿고 클라이언트(203.0.113.7)는 믿지 않는" 화면의 상황을 만들었고, 기본값이 10.0.0.5는 믿고 203.0.113.7과 198.51.100.99는 믿지 않는 것을 같은 실행에서 확인했습니다. 스프링 부트는 Kubernetes 같은 클라우드 플랫폼을 알아보면 이 설정의 기본값을 native로 바꾸는데, 이 실습은 그렇지 않은 경우만 다룹니다. X-Forwarded-For와 X-Forwarded-Proto는 표준이 아니라 널리 쓰이는 관례이고, 같은 정보를 전하는 표준 헤더로 Forwarded(RFC 7239)가 있습니다. 포워드 프록시, 프록시가 여러 대 이어진 경우, 로드밸런서의 분산은 다루지 않았습니다.
