HTTP 메시지와 상태 코드

요청과 응답은 이렇게 생긴 글자다

왜 생겼나 — 브라우저, 앱, 서버를 서로 다른 사람이 만들어도 대화가 되려면 묻고 답하는 모양이 미리 정해져 있어야 한다. HTTP 메시지는 첫 줄, 헤더, 본문의 형식과 메서드, 상태 코드의 뜻을 정해 두어서, 본문을 읽지 않고도 성공했는지, 다른 주소로 가야 하는지, 잠시 뒤 다시 시도할지를 어느 프로그램이든 같은 방식으로 판단하게 한다.

지금 어디에 쓰나 — 스프링 컨트롤러가 돌려주는 ResponseEntity의 상태 코드와 헤더가 그대로 응답 메시지가 된다. REST API를 설계할 때 생성은 201, 입력 오류는 400, 권한 없음은 403처럼 결과에 맞는 상태 코드를 고르고, 문제가 생기면 브라우저 개발자 도구의 Network 탭이나 curl -v로 실제로 오간 메시지를 읽어 원인을 찾는다.

브라우저와 서버가 주고받는 HTTP 메시지는 HTTP/1.1에서는 정해진 모양의 글자입니다(HTTP/2와 HTTP/3은 같은 내용을 이진 형식으로 나눠 보냅니다). 요청에는 "무엇을(주소) 어떻게(메서드)"가, 응답에는 "어떻게 됐는지(상태 코드)"가 첫 줄에 적힙니다.

일부만 실행으로 확인 · 메시지 구조는 실제 원문과 대조, 상태 코드는 표준 기준

이 실습에 나오는 개념

HTTP와 무상태(Stateless)
왜 생겼나 — 서버가 요청마다 앞선 대화를 기억해야 하는 방식이면, 사용자가 늘수록 그 기억을 쌓아 둘 자원이 늘고 연결이 끊기면 대화를 이어 갈 수 없다. HTTP는 요청 하나만 보고 처리할 수 있게 정해, 서버가 요청 사이에 아무것도 기억하지 않아도 되게 했다.
지금 어디에 쓰나 — 웹 페이지와 이미지를 받는 일, 모바일 앱이 서버 API를 부르는 일, 서버가 다른 서비스의 API를 부르는 일이 모두 HTTP로 이뤄진다. 서버 쪽에서도 수시로 먼저 보내야 하는 채팅 같은 기능에는 WebSocket을 함께 쓴다.
HTTP는 클라이언트가 요청을 보내면 서버가 응답하는 방식의 통신 규약이다. 무상태라는 것은 서버가 이전 요청의 내용을 기억하지 않아 각 요청이 그 자체로 처리에 필요한 정보를 모두 담고 있어야 한다는 뜻이다. 서버가 상태를 기억하지 않으므로 어느 서버가 요청을 받아도 되어 서버를 늘리기 쉽다. 로그인 상태처럼 이어져야 하는 정보는 쿠키, 세션, 토큰으로 유지한다.
HTTP 메서드
요청이 자원에 대해 수행하려는 동작을 나타낸다. GET은 조회, POST는 생성이나 처리 요청, PUT은 전체 교체, PATCH는 일부 수정, DELETE는 삭제를 뜻한다. 메서드의 의미에 맞게 사용해야 캐시, 재시도 같은 HTTP의 동작이 기대대로 이뤄진다.
HTTP 상태 코드
왜 생겼나 — 결과를 본문의 글로만 알리면 서버마다 적는 방식이 달라서, 브라우저나 프록시, 모니터링 도구는 그 요청이 성공했는지 알 수 없다. 상태 코드는 결과를 정해진 숫자로 알려, 이런 도구가 서버마다 따로 맞추지 않고도 캐시, 재시도, 오류 집계를 하게 한다.
지금 어디에 쓰나 — 프런트엔드가 401이면 로그인 화면으로, 404면 없는 페이지 안내로 보내는 것처럼 오류 종류에 따라 처리를 나눌 때 쓴다. 운영에서는 5xx 응답의 비율을 지켜보다가 갑자기 늘면 장애로 보고 알림을 보낸다.
서버가 요청을 처리한 결과를 나타내는 세 자리 숫자다. 2xx는 성공, 3xx는 다른 위치로의 이동(리다이렉션), 4xx는 클라이언트의 요청에 문제가 있음, 5xx는 서버 쪽 오류를 뜻한다. 200(성공), 201(생성됨), 400(잘못된 요청), 401(인증 필요), 403(권한 없음), 404(없음), 500(서버 오류)이 자주 쓰인다.
REST
왜 생겼나 — API마다 /getUser, /deleteUserById처럼 주소에 동작 이름을 제각각 지으면, 쓰는 쪽은 API마다 규칙을 새로 익혀야 한다. REST는 주소는 자원만 가리키고 동작은 HTTP 메서드로 나타내게 해서, 처음 보는 API도 같은 규칙으로 읽게 한다.
지금 어디에 쓰나 — 웹 화면이나 모바일 앱이 서버의 데이터를 조회하고 바꾸는 API, 회사 밖에 공개하는 API를 설계할 때 흔히 따른다. 화면마다 필요한 필드만 골라 받으려면 GraphQL을, 서버끼리 빠르게 부르려면 gRPC를 대신 쓰기도 한다.
웹의 자원을 URI로 식별하고, 그 자원에 대한 행위를 HTTP 메서드로 표현하며, 자원의 표현(JSON 등)을 주고받는 아키텍처 스타일이다. 서버가 클라이언트의 상태를 저장하지 않는 무상태성과 일관된 인터페이스를 특징으로 한다. 실무에서는 이 원칙에 따라 설계한 HTTP API를 REST API라고 부른다.
URI와 URL
URI는 자원을 식별하는 문자열이고, URL은 그중 자원의 위치(접근 방법과 주소)로 식별하는 것이다. 웹에서 쓰는 주소는 대부분 URL이며 URL은 URI에 포함되는 개념이다.

이렇게 바꿔 보세요

  • 처음 설정으로 — 조회 성공. 200과 함께 본문이 옵니다.
  • 새 주문 등록 — 201과 함께 새로 만들어진 주소를 알려 줍니다.
  • 잘못된 요청 — 400. 보낸 쪽이 고쳐야 합니다.
  • 로그인 안 함 — 로그인하지 않으면 401이 돌아옵니다. 로그인했지만 권한이 없을 때의 403은 상황 "남의 주문을 조회"에서 봅니다.
  • 없는 주문 — 404. 주소가 가리키는 대상이 없습니다.
  • 서버 오류 — 500. 보낸 쪽이 아니라 서버가 고쳐야 합니다.

처음 설정으로 실행하면

  1. 요청의 첫 줄(시작 줄)입니다. 메서드 GET, 대상 경로 /orders/1, 프로토콜 버전 순서입니다. 메서드는 "무엇을 하려는지", 경로는 "무엇에 대해서인지"를 나타냅니다.
  2. 그다음 줄들은 헤더입니다. "이름: 값" 형태로 요청에 대한 부가 정보를 싣습니다. Host는 어느 사이트로 가는 요청인지, Authorization은 누가 보내는지 알려 줍니다.
  3. 헤더가 끝났다는 표시로 빈 줄이 하나 들어갑니다. 이 요청은 보낼 데이터가 없어 본문이 없습니다. 서버는 이 요청 하나만 보고 처리할 수 있어야 합니다. 앞서 보낸 요청을 기억하지 않기 때문입니다(무상태).
  4. 서버의 응답입니다. 첫 줄의 상태 코드는 200 OK입니다. 세 자리 숫자의 첫 자리가 큰 분류입니다: 2xx 성공.
  5. 요청한 주문을 찾아 본문에 담아 돌려줍니다.

실행 결과

  • 상태 코드의 첫 자리만 봐도 대응이 갈립니다. 4xx는 대부분 요청 쪽을 고쳐야 풀립니다(408, 429처럼 잠시 뒤 다시 보내면 되는 경우도 있습니다). 5xx는 서버 쪽 문제라서 잠시 뒤 다시 시도해 볼 수 있습니다. 모니터링에서도 4xx와 5xx를 따로 셉니다.
  • HTTP/1.1 메시지는 시작 줄, 헤더, 빈 줄, 본문의 네 부분입니다. 요청의 시작 줄에는 메서드와 경로가, 응답의 시작 줄에는 상태 코드가 들어갑니다.

코드

// 컨트롤러 메서드만 보임 (클래스·필드 선언, import, 예시로 만든 타입의 선언은 생략)
@GetMapping("/orders/{id}")
OrderDto get(@PathVariable long id) {
    return orderService.find(id);                 // 200 OK + JSON 본문
}

이 모형의 전제

메시지의 구조(시작 줄, 헤더, 빈 줄, 본문)는 실제 HTTP 서버와 소켓으로 주고받은 원문에서 확인한 모양 그대로이며, 화면에서는 주요 헤더만 남겼습니다. 상황별 상태 코드는 HTTP 표준(RFC 9110)의 정의와 REST API에서 널리 쓰는 관례를 따랐습니다. 남의 자원에 대한 요청에 403 대신 404를 주어 자원의 존재를 숨기는 설계도 있습니다.
