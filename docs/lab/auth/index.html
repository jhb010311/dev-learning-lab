세션과 JWT

로그인 상태는 어디에 저장되나

왜 생겼나 — HTTP 요청은 앞선 요청을 모르므로, 요청마다 비밀번호를 다시 보내지 않으려면 "이미 로그인한 사용자"임을 알릴 표시가 필요하다. 세션은 서버가 로그인 기록을 저장해 두고 세션 ID로 찾아 이 문제를 풀고, JWT는 서버가 서명한 토큰을 검증만 하면 되게 해서 서버가 여러 대여도 로그인 기록을 함께 볼 저장소 없이 사용자를 확인하게 한다.

지금 어디에 쓰나 — 서버가 화면을 만들어 보내는 웹 서비스는 세션을 흔히 쓰고, 서버가 여러 대이면 Redis 같은 공용 저장소에 세션을 둔다. 모바일 앱이나 여러 서비스가 같은 로그인을 확인해야 하는 API에서는 JWT를 흔히 쓰며, 이미 발급한 토큰은 만료 전에 무효로 만들기 어려우므로 액세스 토큰을 짧게 두고 리프레시 토큰으로 다시 발급한다. 스프링 서버에서는 Spring Security가 주는 JwtEncoder(NimbusJwtEncoder)로 토큰을 발급하고, OAuth2 리소스 서버 설정(oauth2ResourceServer)이 JwtDecoder(NimbusJwtDecoder)로 요청마다 서명과 만료 시각을 검사한다.

로그인한 사용자가 10분 간격으로 요청을 보내고, 로드밸런서가 요청을 서버에 돌아가며 나눠 줍니다. 로그인 상태를 서버가 기억하는 방식(세션)과 클라이언트가 들고 다니는 방식(JWT)에서, 서버를 늘리거나 강제 로그아웃을 시킬 때 무슨 일이 생기는지 보세요.

개념 모형 · 널리 쓰이는 구성을 옮긴 모형(JWT 코드는 Spring Security 시그니처 대역으로 컴파일만 확인)

이 실습에 나오는 개념

쿠키
서버가 응답에 실어 보내면 브라우저가 저장해 두었다가 같은 사이트에 요청할 때마다 자동으로 함께 보내는 작은 데이터다. HTTP는 요청 사이의 상태를 기억하지 않으므로, 로그인 상태처럼 이어져야 하는 정보를 유지하는 데 쓰인다. 사용자의 브라우저에 저장되므로 내용을 보거나 바꿀 수 있다는 점을 전제로 사용해야 한다.
세션
사용자의 상태를 서버 쪽에 저장하고, 클라이언트에는 그 저장소를 가리키는 식별자(세션 ID)만 쿠키로 전달하는 방식이다. 실제 정보가 서버에 있으므로 클라이언트가 내용을 고칠 수 없다(세션 ID를 빼앗기는 것은 다른 문제다). 서버가 여러 대일 때는 어느 서버로 요청이 가도 같은 세션을 찾을 수 있도록 Redis 같은 공용 저장소에 세션을 두는 구성이 일반적이다.
JWT(JSON Web Token)
사용자 정보 등의 내용(클레임)을 담고 서명을 붙인 토큰이다. 헤더, 페이로드, 서명의 세 부분으로 이뤄진다. 서버는 서명을 검증해 토큰이 위조되지 않았음을 확인하며, 별도의 저장소를 조회하지 않아도 된다. 페이로드는 암호화된 것이 아니라 인코딩된 것이어서 누구나 내용을 볼 수 있으므로 민감한 정보를 넣지 않는다.
JwtEncoder와 NimbusJwtEncoder
왜 생겼나 — 토큰을 직접 만들면 머리말과 클레임을 JSON으로 적고 base64url로 바꾸고, 알맞은 알고리즘으로 서명해 이어 붙이는 일을 모두 손으로 맞춰야 한다. 스프링은 검증 쪽의 JwtDecoder와 짝이 되도록 발급 쪽에도 인터페이스를 두어, 클레임만 정하면 같은 라이브러리가 서명까지 해 주게 했다.
지금 어디에 쓰나 — 로그인 API가 액세스 토큰을 직접 발급하는 서버에서 쓴다. 같은 키로 만든 JwtDecoder를 빈으로 등록하고 http.oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))를 켜 두면, 발급한 토큰을 이후 요청에서 검증한다. 구글이나 키클록 같은 인가 서버가 토큰을 발급하는 구성에서는 서비스 서버가 JwtEncoder 없이 JwtDecoder만 쓴다.
JwtEncoder는 Spring Security(spring-security-oauth2-jose)가 주는 인터페이스로, 메서드 Jwt encode(JwtEncoderParameters parameters) 하나로 토큰을 만들어 서명한다. 넘기는 값은 JwtClaimsSet.builder()로 적은 클레임(sub, iat, exp 등)과 JwsHeader.with(MacAlgorithm.HS256)처럼 서명 알고리즘을 정한 머리말이고, 돌려받은 Jwt의 getTokenValue()가 사용자에게 내려 줄 토큰 글자다. 실패하면 JwtEncodingException을 던진다. NimbusJwtEncoder는 Nimbus JOSE+JWT 라이브러리로 이 일을 하는 기본 구현이다. 대칭 키(HS256)는 NimbusJwtEncoder.withSecretKey(key).build(), RSA·EC 키 쌍은 withKeyPair(publicKey, privateKey)로 만든다(둘 다 Spring Security 7.0부터).
JwtDecoder와 NimbusJwtDecoder
왜 생겼나 — JWT 검증은 base64url 풀기, 알고리즘 고정, 서명 계산과 시간이 일정한 비교, 키 길이, 만료 시각과 시계 오차 같은 것을 모두 바르게 해야 해서, 직접 짜면 한 군데만 빠뜨려도 위조 토큰이 통과한다. 스프링은 이 일을 검증된 라이브러리에 맡기고 결과만 Jwt 객체와 정해진 예외로 돌려주는 인터페이스를 두었다.
지금 어디에 쓰나 — 스프링 부트에서 JwtDecoder를 빈으로 등록하고 http.oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))를 켜면, BearerTokenAuthenticationFilter가 요청마다 decode를 불러 실패하면 401로 답한다. iss나 aud도 확인하려면 JwtValidators.createDefaultWithIssuer 등으로 만든 검증기를 setJwtValidator로 넣는다.
JwtDecoder는 Spring Security(spring-security-oauth2-jose)가 주는 인터페이스로, 메서드 Jwt decode(String token) 하나로 토큰 글자를 검증해 Jwt 객체로 바꾼다. 검증에 실패하면 JwtException 계열의 예외를 던진다. 형식이나 알고리즘, 서명이 틀리면 BadJwtException을, 서명은 맞는데 만료 시각 같은 검증 규칙에 걸리면 BadJwtException을 물려받은 JwtValidationException을 던진다. NimbusJwtDecoder는 Nimbus JOSE+JWT 라이브러리로 이 일을 하는 기본 구현이다. 대칭 키(HS256)는 NimbusJwtDecoder.withSecretKey(key).build(), 공개 키는 withPublicKey(key), 인가 서버의 키 목록 주소는 withJwkSetUri(uri)로 만든다. 기본 검증기(JwtValidators.createDefault())는 typ 머리말과 만료·시작 시각을 확인하며, 만료 시각에는 60초 여유를 둔다.
액세스 토큰과 리프레시 토큰
왜 생겼나 — 토큰 하나로 로그인을 유지하면 유효 기간을 길게 잡을 때는 탈취된 토큰이 오래 쓰이고, 짧게 잡을 때는 사용자가 자주 다시 로그인해야 했다. 액세스 토큰과 리프레시 토큰으로 나누면 API 요청마다 오가는 토큰은 수명이 짧아지고, 로그인은 리프레시 토큰으로 이어진다.
지금 어디에 쓰나 — JWT로 로그인을 유지하는 모바일 앱과 SPA에서 흔히 쓴다. 리프레시 토큰은 HttpOnly 쿠키나 앱의 보안 저장소에 두고, 서버도 기록해 두었다가 로그아웃하면 폐기하는 구성이 많다.
액세스 토큰은 API를 호출할 때 제시하는 토큰으로, 탈취되었을 때의 피해를 줄이기 위해 유효 기간을 짧게 둔다. 리프레시 토큰은 액세스 토큰이 만료되었을 때 새 액세스 토큰을 발급받는 데 쓰는 토큰으로, 유효 기간이 길고 더 안전하게 보관한다. 서버는 리프레시 토큰을 폐기해 재발급을 막을 수 있다.
HTTP와 무상태(Stateless)
왜 생겼나 — 서버가 요청마다 앞선 대화를 기억해야 하는 방식이면, 사용자가 늘수록 그 기억을 쌓아 둘 자원이 늘고 연결이 끊기면 대화를 이어 갈 수 없다. HTTP는 요청 하나만 보고 처리할 수 있게 정해, 서버가 요청 사이에 아무것도 기억하지 않아도 되게 했다.
지금 어디에 쓰나 — 웹 페이지와 이미지를 받는 일, 모바일 앱이 서버 API를 부르는 일, 서버가 다른 서비스의 API를 부르는 일이 모두 HTTP로 이뤄진다. 서버 쪽에서도 수시로 먼저 보내야 하는 채팅 같은 기능에는 WebSocket을 함께 쓴다.
HTTP는 클라이언트가 요청을 보내면 서버가 응답하는 방식의 통신 규약이다. 무상태라는 것은 서버가 이전 요청의 내용을 기억하지 않아 각 요청이 그 자체로 처리에 필요한 정보를 모두 담고 있어야 한다는 뜻이다. 서버가 상태를 기억하지 않으므로 어느 서버가 요청을 받아도 되어 서버를 늘리기 쉽다. 로그인 상태처럼 이어져야 하는 정보는 쿠키, 세션, 토큰으로 유지한다.

이렇게 바꿔 보세요

  • 처음 설정으로 — 서버 메모리 세션, 서버 2대. 다른 서버로 간 요청은 로그인이 풀립니다.
  • 세션을 Redis로 옮기면 — 어느 서버로 가도 로그인이 유지됩니다. 대신 요청마다 저장소를 조회합니다.
  • JWT로 바꾸면 — 서버는 아무것도 기억하지 않습니다. 25분 뒤 토큰이 만료됩니다.
  • JWT인데 강제 로그아웃 — 이미 발급한 토큰은 만료 전까지 막을 방법이 없습니다.
  • 세션인데 강제 로그아웃 — 저장소에서 세션을 지우면 바로 다음 요청부터 막힙니다.
  • 짧은 액세스 토큰 + 리프레시 토큰 — 15분마다 재발급합니다. 강제 로그아웃이 늦어도 15분 안에 먹힙니다.

처음 설정으로 실행하면

  1. 0분: 서버 1에서 로그인했습니다. 서버 1이 자기 메모리에 세션을 만들고, 세션 ID를 쿠키로 내려 줍니다. 서버 1만 이 사용자를 기억합니다.
  2. 10분: 요청이 서버 2로 갔습니다. 쿠키로 세션 ID를 보냈지만 이 서버 메모리에는 그런 세션이 없어서 로그인하지 않은 사용자로 취급합니다.
  3. 20분: 요청이 서버 1로 갔습니다. 이 서버 메모리에 세션 abc123이 있어서 로그인 상태로 처리합니다.
  4. 30분: 요청이 서버 2로 갔습니다. 쿠키로 세션 ID를 보냈지만 이 서버 메모리에는 그런 세션이 없어서 로그인하지 않은 사용자로 취급합니다.
  5. 40분: 요청이 서버 1로 갔습니다. 이 서버 메모리에 세션 abc123이 있어서 로그인 상태로 처리합니다.
  6. 50분: 요청이 서버 2로 갔습니다. 쿠키로 세션 ID를 보냈지만 이 서버 메모리에는 그런 세션이 없어서 로그인하지 않은 사용자로 취급합니다.

실행 결과

  • 세션이 로그인한 서버 한 대의 메모리에만 있어서, 다른 서버로 간 요청은 로그인이 풀렸습니다. 서버를 여러 대로 늘리려면 같은 사용자를 항상 같은 서버로 보내거나(스티키 세션), 세션을 공용 저장소로 옮겨야 합니다.

코드

// 필요한 부분만 남김 (로그인 처리와 이후 요청 처리는 서로 다른 메서드)

// 로그인 성공 시
HttpSession session = request.getSession();
session.setAttribute("memberId", member.getId());
// 응답 헤더: Set-Cookie: JSESSIONID=abc123; HttpOnly

// 이후 요청마다: 쿠키의 세션 ID로 세션을 찾는다
HttpSession session = request.getSession(false);
if (session == null) {
    throw new ResponseStatusException(HttpStatus.UNAUTHORIZED);   // 스프링이 주는 예외 -> 401 응답
}

이 모형의 전제

로드밸런서는 요청을 서버에 차례로 돌아가며 보낸다고 가정했습니다(로그인은 서버 1, 그다음 요청은 서버 2 …). 세션 만료 시간과 리프레시 토큰 만료(보통 며칠에서 몇 주)는 이 50분 안에 닿지 않는다고 보았습니다. JWT의 서명 검증은 저장소 없이 서버가 가진 키만으로 이루어집니다. 리프레시 토큰을 서버 저장소에 두고 확인하는 것은 널리 쓰이는 구성이지만 표준이 강제하는 것은 아닙니다. 세션 코드에서 ResponseStatusException(HttpStatus.UNAUTHORIZED)을 던지면 401 응답이 되는 것은 스프링 부트 4.1.1 서버를 띄워 확인했습니다(세션 없이 요청하면 401, 로그인해 받은 JSESSIONID 쿠키를 보내면 200). JWT 코드는 Spring Security 7.1.1이 주는 JwtEncoder·NimbusJwtEncoder(발급)와 JwtDecoder·NimbusJwtDecoder(검증)를 썼습니다. 검증 실행 환경에는 spring-security-oauth2-jose와 nimbus-jose-jwt가 없어서 발급과 검증은 실행하지 않았고, 화면의 JWT 코드는 공식 시그니처만 옮긴 대역과 함께 javac로 컴파일되는 것만 확인했습니다. 디코더는 만료 시각에 기본으로 60초 여유를 두지만, 이 실습의 요청은 모두 만료 시각과 5분 이상 떨어져 있어 결과가 바뀌지 않습니다. 만료된 토큰에 decode가 JwtValidationException을 던지고 리소스 서버 설정이 401로 답하는 것은 "JWT의 구조와 검증" 실습에서 공식 소스와 대조한 내용을 따랐습니다.
