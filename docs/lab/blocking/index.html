블로킹·논블로킹·가상 스레드

기다리는 동안 스레드는 무엇을 하나

왜 생겼나 — 요청 하나에 스레드 하나를 붙이는 방식은 DB나 외부 API를 기다리는 동안에도 스레드를 붙잡아 두므로, 동시 요청이 스레드 수를 넘으면 CPU가 놀고 있어도 뒤 요청이 줄을 선다. 논블로킹 이벤트 루프는 기다리는 동안 스레드를 다른 요청에 써서 적은 스레드로 많은 요청을 진행하고, 가상 스레드는 비슷한 효과를 블로킹 방식 코드 그대로 얻게 한다.

지금 어디에 쓰나 — 스프링 MVC는 지금도 요청마다 스레드를 쓰는 블로킹 방식이 기본이고, 가상 스레드를 지원하는 JDK와 스프링 부트에서는 설정으로 요청 처리 스레드를 가상 스레드로 바꿀 수 있다. WebFlux 같은 논블로킹 방식은 외부 호출을 많이 중계하는 게이트웨이나 스트리밍 응답에 쓰며, 이때는 JDBC 같은 블로킹 호출을 이벤트 루프 스레드에서 하지 않아야 한다.

요청마다 DB나 외부 API의 응답을 기다리는 시간이 있습니다. 그 시간에 스레드를 붙잡아 두는 방식(블로킹), 스레드를 놓아주고 응답이 오면 이어서 처리하는 방식(논블로킹), 그리고 블로킹처럼 코드를 쓰지만 기다릴 때 운영체제 스레드를 놓아주는 가상 스레드를 비교해 보세요.

이 실습에 나오는 개념

블로킹과 논블로킹
블로킹은 호출한 작업이 끝날 때까지 호출한 스레드가 멈춰서 다른 일을 하지 못하는 것이다. 논블로킹은 작업이 끝나지 않았어도 호출이 바로 반환되어 스레드가 다른 일을 할 수 있는 것이다. 일반적인 JDBC 호출은 DB 응답이 올 때까지 스레드가 멈추는 블로킹 호출이다.
동기와 비동기
왜 생겼나 — 모든 호출을 동기로 하면 메일 발송처럼 오래 걸리지만 결과가 당장 필요 없는 일까지 끝나기를 기다려야 해서 응답이 늦어진다. 비동기 방식은 일을 맡겨 두고 먼저 다음으로 넘어가 결과는 나중에 받게 한다.
지금 어디에 쓰나 — 결제 승인처럼 결과를 보고 다음 단계를 정해야 하는 호출은 동기로 하고, 알림 발송이나 통계 집계처럼 나중에 끝나도 되는 일은 메시지 큐나 @Async로 비동기 처리한다.
동기는 작업을 요청한 쪽이 결과를 받을 때까지 기다린 뒤 다음으로 진행하는 방식이다. 비동기는 작업을 요청해 두고 결과를 기다리지 않고 다음 일을 진행하며, 결과는 나중에 콜백이나 Future 등으로 전달받는 방식이다.
가상 스레드(Virtual Thread)
지금 어디에 쓰나 — Spring Boot에서는 spring.threads.virtual.enabled=true 한 줄로 요청 처리와 @Async 실행을 가상 스레드로 돌릴 수 있다. 기다림 없이 CPU 계산만 하는 작업에는 이점이 없다.
JDK 21에서 정식 도입된 가벼운 스레드다. 기존 스레드는 운영체제 스레드와 일대일로 묶여 많이 만들 수 없지만, 가상 스레드는 JVM이 관리하며 소수의 운영체제 스레드 위에서 번갈아 실행된다. 대부분의 블로킹 호출에서 대기하는 동안에는 운영체제 스레드를 내주므로, 기존의 단순한 코드 방식으로도 많은 동시 요청을 처리할 수 있다. 다만 JDK 21~23에서는 synchronized 안에서 블로킹하면 운영체제 스레드를 붙잡았고(pinning), 이는 JDK 24에서 해소되었다.
Spring WebFlux와 리액티브
지금 어디에 쓰나 — 외부 API 여러 개를 동시에 불러 모으는 게이트웨이나, 서버가 이벤트를 계속 흘려보내는 스트리밍 응답에 쓴다. JPA로 DB를 쓰는 일반 서비스는 Spring MVC가 맞고, 기다림이 많은 경우는 가상 스레드로 푸는 길도 있다.
적은 수의 스레드로 많은 동시 요청을 처리하기 위한 스프링의 논블로킹 웹 프레임워크다. 요청당 스레드를 하나씩 쓰는 Spring MVC와 달리, I/O를 기다리는 동안 스레드를 붙잡지 않고 데이터가 준비되면 이어서 처리한다. 호출 경로 전체가 논블로킹이어야 효과가 있어 JPA 같은 블로킹 기술과는 맞지 않는다.
이벤트 루프
지금 어디에 쓰나 — WebFlux의 기본 서버인 Netty와 Node.js, Redis가 이 구조로 동작한다. 이벤트 루프에서 블로킹 호출을 해야 하면 Reactor의 Schedulers.boundedElastic() 같은 별도 스레드로 넘긴다.
소수의 스레드가 여러 연결에서 발생하는 입출력 이벤트를 감지해 차례로 처리하는 구조다. 연결마다 스레드를 두지 않으므로 하나의 스레드가 많은 연결을 담당한다. 이 스레드에서 오래 걸리는 작업이나 블로킹 호출을 하면 그 스레드가 맡은 모든 연결의 처리가 멈춘다.
톰캣의 스레드 모델
왜 생겼나 — 요청 하나를 스레드 하나가 끝까지 맡으면, DB 응답을 기다리는 코드도 콜백으로 나누지 않고 위에서 아래로 차례대로 적을 수 있다. 톰캣은 그 스레드를 미리 만든 풀에서 가져다 쓰고 수에 상한을 두어, 요청이 몰려도 스레드가 끝없이 늘지 않게 한다.
지금 어디에 쓰나 — 외부 호출이 느리거나 동시 요청이 많은 스프링 MVC 서비스는 server.tomcat.threads.max와 DB 커넥션 풀 크기를 함께 맞춘다. 요청이 멈춘 듯할 때는 스레드 덤프에서 http-nio-8080-exec-1 같은 요청 처리 스레드가 어느 줄에서 기다리는지 본다.
톰캣은 요청 처리용 스레드를 풀로 관리하며, 요청 하나를 스레드 하나가 맡아 응답이 끝날 때까지 처리한다. 동시에 처리할 수 있는 요청 수는 최대 스레드 수(기본 200)로 제한된다. 쉬는 스레드가 없으면 자바 기본 ThreadPoolExecutor와 달리 최대 수까지 스레드를 먼저 늘리고, 모든 스레드가 사용 중일 때 새 요청이 대기한다. 요청 처리 중 데이터베이스나 외부 호출을 기다리는 동안에도 스레드는 점유된 상태다.

이렇게 바꿔 보세요

  • 처음 설정으로 — 스레드 4개에 요청 12건. 스레드가 기다리느라 묶여 뒤 요청이 줄을 섭니다.
  • 이벤트 루프로 — 스레드 2개로 12건을 동시에 진행합니다.
  • 이벤트 루프에서 블로킹 호출 — 스레드 2개가 묶여 한 번에 2건씩만 진행됩니다. 가장 나쁜 조합입니다.
  • 가상 스레드 — 코드는 블로킹 방식 그대로인데 동시에 진행됩니다.
  • 스레드 풀을 키우면 — 스레드 10개에 요청 30건. 스레드를 늘려도 요청이 그만큼 늘면 똑같이 줄을 섭니다.

처음 설정으로 실행하면

  1. 0.0초: 요청 12건이 들어옵니다. 스레드 4개가 요청을 하나씩 맡습니다. 나머지 8건은 스레드가 빌 때까지 기다립니다.
  2. 0.1초: 각 스레드가 외부 응답을 기다립니다. 기다리는 동안 스레드는 아무 일도 하지 않지만 다른 요청을 맡을 수도 없습니다(블로킹).
  3. 2.0초: 응답이 도착해 요청 4건이 끝났습니다. 풀려난 스레드가 기다리던 요청을 맡습니다(남은 대기 4건).
  4. 4.0초: 응답이 도착해 요청 4건이 끝났습니다. 풀려난 스레드가 기다리던 요청을 맡습니다(남은 대기 0건).
  5. 6.0초: 응답이 도착해 요청 4건이 끝났습니다.

실행 결과

  • 블로킹 방식에서는 동시에 처리할 수 있는 요청 수가 스레드 수를 넘지 못합니다. 기다리는 시간이 길수록 스레드가 오래 묶입니다. 코드가 단순하고 디버깅이 쉬워서 널리 쓰입니다.

코드

// 컨트롤러 메서드만 보임 (클래스·필드 선언, import, 예시로 만든 타입의 선언은 생략)
// 스프링 MVC: 요청마다 스레드 하나가 끝까지 맡는다
// server.tomcat.threads.max=4
@GetMapping("/orders/{id}")
OrderDto get(@PathVariable long id) {
    Order order = orderRepository.findById(id);   // 응답이 올 때까지 스레드가 멈춰 기다림
    Delivery d = deliveryClient.track(order);     // (2초)
    return OrderDto.of(order, d);
}

이 모형의 전제

요청 처리에서 CPU를 쓰는 시간은 무시하고, 외부 응답을 기다리는 시간만 있다고 단순화했습니다. 이벤트 루프와 가상 스레드를 실어 나르는 OS 스레드는 2개로 고정했습니다(실제 기본값은 CPU 코어 수에 맞춰집니다). 가상 스레드는 JDK 21에서 정식 기능이 됐으며, JDK 21~23에서는 synchronized 블록 안에서 기다리면 OS 스레드를 내려놓지 못하는 제약이 있었고 JDK 24에서 해소됐습니다. 검증 환경의 JDK 21에서 기다리는 시간을 0.2초로 줄여 실제로 쟀습니다. 요청 12건 기준으로 스레드 4개 풀은 619ms(세 번에 나눠 처리), 스레드 2개에서 블로킹하면 1,227ms, 가상 스레드는 OS 스레드 2개로 216ms, 스레드 2개에서 기다림을 등록만 하는 방식은 201ms였습니다. 모형의 비율(6초, 12초, 2초, 2초)과 같습니다. 스프링 WebFlux 자체를 띄운 것은 아니고 같은 원리를 JDK만으로 재현한 측정입니다.
