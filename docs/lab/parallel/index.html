순차 호출과 병렬 호출

외부 호출 여러 개를 차례로 할까 한꺼번에 할까

왜 생겼나 — 서로 관계없는 외부 호출 여러 개를 차례로 부르면 각 호출의 대기 시간이 모두 더해진다. 스레드를 직접 만들거나 Future.get으로 하나씩 기다리는 방식은 결과 모으기와 예외 처리가 번거롭다. CompletableFuture는 여러 작업을 동시에 시작해 두고, 결과 합치기와 실패·시간 초과 때 대신할 값 정하기를 메서드를 이어 붙이는 방식으로 쓰게 한다.

지금 어디에 쓰나 — 상품 상세나 마이페이지처럼 화면 하나를 만들려고 회원, 재고, 리뷰 같은 여러 서비스를 함께 불러야 할 때 쓴다. allOf로 모두 끝나기를 기다리고, completeOnTimeout으로 늦은 호출은 기본값으로 대신한다. supplyAsync에 스레드 풀을 넘기지 않으면 대개 공용 ForkJoinPool에서 실행되므로, 외부 호출처럼 기다리는 작업에는 전용 스레드 풀을 지정하는 것이 보통이다.

상품 상세 화면 하나를 만들려고 여러 서비스를 호출합니다. 차례로 부르면 걸리는 시간이 모두 더해지고, 동시에 부르면 가장 느린 호출만큼만 걸립니다.

실행으로 대조 · JDK 21에서 실행해 확인

이 실습에 나오는 개념

CompletableFuture
비동기 작업의 결과를 나타내는 객체로, 작업이 끝났을 때 이어서 실행할 동작을 연결하거나 여러 비동기 작업의 결과를 조합할 수 있다. 결과를 기다리며 스레드를 멈추지 않고 "끝나면 이것을 하라"는 식으로 흐름을 구성한다.
동기와 비동기
왜 생겼나 — 모든 호출을 동기로 하면 메일 발송처럼 오래 걸리지만 결과가 당장 필요 없는 일까지 끝나기를 기다려야 해서 응답이 늦어진다. 비동기 방식은 일을 맡겨 두고 먼저 다음으로 넘어가 결과는 나중에 받게 한다.
지금 어디에 쓰나 — 결제 승인처럼 결과를 보고 다음 단계를 정해야 하는 호출은 동기로 하고, 알림 발송이나 통계 집계처럼 나중에 끝나도 되는 일은 메시지 큐나 @Async로 비동기 처리한다.
동기는 작업을 요청한 쪽이 결과를 받을 때까지 기다린 뒤 다음으로 진행하는 방식이다. 비동기는 작업을 요청해 두고 결과를 기다리지 않고 다음 일을 진행하며, 결과는 나중에 콜백이나 Future 등으로 전달받는 방식이다.
스레드 풀
스레드를 필요할 때마다 만들고 없애는 대신 일정 수의 스레드를 유지하며 재사용하는 구조다. 스레드 생성 비용을 줄이고, 동시에 실행되는 스레드 수를 제한해 과도한 메모리 사용과 컨텍스트 스위칭을 막는다. 처리할 작업은 큐에 쌓이고 빈 스레드가 가져가 실행한다. 톰캣의 요청 처리, DB 커넥션 풀도 같은 발상이다.
ForkJoinPool과 공용 풀
왜 생겼나 — 큰 일을 잘게 나눠 여러 스레드에 주면 스레드마다 끝나는 시간이 달라 먼저 끝난 스레드가 놀게 된다. ForkJoinPool은 스레드마다 작업 줄을 두고, 할 일이 없는 스레드가 다른 스레드의 줄에서 작업을 가져가게(작업 훔치기) 해서 일을 고르게 나눈다.
지금 어디에 쓰나 — Arrays.parallelSort나 병렬 스트림처럼 CPU만 쓰는 큰 계산을 여러 코어에 나눠 돌릴 때 쓰인다. DB나 외부 API를 기다리는 작업은 공용 풀을 붙잡지 않도록 따로 만든 ExecutorService에서 돌린다.
큰 작업을 작은 작업으로 나눠 여러 스레드에서 처리하고 결과를 합치는 데 쓰는 스레드 풀이다. JVM에는 모두가 함께 쓰는 공용 풀(commonPool)이 있으며 병렬 스트림은 기본적으로 이 풀에서 실행된다. 여기서 오래 걸리는 작업을 실행하면 같은 풀을 쓰는 다른 작업까지 느려진다.

이렇게 바꿔 보세요

  • 처음 설정으로 — 4개를 차례로 호출합니다. 시간이 전부 더해집니다.
  • 병렬로 바꾸면 — 가장 느린 호출 하나의 시간만 걸립니다.
  • 병렬인데 스레드가 2개뿐이면 — 동시에 2개까지만 진행됩니다.
  • 느린 호출에 제한 시간 — 1초를 넘는 호출은 기다리지 않고 기본값으로 대신합니다.
  • 5개를 순차로 — 호출이 하나 늘 때마다 그만큼 느려집니다.

처음 설정으로 실행하면

  1. 0.0초: 상품 정보 호출을 시작합니다(0.3초 걸리는 호출).
  2. 0.3초: 상품 정보 응답 도착.
  3. 0.3초: 재고 호출을 시작합니다(0.5초 걸리는 호출).
  4. 0.8초: 재고 응답 도착.
  5. 0.8초: 리뷰 호출을 시작합니다(0.8초 걸리는 호출).
  6. 1.6초: 리뷰 응답 도착.
  7. 1.6초: 추천 상품 호출을 시작합니다(1.6초 걸리는 호출).
  8. 3.2초: 추천 상품 응답 도착.
  9. 3.2초: 모든 결과가 모였습니다. 화면을 조립해 응답합니다.

실행 결과

  • 순차 호출의 응답 시간은 모든 호출 시간의 합입니다. 서로 결과에 의존하지 않는 호출이라면 차례로 부를 이유가 없습니다.

코드

// 메서드 안의 줄만 보임 (클래스·메서드 선언, import, 예시로 만든 productApi·ProductPage 등의 선언은 생략)
var product = productApi.get(id);
var stock = stockApi.get(id);
var reviews = reviewApi.list(id);
var recommend = recommendApi.list(id);

return new ProductPage(product, stock, reviews, recommend);

이 모형의 전제

각 호출의 소요 시간(상품 0.3초, 재고 0.5초, 리뷰 0.8초, 추천 1.6초, 쿠폰 0.4초)은 고정된 예시이고, 호출들은 서로의 결과가 필요 없다고 가정했습니다. 한 호출의 결과가 다음 호출의 입력이라면 그 둘은 순차로 해야 합니다. 병렬 호출은 스레드 하나가 호출 하나를 맡아 기다리는 블로킹 호출을 가정했습니다. completeOnTimeout은 JDK 9부터 있는 메서드입니다. 검증 환경의 JDK 21에서 실제로 실행해 확인했습니다. 같은 시간의 호출 4개로 순차 3,243ms, 병렬(스레드 5개) 1,603ms, 병렬(스레드 2개) 2,127ms, 제한 시간 1초 적용 시 1,011ms가 나와 모형의 값(3.2초, 1.6초, 2.1초, 1.0초)과 일치했습니다.
