N+1

주문 목록 한 번 조회했는데 쿼리는 왜 여러 번 나가나

주문 목록을 조회한 뒤 주문마다 회원 이름을 꺼냅니다. 연관된 회원을 언제, 어떻게 가져오느냐에 따라 DB로 나가는 쿼리 수가 달라집니다. 목록을 가져오는 쿼리 1번에 더해, 연관된 데이터를 가져오는 쿼리가 N번 더 나가는 것을 N+1 문제라고 합니다.

실행으로 대조 · Hibernate 7.4.5와 H2에서 112가지 조합의 SQL 수를 대조

이 실습에 나오는 개념

N+1 문제
목록을 조회하는 쿼리 1번이 실행된 뒤, 조회된 N개의 결과마다 연관 데이터를 가져오는 쿼리가 1번씩 총 N번 더 실행되는 문제다. 데이터가 많아질수록 쿼리 수가 비례해 늘어 성능이 크게 떨어진다. 연관 데이터를 한 번의 쿼리로 함께 가져오거나(fetch join) 여러 건을 묶어 가져오는(배치 조회) 방식으로 해결한다.
지연 로딩과 즉시 로딩
연관된 엔티티를 언제 조회할지에 대한 설정이다. 즉시 로딩(EAGER)은 엔티티를 조회할 때 연관된 엔티티도 함께 가져온다. 지연 로딩(LAZY)은 연관된 엔티티 자리에 프록시 객체를 넣어 두고 실제로 그 값을 사용할 때 조회한다. 즉시 로딩은 필요 없는 데이터까지 항상 가져오고 예상하기 어려운 쿼리를 만들기 때문에 지연 로딩을 기본으로 쓰는 것이 권장된다.
fetch join
JPQL에서 엔티티를 조회하면서 연관된 엔티티를 SQL 조인으로 한 번에 함께 가져오게 하는 기능이다. 지연 로딩으로 설정된 연관 관계라도 이 쿼리에서는 즉시 함께 조회되어 N+1 문제를 해결한다. 컬렉션을 여러 개 함께 가져오면 결과 행이 곱으로 늘어나는 점에 주의한다.
@EntityGraph
조회할 때 함께 가져올 연관 관계를 애노테이션으로 지정하는 기능이다. Spring Data JPA의 리포지토리 메서드에 붙이면 JPQL을 직접 쓰지 않고도 fetch join과 같은 효과를 얻는다.
배치 페치(Batch Size)
지연 로딩 대상을 하나씩 조회하지 않고 여러 개를 IN 조건으로 묶어 한 번에 조회하게 하는 설정이다. 예를 들어 크기를 100으로 두면 100개의 연관 데이터를 한 번의 쿼리로 가져와, N번 실행되던 쿼리가 N/100번으로 줄어든다. 컬렉션을 fetch join하면 페이징을 메모리에서 처리하던 Hibernate 7.3 이하에서, 컬렉션 연관 관계를 페이징과 함께 쓸 수 있는 해결책이다(7.4부터는 fetch join과 페이징의 조합도 DB에서 처리된다).
1차 캐시
영속성 컨텍스트 안에 엔티티를 식별자 기준으로 보관하는 저장소다. 같은 트랜잭션 안에서 같은 식별자로 다시 조회하면 DB에 쿼리를 보내지 않고 보관된 엔티티를 돌려준다. 그 결과 같은 트랜잭션 안에서 같은 식별자의 엔티티는 항상 같은 객체다. 기본적으로 트랜잭션이 끝나면 사라지므로(OSIV가 켜진 웹 요청에서는 요청이 끝날 때까지 유지된다) 애플리케이션 전체의 캐시와는 다르다.

이렇게 바꿔 보세요

  • 처음 설정으로 — 지연 로딩, 주문 10건, 회원 10명. 쿼리가 1 + 10번 나갑니다.
  • 즉시 로딩으로 바꾸면 해결될까 — 쿼리 수는 그대로이고 나가는 시점만 앞당겨집니다.
  • fetch join — 주문과 회원을 한 쿼리로 가져옵니다.
  • 배치 크기 설정 — 회원을 5명씩 묶어서 IN 쿼리로 가져옵니다.
  • 같은 회원의 주문이 많을 때 — 주문 10건, 회원 3명. 이미 읽은 회원은 다시 조회하지 않습니다.
  • 회원 정보를 쓰지 않을 때 — 지연 로딩은 쓰지 않는 회원을 조회하지 않습니다. 즉시 로딩과 비교해 보세요.
  • 주문 30건으로 늘리면 — 지연 로딩에서는 데이터가 늘어난 만큼 쿼리도 늘어납니다.

실행 결과

  • 목록 1번에 더해 회원 수만큼 쿼리가 따라 나갔습니다. 이것이 N+1 문제입니다. 추가 쿼리 수는 주문 건수가 아니라 아직 읽지 않은 서로 다른 회원 수(10명)로 정해집니다.

코드

@Entity class Order {
    @ManyToOne(fetch = FetchType.LAZY)
    Member member;
}

interface OrderRepository {
    @Query("select o from Order o")
    List<Order> findOrders();
}

// 서비스 (트랜잭션 안)
List<Order> orders = repo.findOrders();   // 주문 10건
for (Order o : orders) {
    names.add(o.getMember().getName());  // 회원 이름 사용
}

이 모형의 전제

주문(Order)이 회원(Member)을 @ManyToOne으로 참조하고, 반복문은 트랜잭션(영속성 컨텍스트)이 열려 있는 동안 실행된다고 가정했습니다. 영속성 컨텍스트가 닫힌 뒤에 지연 로딩 대상을 건드리면 기본 설정에서는 쿼리 대신 LazyInitializationException이 납니다. 쿼리 수는 실제 Hibernate 7.4.5와 H2 데이터베이스로 112가지 조합(다섯 가지 방법, 주문 1·10·30건, 회원 1·3·10·30명, 배치 크기 2·5·20, 이름 사용 여부)을 실행해, 실제로 나간 SQL의 수가 화면과 일치하는 것을 확인했습니다. @EntityGraph는 스프링 데이터가 내부에서 쓰는 것과 같은 JPA 엔티티 그래프 힌트로 실행했습니다. 즉시 로딩의 1 + 회원 수는 배치 설정이 없을 때의 값입니다. 배치 로딩은 묶음 크기대로 나누는 Hibernate 6 이후의 방식 기준이며, Hibernate 5의 기본 방식에서는 쿼리가 더 나갈 수 있습니다. SQL 모양은 DB에 따라 달라서 MySQL은 IN 목록을, PostgreSQL은 배열 파라미터(= any(?))를 씁니다. 왕복 시간은 쿼리마다 같다고 단순화했습니다. 실제로는 조인 쿼리 한 번이 단순 조회 한 번보다 무거울 수 있습니다.
