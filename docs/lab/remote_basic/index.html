다른 서버 부르기

서버가 다른 서버를 부르는 것은 메서드를 부르는 것과 무엇이 다른가

왜 생겼나 — 모든 기능을 한 프로그램에 두면 결제 부분만 고쳐도 프로그램 전체를 다시 켜야 하고, 카드 결제나 문자 보내기처럼 다른 회사가 운영하는 기능은 내 프로그램만으로는 할 수 없다. 서버 간 호출은 그런 기능을 따로 실행되는 서버에 맡기고 네트워크로 요청을 보내 결과를 받게 해서, 서로 다른 프로그램끼리 일을 나눠 맡을 수 있게 한다.

지금 어디에 쓰나 — 쇼핑몰 서버가 결제 회사의 서버에 결제를 요청하거나, 지도나 날씨 같은 정보를 다른 서비스의 서버에 물을 때 쓴다. 기능을 여러 서버로 나눈 서비스에서는 주문 서버가 회원 서버나 재고 서버를 부르는 일이 흔하다. 스프링에서는 스프링이 주는 RestClient로 요청을 보내고, 요청 팩토리에 연결 타임아웃과 읽기 타임아웃을 정해 두며, 연결 실패나 타임아웃으로 오는 ResourceAccessException을 받아 처리한다. 요청을 보낸 스레드가 답을 기다리며 멈춰 있지 않게 하려면 WebClient를 쓰고, 답을 바로 받지 않아도 되는 일은 메시지 큐로 넘기기도 한다.

큰 서비스는 기능을 여러 서버로 나누기도 합니다. 주문 서버와 결제 서버가 따로 실행되는 서로 다른 프로그램이라면, 주문 서버의 코드는 결제를 하려고 메서드를 부르는 대신 결제 서버에 네트워크로 요청(POST /pay)을 보내야 합니다. 스프링에서는 이 요청을 스프링이 주는 RestClient로 보냅니다. 화면의 코드는 두 가지입니다. 결제 기능이 같은 프로그램에 있으면 예시로 만든 PayService 객체의 메서드를 payService.pay()로 부르고, 다른 서버에 있으면 restClient.post().uri(...).retrieve().body(String.class)로 결제 서버를 부릅니다. 둘 다 "결제 완료"라는 String을 돌려받지만, 네트워크 너머의 서버를 부를 때는 상대가 꺼져 있어 연결이 거절될 수 있고, 상대가 느리면 답을 기다려야 합니다. 그래서 RestClient를 만들 때 답을 얼마나 기다릴지(타임아웃)를 정해 두고, 실패하면 오는 ResourceAccessException을 catch로 받습니다. 결과는 화면의 코드를 그대로 컴파일해 실행하고, 결제 서버 역할을 하는 작은 서버를 따로 띄워 맞춘 것입니다.

실행으로 대조 · Spring Framework 7.0.9의 RestClient로 화면의 코드를 그대로 컴파일해 실행하고, 결제 서버 역할의 작은 HTTP 서버(정상·느림·꺼짐)를 띄워 열두 가지 조합을 대조(verify/spring/cmp_remote_basic.js)

이 실습에 나오는 개념

서버 간 호출(네트워크 호출)
서버 간 호출은 한 서버의 프로그램이 다른 서버에 네트워크로 요청을 보내 그쪽 기능을 쓰는 것이다. RFC 9110 3.3절은 연결을 맺어 요청을 보내는 프로그램을 클라이언트, 연결을 받아 응답하는 프로그램을 서버라 부르고, 같은 프로그램이 어떤 연결에서는 클라이언트이고 다른 연결에서는 서버일 수 있다고 한다. 그래서 주문 서버는 브라우저에게는 서버이고, 결제 서버에게는 클라이언트이다. 같은 프로그램 안의 메서드 호출과 달리 상대가 꺼져 있어 연결에 실패할 수 있고, 상대가 느리면 답이 올 때까지 기다려야 하며, 답이 영영 오지 않을 수도 있다. 그래서 호출하는 쪽의 코드에 얼마나 기다릴지와 실패했을 때 무엇을 할지를 정해 두어야 한다. 스프링에서는 스프링이 주는 RestClient로 이런 호출을 하고, 기다리는 시간은 요청 팩토리에 정한다.
메서드 호출
메서드 호출은 add(2, 3)처럼 메서드 이름 뒤에 괄호를 붙이고 괄호 안에 넘길 값을 적어 그 메서드의 본문을 실행시키는 식이다. 컴파일러는 호출마다 그 이름의 메서드를 찾고, 고정 인자 메서드라면 넘긴 값의 개수가 매개변수의 개수와 같은지 확인한다. 그 이름의 메서드가 없거나 개수가 맞지 않아 부를 수 있는 메서드가 하나도 없으면 컴파일 오류이다. 실행할 때는 넘기는 값을 왼쪽부터 차례로 계산하고, 그 값을 새로 만든 매개변수 변수에 담은 뒤 본문을 실행한다. 같은 메서드를 두 번 부르면 본문도 두 번 실행된다.
RestClient
왜 생겼나 — RestTemplate은 getForObject, exchange처럼 경우마다 다른 메서드에 인자를 길게 넘겨야 했고, 메서드를 이어 쓰는 WebClient는 리액티브 라이브러리가 필요했다. RestClient는 이어 쓰는 방식을 동기 호출에서 쓰게 한다.
지금 어디에 쓰나 — 스프링 부트 서버에서 결제 API나 다른 서비스의 HTTP API를 부를 때 쓴다. 스프링 부트가 만들어 둔 RestClient.Builder를 주입받아 기본 주소와 헤더를 정해 쓰고, 많은 호출을 스레드를 묶지 않고 다뤄야 하면 WebClient를 쓴다.
스프링에서 다른 서버의 HTTP API를 호출할 때 쓰는 클라이언트다. client.get().uri(주소).retrieve().body(타입)처럼 메서드를 이어 쓰는 방식으로 요청을 만들고, 응답 본문은 메시지 컨버터가 객체로 바꿔 돌려준다. 응답이 올 때까지 호출한 스레드가 기다리는 동기 방식이며, 예전부터 쓰이던 RestTemplate의 뒤를 잇는다. 4xx 응답은 HttpClientErrorException, 5xx 응답은 HttpServerErrorException, 연결 실패나 타임아웃은 ResourceAccessException으로 바뀌어 던져진다. 실제 통신은 요청 팩토리가 맡으며, 타임아웃도 요청 팩토리에 정한다.
연결 타임아웃과 읽기 타임아웃
다른 서버를 호출할 때 얼마나 기다리다 포기할지를 정하는 두 가지 시간이다. 연결 타임아웃은 상대와 TCP 연결이 맺어지기까지 기다리는 한도이고, 읽기 타임아웃은 연결이 맺어진 뒤 응답 데이터가 오지 않는 채로 기다리는 한도다. 두 시간은 서로 다른 구간을 재므로, 연결 타임아웃만 정하면 연결은 됐는데 응답이 늦는 경우를 막지 못한다. 타임아웃을 정하지 않으면 느린 상대 때문에 호출한 스레드가 계속 묶이고, 스레드 풀이 바닥나면 장애가 호출한 쪽으로 번진다. 읽기 타임아웃이 났다고 해서 상대가 요청을 처리하지 않았다는 뜻은 아니므로, 같은 요청을 다시 보낼 때는 중복 처리를 조심해야 한다.
ResourceAccessException
왜 생겼나 — 다른 서버를 부르는 호출은 네트워크 때문에 실패할 수 있는데, 어떤 HTTP 클라이언트 라이브러리를 쓰느냐에 따라 그 오류의 종류가 다르다. 스프링은 이를 한 가지 예외로 던져서, 호출하는 코드가 라이브러리와 상관없이 "응답을 얻지 못했다"를 한 곳에서 받게 한다.
지금 어디에 쓰나 — 다른 서버를 부르는 코드에서 catch (ResourceAccessException e)로 받아, 다시 보내거나 기본값을 쓰거나 사용자에게 잠시 뒤 다시 하라고 알린다. 실패가 이어지면 서킷 브레이커가 이 예외를 세어 한동안 호출을 멈추게 하기도 한다.
ResourceAccessException은 RestClient로 다른 서버를 부르다가 입출력 오류가 나서 응답을 얻지 못했을 때 스프링(spring-web)이 던지는 예외이다. 상대 서버가 꺼져 있어 연결이 거절되거나, 정해 둔 타임아웃이 지나 기다림을 끊었을 때가 그렇다. RestClientException을 물려받은 RuntimeException이라 catch를 강제하지 않으며, 실제로 무슨 일이 있었는지는 getCause()로 본다. 이 실습의 실행에서는 연결이 거절되면 원인이 java.net.ConnectException, 읽기 타임아웃에 걸리면 java.net.SocketTimeoutException이었다. 상대가 답은 했지만 404나 500처럼 오류 상태 코드로 답한 경우는 이 예외가 아니라 HttpClientErrorException이나 HttpServerErrorException으로 온다.

이렇게 바꿔 보세요

  • 처음 설정으로 — RestClient로 결제 서버에 POST /pay를 보내고, 약 0.1초 뒤 "결제 완료"를 String으로 돌려받습니다.
  • 같은 프로그램의 메서드라면 — payService.pay() 한 줄로 부르고, 주소도 연결도 타임아웃도 없습니다. 돌려받는 것은 같은 "결제 완료"입니다.
  • 결제 서버가 꺼져 있으면 — 연결이 거절되어 곧바로 ResourceAccessException이 나고, 원인은 ConnectException입니다.
  • 같은 프로그램이면 결제 쪽만 꺼질 수 있나 — 생기지 않습니다. 주문 코드가 실행되는 동안에는 pay도 부를 수 있어서 처음과 같이 "결제 완료"를 받습니다.
  • 결제 서버가 3초 뒤에 답하면 — 읽기 타임아웃 1초에 걸려 ResourceAccessException이 나지만, 결제 서버는 3초 뒤에 결제를 끝냅니다.
  • 타임아웃을 정하지 않으면 — 3초를 모두 기다려 "결제 완료"를 받습니다.
  • 같은 프로그램의 메서드가 3초 걸리면 — 메서드 호출도 3초를 기다립니다. 그동안 이 스레드가 pay의 본문을 실행하고 있고, 타임아웃을 정하는 자리는 없습니다.

처음 설정으로 실행하면

  1. 주문 서버의 main이 RestClient를 만듭니다. RestClient는 스프링(spring-web)이 주는 HTTP 클라이언트로, 다른 서버에 HTTP 요청을 보내고 답을 받는 일을 합니다. OrderApp은 예시로 지은 클래스 이름입니다. 먼저 스프링이 주는 SimpleClientHttpRequestFactory(요청 팩토리: 실제로 연결을 맺고 요청을 보내는 부품)를 만들어, setConnectTimeout으로 연결을 맺기까지 최대 1초, setReadTimeout으로 연결된 뒤 답을 최대 1초 기다리도록 정합니다. 그리고 RestClient.builder()에 이 팩토리를 넘겨 RestClient를 만듭니다.
  2. restClient.post().uri("http://localhost:9000/pay").retrieve().body(String.class) 문장이 실행됩니다. 겉모양은 메서드를 이어 부르는 것이지만, 이 문장이 하는 일은 결제 서버에 연결을 맺고 POST /pay 요청을 네트워크로 보낸 뒤 답을 받는 것입니다. 결제를 하는 코드는 이 프로그램에 없고, 따로 실행되는 결제 서버 프로그램에 있습니다. post()는 HTTP 메서드를, uri(...)는 보낼 주소를 정하고, body(String.class)는 답의 본문을 String으로 바꿔 돌려줍니다.
  3. 결제 서버가 POST /pay 요청을 받아 결제를 처리합니다. 이 결제 서버는 처리에 0.1초가 걸립니다. 그동안 주문 서버의 main 스레드는 이 문장에서 멈춰 답을 기다리기만 하고, 결제를 하는 일은 결제 서버 프로그램이 합니다.
  4. 0.1초 뒤 결제 서버가 200 응답으로 본문 "결제 완료"를 보냅니다. body(String.class)가 이 본문을 String으로 돌려주고, result에 대입됩니다. System.out.println(result)가 결제 완료를 찍습니다. 정해 둔 1초보다 일찍 답이 와서 타임아웃은 쓰이지 않았습니다.

실행 결과

  • 다른 서버를 부르는 것은 네트워크로 요청을 보내고 답을 기다리는 일입니다. 주문 서버가 RestClient로 결제 서버에 POST /pay를 보냈고, 약 0.1초 뒤 "결제 완료"를 String으로 돌려받았습니다.
  • 돌려받는 것은 같은 프로그램의 메서드를 부를 때와 같은 String이지만, 이 결과를 얻으려면 결제 서버가 켜져 있고 제때 답해야 했습니다. 꺼져 있거나 늦게 답하는 경우는 다음 물음들에서 봅니다.

코드

// 주문 서버의 코드. 결제는 따로 실행되는 결제 서버가 맡는다. OrderApp은 예시로 지은 이름이다.
import java.time.Duration;

import org.springframework.http.client.SimpleClientHttpRequestFactory;
import org.springframework.web.client.ResourceAccessException;
import org.springframework.web.client.RestClient;

public class OrderApp {
    public static void main(String[] args) {
        // 기다리는 시간(타임아웃)은 실제로 연결을 맺고 요청을 보내는 요청 팩토리에 정한다
        SimpleClientHttpRequestFactory factory = new SimpleClientHttpRequestFactory();
        factory.setConnectTimeout(Duration.ofSeconds(1));  // 연결을 맺기까지 최대 1초
        factory.setReadTimeout(Duration.ofSeconds(1));     // 연결된 뒤 답을 최대 1초 기다린다
        RestClient restClient = RestClient.builder()
                .requestFactory(factory)
                .build();

        try {
            String result = restClient.post()
                    .uri("http://localhost:9000/pay")    // 결제 서버의 주소 (9000은 예시 번호)
                    .retrieve()
                    .body(String.class);                 // 답의 본문을 String으로 받는다
            System.out.println(result);
        } catch (ResourceAccessException e) {           // 연결 실패나 타임아웃
            System.out.println("호출 실패: " + e.getCause());
        }
    }
}

이 모형의 전제

Spring Framework 7.0.9(spring-web)의 RestClient를 JDK 21.0.12.1(Windows 11)에서 실행해 대조했습니다. 열두 가지 조합(결제 기능이 있는 곳 두 가지, 결제 쪽의 상태 세 가지, 타임아웃을 정했는지 두 가지)을 모두, 화면의 코드와 같은 글을 OrderApp.java로 써서 javac로 컴파일하고 실행했습니다. 다른 서버를 부르는 코드는 주소의 9000만 실제로 연 빈 포트로 바꾸었습니다(9000은 예시 번호입니다). 결제 서버 역할은 대조 프로그램(verify/spring/src/RemoteBasicProbe.java)이 자바의 ServerSocket으로 127.0.0.1에 띄운 작은 HTTP 서버로, POST /pay를 받으면 0.1초 또는 3초 뒤 200 응답과 본문 "결제 완료"(text/plain, UTF-8)를 보냅니다. 꺼진 결제 서버는 포트를 열었다가 닫아 아무도 듣지 않는 포트를 만들어 흉내 냈습니다. 이 결제 서버는 주문 쪽이 연결을 닫았는지 보지 않고 처리를 끝내도록 이 실습에서 쓴 것이므로, 모든 서버가 그렇게 동작한다는 뜻은 아닙니다. 조합마다 main이 찍은 글, 걸린 시간, 결제 서버가 받은 요청 줄(POST /pay HTTP/1.1), 결제 서버가 처리를 끝낸 때와 그때 주문 쪽 연결이 이미 닫혀 있었는지를 모형과 대조했고, 화면의 코드가 실행한 소스와 같은 글인지도 확인했습니다(verify/spring/cmp_remote_basic.js). 걸린 시간은 화면에 어림으로 적었고, 실행에서 잰 값은 약 0.1초가 0.10~0.21초, 바로가 0.06초 이하, 약 1초가 1.01초, 약 3초가 3.01~3.08초였습니다. 같은 호출을 대조 프로그램에서 한 번 더 해서, catch에 잡힌 예외가 정확히 org.springframework.web.client.ResourceAccessException이고 원인이 java.net.ConnectException(연결 거절)과 java.net.SocketTimeoutException(Read timed out)임을 확인했습니다. catch가 찍는 글에서 ConnectException 뒤의 설명은 요청 팩토리에 따라 달랐습니다. 타임아웃을 정한 SimpleClientHttpRequestFactory는 "Connection refused: getsockopt"를 붙였고, RestClient.create()로 만든 것은 설명 없이 클래스 이름만 찍었습니다. RestClient.create()는 이 실행의 라이브러리 구성(Apache HttpClient, Jetty, Reactor Netty가 없음)에서 JDK의 HttpClient를 쓰는 JdkClientHttpRequestFactory를 골랐고, 타임아웃은 정하지 않았습니다. 다른 라이브러리가 있으면 다른 요청 팩토리를 고를 수 있습니다. 결제 서버가 요청을 받고도 끝내 답하지 않게 했을 때, RestClient.create()로 만든 RestClient는 4초가 지나도록 기다렸고(그 이상은 보지 않았습니다), 타임아웃 1초를 정한 RestClient는 약 1초에 ResourceAccessException(원인 SocketTimeoutException)으로 끝났습니다. 같은 프로그램의 PayService(예시로 만든 클래스)는 Thread.sleep으로 결제 처리에 걸리는 시간을 흉내 냈고, "결제 쪽만 꺼져 있다"는 일은 메서드에는 생기지 않으므로 처음 설정과 같은 0.1초로 실행했습니다. 메서드 호출에는 연결이라는 단계가 없다는 것과, 메서드를 부른 스레드가 그대로 본문을 실행한다는 것은 자바 언어의 동작을 설명한 것이고 따로 재지 않았습니다. 메서드 호출도 다른 스레드에 맡기고 Future.get에 시간을 주어 기다림에 한도를 둘 수는 있지만, 이 실습은 메서드를 그냥 부르는 줄만 다룹니다. 화면은 한 번 부르는 가장 단순한 경우만 다루었고, 연결 타임아웃이 실제로 걸리는 경우(연결 요청에 아무 답이 없는 상대)와 404·500 응답은 "외부 API 호출과 타임아웃", 실패하는 서버를 막아 주는 장치는 "서킷 브레이커", 여러 서버의 일을 되돌리는 방법은 "Saga와 Outbox", 요청을 한곳에서 받아 나누는 방법은 "게이트웨이와 점진적 전환"에서 다룹니다.
