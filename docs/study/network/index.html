이 사이트의 실습은 자바스크립트를 켜야 움직입니다. 아래는 같은 내용을 글로 적은 것입니다.

공부

네트워크

주소를 입력한 뒤 응답이 오기까지. DNS, TCP, HTTP, TLS와 그 사이에 놓인 장비들을 봅니다.

큰 그림

  • 주소 입력부터 응답까지 — 주소창에 입력하고 엔터를 누르면
  • 계층 구조와 캡슐화 — 1500바이트를 보냈는데 왜 전선에는 1616바이트가 지나갈까

주소와 이름

  • URL의 구조 — 검색어 "A&B"를 주소에 붙였더니 서버에는 "A"만 도착했다
  • DNS — 도메인 이름의 주소는 누가 알고 있고, 바꾸면 언제 반영될까
  • IP 주소와 서브넷 — 앞의 세 숫자가 같은 두 IP 주소는 같은 네트워크일까
  • 스위치와 라우터 — 받는 IP는 서버인데 왜 라우터의 MAC 주소로 보내나

전송 계층

  • 소켓과 포트 — 한 컴퓨터의 여러 프로그램 가운데 누가 이 데이터를 받나
  • TCP 연결과 재전송 — 패킷이 사라지면 누가 알아채고 다시 보내나
  • TCP와 UDP — 세 번에 나눠 보낸 데이터는 세 번에 나뉘어 도착하나
  • 흐름 제어와 혼잡 제어 — TCP는 한 번에 얼마나 보낼지를 어떻게 정하나

HTTP

  • HTTP 메시지와 상태 코드 — 요청과 응답은 이렇게 생긴 글자다
  • HTTP/1.1, 2, 3 — 파일 30개를 받을 때 버전마다 무엇이 다른가
  • 쿠키 — 기억하지 못하는 서버에게 매번 이름표를 내민다
  • HTTP 캐시와 ETag — 같은 파일을 또 받을 필요가 있을까
  • 재시도와 멱등성 — 응답을 못 받아서 다시 보냈더니
  • 리다이렉션 — "다른 주소로 가라"는 응답을 받으면 다음 요청은 어떻게 나가나
  • 내용 협상과 압축 — 같은 주소인데 왜 사람마다 다른 응답을 받나
  • CORS — Postman에서는 되는데 브라우저에서만 막히는 이유
  • 폴링·SSE·WebSocket — 서버에서 생긴 일을 브라우저에 알리는 네 가지 방법

보안 연결

  • TLS 핸드셰이크 — https의 자물쇠가 잠기기까지

웹 서버 앞의 장비

  • 로드밸런서와 스케일 아웃 — 서버를 늘리면 어디까지 버티나
  • 프록시와 리버스 프록시 — 프록시 뒤의 서버는 누가 요청했는지 어떻게 아나
  • CDN — 원본을 바꿨는데 왜 사용자는 아직 옛 파일을 받나
