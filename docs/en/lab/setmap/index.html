Kinds of Set and Map

Why do the same values come out in a different order?

Why it exists — HashSet and HashMap choose a place by the hash value and so find things quickly, but the order in which things come out has nothing to do with either the insertion order or the sorted order. It is troublesome to sort separately every time you need an order, or to manage a List alongside to record the order. So Java provides LinkedHashSet and LinkedHashMap, which remember the insertion order, and TreeSet and TreeMap, which always stay sorted.

Where it's used today — If you only need to remove duplicates or look up by key regardless of order, you use HashSet and HashMap. The Linked family is used for lists that must be shown in insertion order and for caches that remove the least recently used entries first (LinkedHashMap's access-order mode), and the Tree family is used for lists in name order and for range searches such as ceilingKey and subMap.

A Set is a collection that holds each value only once, and a Map is a collection that holds keys paired with values. Each comes in three kinds, whose names start with Hash, LinkedHash, and Tree, and the kind you choose determines the order in which things come out and which values can go in.

Checked against real execution · Checked by running 30 combinations on JDK 21

Concepts in this lab

List, Set, Map
These are the three basic kinds of Java collections. A List is ordered, allows duplicates, and is accessed by index. A Set does not allow duplicates. A Map stores key-value pairs, and its keys cannot be duplicated. You choose among them by the nature of the data (whether order is needed, whether duplicates are allowed, and whether you look things up by key).
Hash table and HashMap
This data structure decides the storage location (bucket) of a key from the value that a hash function produces for that key. The location can be computed directly from the key alone, so lookup, insertion, and removal are O(1) on average. Java's HashMap has this structure; it does not guarantee order and is not thread-safe.
LinkedHashSet and LinkedHashMap
Why it exists — HashSet and HashMap do not guarantee iteration order, so to take elements out in insertion order you had to keep a separate List to record the order. LinkedHashSet and LinkedHashMap maintain an order link along with the entries, so one collection gives both fast lookup and insertion order.
Where it's used today — You use them to make a list that must remove duplicates but keep the order in which items first appeared (search terms, tags). LinkedHashMap is also used to make a small cache that discards the least recently used entries first, by setting accessOrder to true and overriding removeEldestEntry.
These are a HashSet and a HashMap that remember insertion order. They put entries into a hash table in the same way, but they also maintain a linked list that connects the entries in insertion order, so iteration returns them in insertion order. Re-inserting an element or a key that is already present does not change the position where it was first inserted. Insertion and lookup are O(1) on average, the same as HashMap, and maintaining the linked list takes a little more memory. They are used for lists that must be shown in insertion order.
TreeSet and TreeMap
Why it exists — To see the values put in a HashMap in order, you have to sort separately every time you take them out, and to pick only those at or above some value, you have to scan them all. TreeSet and TreeMap decide the position on each insertion and always keep the elements sorted, so taking elements out in order and searching a range can be done directly.
Where it's used today — You use them to show records by date in time order, or to find, with floorKey, "the largest threshold that is at or below this score" in a table of score bands. If order is not needed, you use the faster HashMap and HashSet.
These are a Set and a Map that always keep their elements (for TreeMap, the keys) in sorted order. Internally each is a red-black tree, and on every insertion the position is decided by comparing with compareTo (or with the Comparator given to the constructor), so iteration returns the smallest first. Insertion, lookup, and removal are all O(log n), which is slower than HashMap, but the smallest value or the range of values greater than or equal to some value can be obtained directly. If no Comparator was given, or the given Comparator does not permit null, inserting null throws a NullPointerException. If no Comparator was given, inserting an object that does not implement Comparable throws a ClassCastException. Whether two values are the same is decided by whether the comparison result is 0, not by equals.
Time complexity (big-O notation)
Why it exists — If you measure running time in seconds, the value differs by computer and by input, so it is hard to say which of two approaches is better. Big-O notation drops constants and small terms and keeps only the shape of the growth as the input gets larger, so it lets you compare approaches regardless of the environment.
Where it's used today — It is used when choosing a data structure (contains is O(n) for ArrayList and O(1) on average for HashSet), when judging whether a double loop can withstand growing data, and when estimating whether a solution will finish in time in a coding test.
This notation shows how fast the number of operations of an algorithm grows as the input size n grows. O(1) means constant regardless of size, O(log n) means only one more step when the size doubles, O(n) means proportional to the size, and O(n²) means proportional to the square of the size. It is the basis for judging which approach holds up as the amount of data grows.

Try these

  • Default settings — Strings are added to a HashSet. They come out in an order that is neither the insertion order nor the sorted order.
  • LinkedHashSet — The values come out in insertion order.
  • TreeSet — The values come out in sorted order.
  • Small integers in a HashSet — It looks as if the set sorted them. Change the values to 40, 5, 17, 5, 100 and compare.
  • null in a TreeSet — null cannot be compared, so a NullPointerException is thrown.
  • Objects of your own class in a TreeSet — An object that does not implement Comparable causes a ClassCastException.
  • The same key again in a LinkedHashMap — Only the value changes, and the position stays where the key was first inserted.

Running with the default settings

  1. Set<String> set = new HashSet<>(): Creates an empty HashSet. HashSet uses hashCode to compute a bucket number for each element and stores it in that bucket. It does not keep track of insertion order.
  2. set.add("grape"): "grape" gets bucket number 11, which is computed from its hashCode. Iteration starts from the lowest bucket number, so the order is now grape.
  3. set.add("apple"): "apple" gets bucket number 1, which is computed from its hashCode. Iteration starts from the lowest bucket number, so the order is now apple, grape.
  4. set.add("date"): "date" gets bucket number 0, which is computed from its hashCode. Iteration starts from the lowest bucket number, so the order is now date, apple, grape.
  5. set.add("apple"): The same element is already in the set. A Set cannot contain duplicate elements, so add does not add it and returns false, and that false is printed. The size stays at 3.
  6. set.add("fig"): "fig" gets bucket number 5, which is computed from its hashCode. Iteration starts from the lowest bucket number, so the order is now date, apple, fig, grape.
  7. System.out.println(set): Prints the elements by going through them one after another from the start (iteration). HashSet iterates starting from the bucket with the lowest number. This is neither the insertion order (grape, apple, date, fig) nor the sorted order (apple, date, fig, grape). The output is [date, apple, fig, grape].
  8. System.out.println(set.size()): The code adds five times, but one element was a duplicate and did not go in again, so the size is 4.

Result of this run

  • The iteration order of HashSet and HashMap is the order of the bucket numbers that hashCode determines. To a person it looks scrambled, and it can change with the Java version or with the number of entries, so do not write code that relies on this order.
  • How to choose: the Hash kind if you do not need any order (the fastest), the LinkedHash kind if you need insertion order, and the Tree kind if you need sorted order.

Code

// Only the lines inside main are shown (class, main declaration, and imports omitted)
Set<String> set = new HashSet<>();
set.add("grape");
set.add("apple");
set.add("date");
System.out.println(set.add("apple"));   // adds a value that is already present
set.add("fig");

System.out.println(set);                   // iterates from the start and prints
System.out.println(set.size());

Assumptions of this model

The output, the size, the value returned when a duplicate is added, and the type of exception were checked for all 30 combinations against the result of running the same code on JDK 21 in our test environment. The bucket numbers of HashSet and HashMap were also checked against values read from the internal array of real objects. However, the Java specification does not guarantee the iteration order of the Hash kind. The order shown here is the one on JDK 21 with 16 buckets (12 elements or fewer), and it can change with a different version or a different number of elements. The specific value that the hashCode of a record returns is not specified either, and on JDK 21 the hashCode of Task(int id) was equal to id. A TreeSet decides whether two values are the same by whether the result of compareTo is 0, not by equals. The difference in performance (the Hash kind is faster than the Tree kind) was not measured, and the lab follows the time complexity stated in the documentation.
