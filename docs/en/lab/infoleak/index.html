Information leakage

What do error responses and login failure messages tell the outside world?

Why it exists — If every controller builds its own error response with try-catch, it is easy for one of them to make the mistake of sending out the exception message as it is, and the shape of the responses also becomes inconsistent. @ControllerAdvice and @ExceptionHandler let you receive the exceptions raised in many controllers in one place and decide what to send as the response, so the details go to the log, and only a short message and a status code decided in advance go outside.

Where it's used today — In a REST API, it is used to return an error body of the same shape for each kind of exception, such as 400 for a validation failure, 404 for a missing resource, and 500 for an unexpected error. A login failure message also does not tell a nonexistent ID from a wrong password, and by default Spring Security converts a nonexistent ID into the same BadCredentialsException as a wrong password and reports it.

The response a server returns when something fails can carry more than you might expect. An SQL statement inside an exception message, or the class names and line numbers inside a stack trace, show what the inside of the server looks like and give an attacker clues. If a login failure message tells "unknown user ID" apart from "wrong password", it also tells which IDs are registered.

Checked against real execution · Checked against the actual responses of a Spring Boot 4.1.1 (Spring Security 7.1.1) server for 20 combinations. What was compared is which items are in the response and whether the two responses are the same, not the message texts

Concepts in this lab

Error responses and information leakage
Information leakage through error responses is when the response a server returns on failure carries information from inside the server and sends it outside. An exception message can contain the SQL that was about to run or a file path, and a stack trace shows the framework in use and the structure of the code, so they give an attacker clues for the next attempt. The default error response of Spring Boot does not include the exception message or the stack trace. Information leaks when a setting is changed to always or when code puts the exception message into the response as it is. The basic rule is to put only a fixed message and an error ID in the response and to keep the details in the server log.
Stack trace
Why it exists — One line of an exception message cannot tell you in which method and through which calls the problem occurred. A stack trace leaves that order of calls, down to line numbers, so that you can find the place of the problem without running it again.
Where it's used today — When writing a log, if you pass the exception object as the last argument, as in log.error("Order failed", e), it is recorded together. For an error that occurred in production, you find the cause by looking at this record.
A stack trace is a record of which methods were being called, and in what order, at the moment an exception occurred. The first line has the class name and the message of the exception, and below it comes one line per method with the class name, method name, file name, and line number. If another exception was the cause, it is added with Caused by. It is the first thing a developer looks at to find the cause of an error. Because it shows the inner structure of a program in such detail, it is not put in the response to the user and is kept only in the log.
Account enumeration
Account enumeration is finding out which user IDs or email addresses are registered by using differences in the server's responses. If the login failure message tells "unknown user ID" apart from "wrong password", or if the sign-up and password recovery screens reveal whether an account exists, an attacker can request with different IDs and build a list of registered IDs. That list becomes the target of password guessing or of deceptive emails. To prevent it, make the responses for the two cases the same, down to the message and the status code, and reduce the difference in response time too. Spring Security by default treats the two cases as the same exception.
@ControllerAdvice and @ExceptionHandler
Where it's used today — With @RestControllerAdvice, you decide the status code and error body for each exception, such as 400 for an input validation failure (MethodArgumentNotValidException) and 404 when the requested resource does not exist. The error body is sometimes made to follow the standard format with Spring's ProblemDetail.
This feature lets you handle the exceptions raised in several controllers in one place. If you put an @ExceptionHandler method for each kind of exception inside an @ControllerAdvice class, an exception raised while a controller runs is passed to that method, which can build an error response in a consistent format.
HTTP status codes
Why it exists — If results were reported only as text in the body, each server would write them differently, and browsers, proxies, and monitoring tools could not tell whether a request succeeded. A status code reports the result as a fixed number, so these tools can do caching, retries, and error counting without being adjusted for each server.
Where it's used today — It is used to branch handling by the kind of error, such as a frontend that sends the user to the login screen on a 401 and to a "page not found" notice on a 404. In operations, you watch the ratio of 5xx responses and, if it suddenly rises, treat it as an outage and send an alert.
A three-digit number that shows the result of the server's handling of a request. 2xx means success, 3xx means a move to another location (redirection), 4xx means a problem with the client's request, and 5xx means an error on the server side. Common ones are 200 (success), 201 (created), 400 (bad request), 401 (authentication required), 403 (no permission), 404 (not found), and 500 (server error).

Try these

  • Default settings — A server where both settings are always, to make development easier. The SQL and the stack trace go into the response.
  • Spring Boot defaults — Both are never. Only the fact that an error happened goes out.
  • on_param with ?trace=true — Anyone can add the parameter, so the trace is not hidden.
  • Exception message sent as it is — Even with default settings, information leaks if the code sends it out itself.
  • Only a fixed message and an error ID — The details are kept only in the server's log.
  • If the login failure messages differ — They tell whether the user ID is registered.
  • Login with the Spring Security default — The responses for an unknown user ID and for a wrong password are the same.

Running with the default settings

  1. A GET /orders/7 request arrives. It is an ordinary request to look up order 7.
  2. jdbc.queryForMap(SQL, id): the column name price is misspelled as pirce in the SQL. The database rejects the SQL, and Spring converts that into a BadSqlGrammarException and throws it. The message of this exception contains the whole SQL statement that was about to run.
  3. No code catches the exception, so the request is forwarded to /error, and the BasicErrorController of Spring Boot builds the error response. The items included regardless of the settings are timestamp, status, error, and path. Up to here, the response only says that "an error happened".
  4. include-message=always: the exception message is put in the message item. The SQL statement goes into the response as it is, and the table name (orders) and the column names (id, item) are exposed.
  5. include-stacktrace=always: the stack trace is put in the trace item. The first line has the class name of the exception and its message (including the SQL), and below it the methods the exception passed through are listed with their class names and line numbers. The class name of the database driver (org.h2…) also shows which database is used.
  6. The server sends a 500 response. The items in the body are timestamp, status, error, trace, message, path. Whoever sent the request can read the SQL statement, class names and line numbers, database product name.

Result of this run

  • A stack trace reveals the most. It shows the framework and database in use and the class names and structure of your code, and its first line contains the exception message, so the SQL goes out too even if include-message is never.
  • This information alone does not break into the server, but the more an attacker learns about table and column names, the products in use, and the structure of the code, the more precisely the next attempt can be aimed.

Code

# application.properties
spring.web.error.include-message=always
spring.web.error.include-stacktrace=always

// Order lookup. A column name in the SQL is wrong (price is written as pirce) (controller class declaration, jdbc field, and imports omitted)
@GetMapping("/orders/{id}")
public Map<String, Object> order(@PathVariable long id) {
    return jdbc.queryForMap(
        "select id, item, pirce from orders where id = ?", id);
}

// Request: GET /orders/7

Assumptions of this model

12 error responses (2 message settings × 3 stack trace settings × whether the trace parameter is present), 2 responses built by hand, and 6 login failures were checked against the actual responses of a Spring Boot 4.1.1 (Spring Security 7.1.1, Spring JDBC, H2) server started on 127.0.0.1. The message texts and the number of stack trace lines vary with the version and the environment, so what was checked is which items are in the body, whether the SQL statement, the stack trace lines, and the name of the database driver are visible in the body, whether the two login failure responses are the same, which exception occurred, and how many times the password comparison was called. The message values on screen are the ones seen in this test run, and the example errorId is a made-up value. The checks were based on requests that receive JSON; for a request that receives HTML, as a browser does, the same content appearing on the error page was confirmed for one setting. The setting names are the spring.web.error.* names of Spring Boot 4.1.1 (server.error.* up to Spring Boot 3). include-exception, include-binding-errors, and the on_param value of message are not covered. That the whole exception is written to the log in the safe response was confirmed by collecting the log output. Not run: the difference in response time was not measured (only the number of times the password comparison was called was checked), and the messages on the sign-up and password recovery screens are an explanation that follows the authentication guidance of OWASP. How much the leaked information helps in a real attack differs from server to server.
