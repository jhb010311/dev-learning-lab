TLS handshake

What happens before the https padlock locks

Why it exists — If only HTTP is used, anyone on the same Wi-Fi or passing through an intermediate device can read or swap passwords and cookies as they are, and there is no way to know whether the other party is really that site. TLS adds one more encryption layer under HTTP, so that without changing application code, the content going back and forth cannot be snooped on or altered, and the identity of the other server is vouched for by a certificate.

Where it's used today — Not only login and payment screens: now most websites and app API calls go over https. Browsers use HTTP/2 only over https, and TLS is sometimes turned on for calls between servers and for DB connections too. Rather than putting the certificate on the Spring server directly, it is common for nginx or a load balancer in front to handle TLS and for the servers behind to receive HTTP.

HTTPS is HTTP wrapped in TLS. Before any data is sent, the browser and the server check that "the other side really is that server" and create "an encryption key that only the two of them know".

Checked against real execution · Checked by making real TLS 1.3 connections with openssl

Concepts in this lab

HTTPS and TLS
HTTPS is HTTP communication encrypted with TLS. TLS keeps third parties from seeing the content (confidentiality), keeps it from being changed on the way (integrity), and uses a certificate to check that the server you connected to is the real one (authentication). SSL is the protocol that came before TLS. It is now deprecated and only TLS is actually used, but the name SSL is still used alongside it by habit.
TLS handshake and certificates
Why it exists — If you only encrypt and do not verify the other side, you end up in an encrypted conversation even with a fake server that has put itself in the middle. The TLS handshake and certificates let two parties who have not shared a key beforehand meet for the first time and agree on a key, while also verifying that the other side is the owner of that domain.
Where it's used today — A server operator gets a certificate from a certificate authority such as Let's Encrypt, installs it on a web server or load balancer, and renews it before it expires. Between internal services, calls are sometimes protected with mTLS, in which both sides verify each other's certificates.
The TLS handshake is the process, before encrypted communication starts, in which the client and the server agree on the cryptographic algorithms to use, verify the identity of the server, and agree on the keys that will encrypt the data. A certificate is a document that contains the server's public key and domain information and is signed and vouched for by a trusted certificate authority (CA). The client validates it to confirm that the server it connected to is the real one.
Symmetric-key cryptography and public-key cryptography
Where it's used today — In HTTPS (TLS), public-key cryptography is used when the connection is set up, to verify the signature of the server certificate and to exchange keys, and the HTTP data that follows is encrypted with a symmetric key such as AES. Values stored in a database, such as card numbers, are encrypted with a symmetric key, and the key pair used for SSH login is a public-key one.
Symmetric-key cryptography uses the same key to encrypt and to decrypt. It is fast, but it has the problem that the key must be shared safely with the other party (AES). Public-key cryptography uses a pair of keys, a public key and a private key. Data encrypted with the public key can be decrypted only with the private key, so there is no key-sharing problem, but it is slow (RSA). In practice, public-key cryptography is used to exchange a symmetric key safely, and then the symmetric key encrypts the data.
HMAC and digital signatures
Why it exists — If you send only a hash value, someone in the middle can change the content, compute a new hash, and attach it, so the forgery cannot be noticed. HMAC and digital signatures attach a value that can be created only with a key, so the receiving side can tell apart a message modified by a party that does not have the key.
Where it's used today — They are used for the signature of a JWT (HS256 is HMAC, RS256 is a digital signature), for signatures sent in a request header as with GitHub webhooks, and for verifying HTTPS certificates.
Techniques for confirming that a message was not changed on the way and that the legitimate party sent it. HMAC hashes the message together with a secret key that both sides share to produce an authentication code. With a digital signature, the sender signs with a private key and the receiver verifies with the public key. Only the signer can create the signature, so the sender cannot deny having sent the message.

Try these

  • Default settings — A normal TLS 1.3 handshake.
  • If the certificate has expired — The browser shows a warning and stops the connection.
  • If the domain is different — The certificate is genuine, but it does not belong to this server.
  • Self-signed certificate — A certificate that no one vouches for.

Running with the default settings

  1. The browser connects to https://shop.example. After the TCP connection is established, it sends the list of cipher suites it can use and a public value (key share) to be used for the key exchange. This message is not encrypted.
  2. The server picks one cipher suite and sends its own public value for the key exchange. Each side combines the other side's public value with its own secret value and computes the same result. Someone who only watched the public values in the middle cannot compute this result.
  3. Each side derives a symmetric key from this result. The key itself was never sent over the network. The handshake messages from here on are encrypted.
  4. The server sends its certificate. The certificate contains the domain name, the server's public key, the validity period, and a signature over this content. A website's certificate is usually signed by a certificate authority (CA) with its own private key.
  5. The browser validates the certificate. The signature comes from a trusted certificate authority, the certificate is within its validity period, and the domain matches shop.example. You can trust that this public key belongs to the real shop.example.
  6. The server signs everything exchanged so far with its private key and sends the signature. The browser checks this signature with the public key in the certificate. Anyone can copy a certificate, but only the real server that holds the matching private key can create the signature.
  7. Both sides exchange a verification value over the entire handshake, to check that no one changed a message in the middle.
  8. Now the HTTP request and the response travel encrypted with the agreed symmetric key. Someone watching in the middle can see only roughly which server you are talking to, and cannot see the content (the path of the address, the headers, cookies, and the body).

Result of this run

  • Public-key cryptography (a public key and a private key) is used only for the signatures that confirm the other side is genuine and for agreeing on a key safely. The reason is that its computation is slow. The actual data is encrypted with the fast symmetric key. The two methods share the work, each doing what it is good at.
  • TLS 1.3 completes this process in one round trip (earlier versions need two). Even so, every connection has a cost, so it is important to reuse a connection once it has been made.

Code

# application.yml (server-side settings)
server:
  port: 443
  ssl:
    enabled: true
    key-store: classpath:shop.p12       # certificate + private key
    key-store-password: "********"     # hidden here
    protocol: TLS
    enabled-protocols: TLSv1.3

# In production, a load balancer or nginx in front usually handles TLS,
# and the application server receives plain HTTP behind it

Assumptions of this model

This simplifies the basic TLS 1.3 handshake (in a real handshake, several of the server's reply messages are sent bundled together). The key exchange is the kind in which both sides exchange public values and compute the same secret (ECDHE); it does not encrypt a symmetric key with the server's public key and send it, as the older method did. The certificate checks follow the standard procedure of TLS and the web PKI. In our test run, openssl was used to create a test certificate authority and four kinds of certificate, and real TLS 1.3 connections were made with them to check. The valid certificate passed validation, and each of the others was rejected with the error certificate has expired, hostname mismatch, or self-signed certificate. It was also confirmed that the handshake messages are exchanged in the order ClientHello, ServerHello, EncryptedExtensions, Certificate, CertificateVerify, Finished.
