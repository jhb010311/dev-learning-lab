Sequential and parallel calls

Several external calls: one after another, or all at once?

Why it exists — If several unrelated external calls are made one after another, the waiting times of all the calls add up. Creating threads directly or waiting for each with Future.get makes collecting results and handling exceptions troublesome. CompletableFuture lets you start several tasks at the same time and lets you combine results and decide the substitute value for failure or timeout by chaining methods.

Where it's used today — It is used when building one screen, such as a product detail page or a user's account page, requires calling several services together, such as member, stock, and reviews. allOf waits for all of them to finish, and completeOnTimeout replaces a late call with a default value. If no thread pool is passed to supplyAsync, it usually runs in the shared ForkJoinPool, so for tasks that wait, such as external calls, it is usual to specify a dedicated thread pool.

To build a single product detail page, the application calls several services. If it calls them one after another, all the times add up. If it calls them at the same time, the page takes only as long as the slowest call.

Checked against real execution · Checked by running code on JDK 21

Concepts in this lab

CompletableFuture
This object represents the result of an asynchronous task. You can attach actions that run next when the task finishes, and you can combine the results of several asynchronous tasks. The flow is built in the style of "when it finishes, do this", so no thread is stopped while waiting for the result.
Synchronous and asynchronous
Why it exists — If every call is synchronous, you must wait for even a task that takes long but whose result is not needed right away, such as sending an email, so the response becomes slow. The asynchronous approach hands off the work, moves on to the next thing first, and receives the result later.
Where it's used today — A call whose result decides the next step, such as payment approval, is made synchronously, and work that may finish later, such as sending a notification or aggregating statistics, is handled asynchronously with a message queue or @Async.
Synchronous means that the side that requests a task waits until it receives the result and only then moves on. Asynchronous means that the requester starts the task and moves on to the next work without waiting for the result, and the result is delivered later through a callback, a Future, or a similar means.
Thread pool
This structure keeps a fixed number of threads and reuses them, so that threads are not created and destroyed every time they are needed. It reduces the cost of creating threads, and by limiting the number of threads that run at the same time, it prevents excessive memory use and context switching. Tasks to be processed pile up in a queue, and an idle thread takes one and runs it. Tomcat's request handling and a DB connection pool follow the same idea.
ForkJoinPool and the common pool
Why it exists — If you split a large task into small pieces and give them to several threads, the threads finish at different times, and a thread that finishes first sits idle. ForkJoinPool gives each thread its own queue of tasks and lets a thread with nothing to do take tasks from another thread's queue (work stealing), so the work is divided evenly.
Where it's used today — It is used when a large CPU-only computation is spread over several cores, as with Arrays.parallelSort and parallel streams. Tasks that wait for a database or an external API are run on a separately created ExecutorService so that they do not hold on to the common pool.
This is a thread pool used to split a large task into small tasks, process them on several threads, and combine the results. The JVM has a common pool (commonPool) that everything shares, and parallel streams run in it by default. If you run a long task there, other tasks that use the same pool also slow down.

Try these

  • Default settings — The 4 services are called one after another. All the times add up.
  • Switch to parallel — The page takes only as long as the single slowest call.
  • Parallel, but with only 2 threads — Only 2 calls are in progress at a time.
  • A timeout on the slow call — A call that takes longer than 1s is not waited for. A default value is used in its place.
  • 5 calls, sequential — Each additional call makes the page slower by the time of that call.

Running with the default settings

  1. 0.0s: The call to Product details starts (a call that takes 0.3s).
  2. 0.3s: The call to Product details receives its response.
  3. 0.3s: The call to Stock starts (a call that takes 0.5s).
  4. 0.8s: The call to Stock receives its response.
  5. 0.8s: The call to Reviews starts (a call that takes 0.8s).
  6. 1.6s: The call to Reviews receives its response.
  7. 1.6s: The call to Recommendations starts (a call that takes 1.6s).
  8. 3.2s: The call to Recommendations receives its response.
  9. 3.2s: All the results have arrived. The application assembles the page and responds.

Result of this run

  • With sequential calls, the response time is the sum of all the call times. If the calls do not depend on each other's results, there is no reason to make them one after another.

Code

// Only the lines inside the method are shown (class, method declaration, imports, and the example productApi, ProductPage, etc. omitted)
var product = productApi.get(id);
var stock = stockApi.get(id);
var reviews = reviewApi.list(id);
var recommend = recommendApi.list(id);

return new ProductPage(product, stock, reviews, recommend);

Assumptions of this model

The time each call takes (product details 0.3s, stock 0.5s, reviews 0.8s, recommendations 1.6s, coupons 0.4s) is a fixed example, and the model assumes that the calls do not need each other's results. If the result of one call is the input of the next, those two must be made sequentially. For parallel calls, the model assumes blocking calls, in which one thread makes one call and waits for it. completeOnTimeout is a method that has existed since JDK 9. This was checked by actually running code on JDK 21 in our test environment. With 4 calls of the same durations, the measured times were 3,243ms sequential, 1,603ms parallel (5 threads), 2,127ms parallel (2 threads), and 1,011ms with the timeout of 1s applied, which matched the values of the model (3.2s, 1.6s, 2.1s, 1.0s).
