HTTP responses

What does an HTTP response look like as text?

Why it exists — If the shape of responses differed from server to server, a browser would have to work out separately for each server where the part that reports the result ends and where the content begins. The fixed shape of an HTTP response has everyone follow the order of a status code on the first line, headers below it, and the body after a blank line, so that an answer sent by any server is read the same way.

Where it's used today — When a browser receives a web page or an app fetches data from a server, every answer that comes has a status code and headers, and usually a body follows. When a Spring controller returns a value, Spring and Tomcat attach the status code and headers to make the response. During development, you can see the status code and headers directly in the Network tab of the browser's developer tools.

The HTTP response that a server sends back in answer to a request is also a few lines of text in a fixed shape. The first line (the status line) holds the version, the status code (a three-digit number like 200 or 404), and a short description. Below it come lines called headers, in the form "name: value", and after an empty line, a line with no text at all, comes the body (the actual content). The client (the browser) learns from the status code what happened to the request, from the Content-Type header what kind of content the body is, and from the Content-Length header how many bytes the body is. In this lab you change or remove the status line, the Content-Type line, and the Content-Length line one at a time, send that text exactly as it is to the client, and see what the client reads out of it. The (empty line) in the code box is a way to show a line with no text at all, so that you can see it.

Concepts in this lab

Status line
The status line is the very first line of an HTTP response, and it holds the HTTP version, the status code, and a short description in order, separated by spaces. For example, HTTP/1.1 200 OK means that the text is written by the rules of HTTP/1.1, the result of the request is 200, and the description that people read is OK. The status code is a three-digit number that tells what happened to the request, and the description is only text for people (RFC 9112 section 4). The client reads from this line, so if a response does not start with a status line, the client cannot read that text as an HTTP response.
HTTP status codes
Why it exists — If results were reported only as text in the body, each server would write them differently, and browsers, proxies, and monitoring tools could not tell whether a request succeeded. A status code reports the result as a fixed number, so these tools can do caching, retries, and error counting without being adjusted for each server.
Where it's used today — It is used to branch handling by the kind of error, such as a frontend that sends the user to the login screen on a 401 and to a "page not found" notice on a 404. In operations, you watch the ratio of 5xx responses and, if it suddenly rises, treat it as an outage and send an alert.
A three-digit number that shows the result of the server's handling of a request. 2xx means success, 3xx means a move to another location (redirection), 4xx means a problem with the client's request, and 5xx means an error on the server side. Common ones are 200 (success), 201 (created), 400 (bad request), 401 (authentication required), 403 (no permission), 404 (not found), and 500 (server error).
Content-Type header
Why it exists — A body is just bytes, so if its kind is not announced, the receiver has to guess from the content, and a wrong guess garbles Korean text or makes it look wrong. The Content-Type header lets the sender tell the kind and the encoding directly.
Where it's used today — When a REST controller in Spring returns an object, Spring converts it to JSON text and adds Content-Type as application/json. In the opposite direction, when you send JSON to the server, you must add this header too, so that Spring reads the body as JSON.
Content-Type is a header that tells what kind of content the body of a response is, and it is written like text/plain; charset=utf-8. The text/plain at the front is the kind (the media type), plain text, and charset=utf-8 is the character encoding the text is written in. The client looks at this value to decide whether to show the body as text or to handle it as a picture or another format. RFC 9110 section 8.3 says that when this header is missing, the receiver may assume the kind is application/octet-stream or may examine the data to decide it.
Content-Length header
Why it exists — Without an indication of the length of the body, the end can be signaled only by closing the connection, so a new connection has to be made for every response. Content-Length announces the length in advance, so that the next request and response can follow one after another over the connection kept open.
Where it's used today — A browser uses this value to show what percent of a file has been downloaded. A response whose length is not known in advance is sent instead with Transfer-Encoding: chunked, with a length attached to each chunk.
Content-Length is a header that tells the size of the body of a response as a number of bytes. The client uses this number to decide how far the body extends among the text that follows the headers (RFC 9112 section 6.2). It is a number of bytes, not a number of characters, so a Korean letter, which takes 3 bytes in UTF-8, counts as three times as many as the number of letters. A response that has neither Content-Length nor any other length indication takes the bytes received before the server closes the connection as the body (RFC 9112 section 6.3). So in this case a server that does not close the connection cannot tell where the body ends.

Try these

  • Default settings — A response with the right shape. The client reads the status, the kind of body, and the body.
  • Changing the status code to 404 — Only the status is read as 404, and the body is read as it is.
  • Removing the Content-Type line — The body is read, but there is no header that says the kind of the body.
  • Writing Content-Length shorter than the body — Only the 5 bytes written are read as the body, so the text is cut off.
  • Removing the Content-Length line — There is no length information, so all the text received until the connection closes becomes the body.
  • Removing the first line (the status line) — It is not read as a response. It does not help even if the headers and body are right.

Running with the default settings

  1. The browser sends a GET /hello request to the server, and the server answers by sending back the text below. This text is the HTTP response. The server in this lab sends the text in the code box exactly as it is, and closes the connection when it is done. The client that reads the response is the http module of Node.js.
  2. The client reads the first line. The text it read is "HTTP/1.1 200 OK". The first line (the status line) has three things written in order. HTTP/1.1 is the rules the text was written by (the version), the 200 part is a three-digit number that tells what happened to the request (the status code), and OK is a short description that puts that code into words for people to read. 200 means the request was handled well. The status the client read is "200 OK".
  3. The client reads the next line. The text it read is "Content-Type: text/plain; charset=utf-8". A line in the form "name: value" is called a header. The Content-Type header tells what kind of content the body is. text/plain means plain text, and charset=utf-8 means that the text is written in UTF-8.
  4. The client reads the next line. The text it read is "Content-Length: 12". The Content-Length header tells how many bytes the body is, and the client uses this number to decide where the body ends. A byte is the unit used to count the size of data (it can differ from the number of characters). In UTF-8, each of the 12 characters of "Hello, world" is 1 byte, so the body is 12 bytes.
  5. The client reads the next line and finds an empty line with no text at all (the (empty line) on the screen). An empty line marks the end of the headers, and the text from the next character on is the body.
  6. The client reads as the body as many bytes as Content-Length says, 12 bytes. The text it read is "Hello, world", and the body ends exactly here. This number is how the client knows where the body ends.
  7. The client has finished reading the response. What it read is the status "200 OK", the kind of body "text/plain; charset=utf-8", and the body "Hello, world".

Result of this run

  • An HTTP response is a few lines of text that the server sends back. The first line (the status line) holds the version, the status code, and a short description, below it are headers in the form "name: value", and the body follows an empty line.
  • From the status code 200 the client learned that the request was handled well, from Content-Type that the body is text/plain, and from Content-Length that the body is 12 bytes, and it read the body. The body it read is "Hello, world".

Assumptions of this model

The server is one started with the net module of Node.js 24.18.0. When a connection comes, it reads the request up to the empty line, then writes the text of the code box exactly as it is, with CRLF line endings, and closes the connection (a response made with the http module cannot send a wrongly shaped one, so it was not used). Nothing is attached after the body "Hello, world", and this text is 12 bytes in UTF-8 and the first part, "Hello", is 5 bytes, which was measured to confirm. The client sent a GET /hello request with the http module of Node.js (a real HTTP parser) and read the response. All 18 combinations were run, and the status the client read (the status code and description), the value of the content-type header it received, and the body it actually received with its number of bytes were checked against the model. For each combination it was also checked that the code on the screen is the same text as the text the server sent. When Content-Length was 5, this client received only the first 5 bytes ("Hello") as the body, and then raised one parse error (HPE_INVALID_CONSTANT) while reading the remaining 7 bytes. All 6 combinations without a status line failed to read the response with the same parse error (HPE_INVALID_CONSTANT, with the message Expected HTTP/, RTSP/ or ICE/), whatever the headers and body were. These are behaviors observed on this Node.js version. When there is no Content-Length, this server closes the connection after sending, so the client read everything until the connection closed as the body. A server that does not close the connection is not covered on the screen, but as a separate check, the same text was sent to a server that does not close the connection, and the client received the 12 bytes of the body, but the response had not ended even after 1.5 seconds (when Content-Length was present, it ended right away even without closing the connection). What happens when it waits longer, or with another client, was not examined. How a browser guesses and shows a body without Content-Type was not checked in this lab. What was checked against the documentation is RFC 9112 section 2.1 (message format: start line, headers, empty line, body), section 4 (the status line: version, three-digit status code, description), sections 6.2 and 6.3 (Content-Length sets the number of bytes of the body, and for a response with no length information, the length of the body is the number of bytes received before the server closes the connection), and RFC 9110 section 8.3 (Content-Type tells the media type of the body, and without it the receiver may assume application/octet-stream or examine the data to decide the kind), section 8.6 (Content-Length), section 15 (a status code is a three-digit number), section 15.3.1 (200), and section 15.5.5 (404). The response on the screen has the minimum shape, with only two headers left, and only GET responses whose body is text were covered. Writing the line endings of the text the server sent as CRLF, and using Node.js as the client, are choices of this lab, and a browser was not used. The in-depth details on the same subject (the shape of requests and responses, all the status codes) are covered in the in-depth lab "HTTP messages and status codes".
