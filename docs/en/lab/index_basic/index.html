Indexes

What is an index, and what changes when there is none?

Why it exists — When there are only a few rows, scanning from beginning to end finishes quickly, but when there are millions of members, even finding one person is slow because every row is read. If many such lookups come in at once, the whole database slows down. An index keeps a separate list in which values are arranged in advance, so that the time to find does not grow much even as rows increase.

Where it's used today — Create it on columns that are often used in the condition of WHERE or a join, such as the email used at login or the member number used to see an order list. Most databases create one automatically on columns with a primary key or UNIQUE. The more indexes you make, the slower inserting or deleting rows becomes, so you do not create them even on columns that are not searched often.

An index is a list that keeps the values of a column in order and points to the rows that hold each value. The database builds it separately from the table, and it works like the index at the back of a book. CREATE INDEX idx_name ON member(name) is the statement that builds an index on the name column. Without an index, the database has to read the rows of the table from the first to the last to find the rows that match a condition. With an index, it looks up the value in the index and reads only the rows it needs. In this lab, you remove CREATE INDEX or change the column you search by, run the same SELECT, and see how the number of rows the database reads changes even though the rows it finds stay the same. This lab does not cover how an index organizes its values or what it costs to build one.

Concepts in this lab

Index
A data structure that keeps the values of specific columns separately, in sorted form, so that the wanted rows of a table can be found quickly. Without one, the whole table must be read to find the rows that match a condition. Reads get faster, but it must also be updated every time data is inserted, updated, or deleted, so it costs write performance and storage space.
CREATE INDEX
Why it exists — When you create a table, it is hard to know in advance which columns you will often search by. CREATE INDEX lets you add an index later, even to a table that already has data, without recreating the table.
Where it's used today — When you find a slow query while running a service, you add an index with this statement to the column used in its condition. If there are very many rows, building an index takes time, so it is sometimes run at a time when there are few users.
CREATE INDEX is the SQL statement that adds an index to a column of a table that already exists, in the form CREATE INDEX index_name ON table(column). For example, CREATE INDEX idx_name ON member(name) builds an index on the values of the name column of the member table. The index is stored separately from the table and does not change the rows of the table. An index is used mainly when you search by the column it was built on, so to search by another column quickly, that column needs an index of its own (without one the search still works, but it scans everything). The database builds an index automatically on a column with PRIMARY KEY, so you do not need CREATE INDEX for it (in MySQL, the primary key itself is created not with CREATE INDEX but with CREATE TABLE or ALTER TABLE).
Full table scan
A way of finding the rows that match a condition by reading every row of the table from beginning to end. It is chosen when no index can be used for the condition, or when an index exists but the optimizer judges that reading everything is better because too many rows match the condition. When it is used to find a few rows in a large table, it causes performance problems.
Query execution plan (EXPLAIN)
The plan that the database decides on for how to run a query. It shows which indexes are used, in what order the tables are joined, and how many rows the database expects to read. You view it by putting EXPLAIN in front of the query, and it is the starting point for finding the cause when a query is slow.

Try these

  • Default settings — A table with an index on name. The database looks up user777 in the index and reads only that 1 row.
  • Removing CREATE INDEX — It finds the same 1 row, but the database reads all 1000 rows of the table.
  • Searching by a column with no index — idx_name is an index on the name values, so it is not used when you search by city, and the database reads all 1000 rows.
  • Searching by the primary key — You did not use CREATE INDEX, but the primary key already has an index, so the database reads only 1 row.

Running with the default settings

  1. CREATE TABLE: The database creates a table named member. It has three columns, id, name, and city, and for now it has no rows. PRIMARY KEY is written on the id column, so the database also builds an index for finding rows by id. An index is a list that keeps the values of a column in order and points to the rows that hold each value, and it works like the index at the back of a book. This index exists even if you do not use CREATE INDEX.
  2. Inserting 1000 members (1000 INSERT statements that the screen omits): The database inserts ids 1 to 1000, names user1 to user1000, and cities in turn from Seoul, Busan, Daegu, and Gwangju. The table now has 1000 rows, and each city has 250 rows.
  3. CREATE INDEX idx_name ON member(name): The database builds an index of the values of the name column in order, separately from the table. The index holds the name values (…, user776, user777, user778, …) and information that points to the row that has each value. The table still has 1000 rows. Building an index does not change the rows.
  4. SELECT * FROM member WHERE name = 'user777': The database first checks whether there is an index for the name column used in the condition. The name column has the index idx_name that CREATE INDEX built, so the database decides to search with this index.
  5. The database finds user777 in the name index and follows the information attached to that value straight to the row with id 777 in the table. It did not read the other 999 rows of the table. The database read 1 row.
  6. Result of the SELECT: It returns 1 row, the user777 row with id 777. If you run the same SELECT on a table without CREATE INDEX, it finds exactly the same row. The difference is that the database then reads 1000 rows.

Result of this run

  • An index is a list, built separately from the table, that keeps the values of a column in order and points to the rows that hold each value. Because the name index exists, the database went straight to the user777 row and read only 1 of the 1000 rows.
  • The rows found are exactly the same as without the index. What an index changes is not the result but the amount the database reads.

Code

CREATE TABLE member (
    id   INT PRIMARY KEY,
    name VARCHAR(20),
    city VARCHAR(20)
);
-- Insert 1000 members (user1 to user1000. The INSERT statements are omitted on the screen)

-- Index: build an index so that rows can be found quickly by the name value
CREATE INDEX idx_name ON member(name);

SELECT * FROM member WHERE name = 'user777';

Assumptions of this model

It was run and checked against H2 2.4.240 (in-memory database, JDBC). It ran all 6 combinations, and it ran the whole SQL on the screen, including the comment lines, exactly as written. At the "Insert 1000 members" comment line on the screen, the verification program inserted 1000 members (ids 1 to 1000, names user1 to user1000, and 250 members each for the cities Seoul, Busan, Daegu, and Gwangju, in turn), and the INSERT statements are omitted on the screen. What it checked is the number of rows the SELECT returned, how H2 EXPLAIN said it would search (the name index IDX_NAME, the primary key index PRIMARY_KEY, and tableScan with no index), the scanCount that EXPLAIN ANALYZE reported, and the facts that the step sentences rely on. The facts they rely on are that the index on the id column exists automatically right after CREATE TABLE, that CREATE INDEX built an index with the name column in order, that the table still has 1000 rows before and after CREATE INDEX, and that the SELECT returns the same rows with and without an index. The "Rows the database read" on the screen is scanCount minus 1. The H2 documentation does not define what scanCount means, and in this version the scanCount we observed is 1 more than the number of rows read (it looks like one more is added to confirm that there are no more rows to read). The evidence is this. When we read a table with 0, 10, and 1000 rows from start to finish, scanCount was 1, 11, and 1001. When we forced a full read by using a function that counts how many times it is called per row in the condition, the function was called 1000 times and scanCount was 1001. When we looked up a value that does not exist by an index, scanCount was 1, and for a value that exists, it was 2. Following this observation, the "1 row" for a search by index is also the value with 1 subtracted in the same way, and it equals the number of rows found. The database decides how to search by looking at the amount and distribution of the data, so on another database or with other data it may not use an index even if there is one. This is the result observed with this data in our test run (H2 2.4.240). We opened the H2 documentation, on the performance page, "How Data is Stored and How Indexes Work" (an index is like a table with the indexed columns and the row number) and "Statement Execution Plans (EXPLAIN)" (EXPLAIN ANALYZE shows the rows read, tableScan means that no index was used, and an index is created automatically for a primary key and a unique constraint), and checked against it. We opened the MySQL 8.4 documentation, section 10.3.1 How MySQL Uses Indexes (without an index, it has to read the whole table from the first row), section 15.1.15 CREATE INDEX Statement (it adds an index to an existing table), section 10.3.2 Primary Key Optimization (a primary key has an index attached), and the PRIMARY KEY item of the CREATE TABLE statement, and checked against them. However, we did not check against execution on MySQL. Also, this screen draws the index of the primary key as a box like the name index, but H2 and MySQL (InnoDB) use an integer primary key as the sort order of the table data itself, so the index of the primary key is not a list separate from the table like the name index. We did not cover the structure of an index (B-tree and so on), or the cost that comes from INSERT, UPDATE, and DELETE having to update the index as well when an index exists. The in-depth lab "Indexes and full table scans" covers them.
