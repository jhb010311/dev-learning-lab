Window functions

How do you add a rank and a running total without reducing the rows?

Why it exists — To give each row a rank without window functions, you had to join the table to itself or use a correlated subquery to count, for each row, "the number of rows with a higher score than mine", so the statement was long and got slower as rows increased. A window function lets you do the same calculation in one statement by writing only the partition criteria and the sort order in the OVER clause.

Where it's used today — You use it in reports and statistics that need a value compared with the surrounding rows for each row, such as the ranking of popular posts on a board, salary ranking by department, the running total of sales by date, and the change from the previous month. A condition such as "only the first of each team" is done by numbering with ROW_NUMBER and then filtering in an outer query. If you need only totals and do not need each row, use GROUP BY.

GROUP BY combines many rows into one row to compute a total. A window function leaves the rows as they are and adds one value, such as a rank or a running total, next to each row.

Concepts in this lab

Window function
This is a function that adds to each row a value computed by looking at several rows related to that row, without combining the rows. You write OVER (...) after the function to say which rows are laid out in which order for the calculation. Unlike GROUP BY, which reduces each group to one row of the result, the number of result rows stays the same, so you can see the original value of each row and its rank or running total on one line. In MySQL, window functions are available from version 8.0. They are allowed only in the select list and in ORDER BY, so to filter on the result of a window function, you wrap the query in a subquery.
ROW_NUMBER, RANK, DENSE_RANK
Where it's used today — ROW_NUMBER is used to split a list into pages or to keep only one of the rows with overlapping values, RANK when the rank after a tie must be left empty, as in a contest ranking, and DENSE_RANK when you count the rank of distinct values, as in "the top three score levels".
These are window functions that give rows a number or a rank in the order of the ORDER BY inside OVER. The difference among the three is how they handle rows with the same sort value (ties, which the MySQL documentation calls peers). ROW_NUMBER gives different numbers even to peers. RANK gives peers the same rank and then skips as many ranks (1, 1, 3), and DENSE_RANK gives peers the same rank without skipping (1, 1, 2). With ROW_NUMBER, which of the tied rows gets the lower number is not defined, so if the result must always be the same, add a column whose values are unique to the sort order.
PARTITION BY
Where it's used today — You use it when you must count separately "by something", such as a rank within each class, an order sequence number for each customer, and a running total of monthly sales for each product. If you add OVER (PARTITION BY customer-number-column) to an aggregate function such as SUM or COUNT, you can see that customer's order total together on every order row.
This is a clause you write inside the OVER of a window function to divide the rows into groups that have the same value in the columns you name. Each group is called a partition, and the numbers, ranks, and running totals are calculated again from the beginning for each partition. It looks similar to GROUP BY, but the difference is that it does not combine rows. If you do not write PARTITION BY, the whole result is one partition.
LAG and LEAD
Where it's used today — You use LAG when you compare with the immediately preceding row, such as the change in sales from the previous day or the time difference from the previous login, and LEAD when you need a following row, such as attaching the next visit date to find the number of days until the customer returned.
These are window functions that fetch the value of a row before or after the current row in an ordered line of rows. LAG fetches the value of the previous row, and LEAD fetches the value of the next row. They let you compare neighboring rows, such as the difference between yesterday and today, without joining the same table one more time. For the first row of a partition (LAG) or the last row (LEAD), where there is no row to fetch, the value is NULL.
GROUP BY, WHERE, HAVING
Why it exists — Without GROUP BY, you would have to bring every row into the application and count and add them yourself to get a total per group. GROUP BY and HAVING finish the grouping, counting, and filtering in the database, so the application receives only a few result rows.
Where it's used today — It is used in queries for statistics and admin screens, such as daily sales, the number of products per category, and finding members who have ordered more than three times.
GROUP BY groups rows that have the same value in the specified columns and computes an aggregate (such as a sum or a count) for each group. WHERE filters individual rows before they are grouped, and HAVING filters groups after grouping. So put conditions on aggregate results in HAVING and all other conditions in WHERE.

Try these

  • Default settings — RANK. If two people have 90 points, both are ranked 1 and there is no rank 2.
  • Switching to DENSE_RANK — The rank after a tie is not skipped.
  • Switching to ROW_NUMBER — The numbers do not repeat, even for a tie.
  • Compare with GROUP BY — The 6 rows shrink to 2 rows (one per team), and the names disappear.
  • Rank by team — PARTITION BY team. Each team is ranked from 1 again.
  • A running total with ties — The two tied rows get the same running total.
  • Getting the previous row's value — LAG. The first row of a team has no previous row, so the value is NULL.

Running with the default settings

  1. FROM score: The 6 rows of the score table are read. Each row is one person's score. Two people have 90 points (Alice and Bob), and two have 70 points (Carol and Eve).
  2. OVER (ORDER BY pts DESC): This decides how the rows are laid out when each value is computed. All 6 rows are lined up from the highest score. The rows are only put in a line. They are not combined.
  3. Alice (90 pts): RANK() adds 1 to the number of rows with a higher score. No row has a higher score than this one, so the rank is 1.
  4. Bob (90 pts): No row has a higher score than this one, so the rank is 1. The score ties with the previous row, so the rank is the same.
  5. Dave (80 pts): The number of rows with a higher score is 2, so the rank is 3. The two tied rows before this one took two places, so rank 2 is skipped.
  6. Carol (70 pts): The number of rows with a higher score is 3, so the rank is 4.
  7. Eve (70 pts): The number of rows with a higher score is 3, so the rank is 4. The score ties with the previous row, so the rank is the same.
  8. Frank (60 pts): The number of rows with a higher score is 5, so the rank is 6. The two tied rows before this one took two places, so rank 5 is skipped.
  9. ORDER BY pts DESC: The result is returned. The 6 rows are still 6 rows, and each row now has one value in the rnk column.

Result of this run

  • How ties are handled is the difference among the three functions. For the scores 90, 90, 80, ROW_NUMBER gives 1, 2, 3 (different numbers even for a tie), RANK gives 1, 1, 3 (the tied rows share a rank, and the next rank is skipped), and DENSE_RANK gives 1, 1, 2 (the tied rows share a rank, and no rank is skipped).

Code

-- score table (6 rows)
-- name  team  pts
-- Alice   A     90
-- Bob   A     90
-- Carol   A     70
-- Dave   B     80
-- Eve   B     70
-- Frank   B     60

SELECT name, team, pts,
       RANK() OVER (ORDER BY pts DESC) AS rnk
  FROM score
 ORDER BY pts DESC;

Assumptions of this model

For all 24 combinations, the same SQL statement as the one on the screen was run on MySQL 8.4, and the number of result rows and the value added to each row were checked against the screen. The values with ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW in the running total were checked the same way. SQL does not define which of the tied rows is placed first (see the ROW_NUMBER description in the MySQL documentation), so the order of the two tied people on the screen is just one example, and the check was made on the team, the score, and the added value, not on the names. Window functions are available from MySQL 8.0. The way the step sentences calculate (for example, adding 1 to the number of rows with a higher score) is a plain-words version of each function's definition. A real database sorts the rows and then makes one pass over them to compute the values.
