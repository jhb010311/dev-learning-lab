Proxy servers

What is the difference between calling a server directly and calling it through nginx (a proxy)?

Why it exists — If a server program is exposed directly to the internet, then when you add servers or replace them, the address that users connect to changes too, and work such as handling HTTPS or blocking bad connections has to be done separately in each server program. A reverse proxy stands in front of the servers at one address, receives requests, and passes them on, so users connect to the same address even when the servers behind it change.

Where it's used today — A common setup puts nginx in front of a Spring Boot server and uses the proxy_pass setting of nginx to pass requests received on ports 80 and 443 to Spring Boot on port 8080. Spring Boot then sees nginx as the peer that connected to it, so nginx writes the real user's IP address into the X-Forwarded-For header with proxy_set_header and passes it along. There is also a proxy (a forward proxy) that gathers requests going from inside a company to outside sites in one place and filters them.

A proxy server is a server that stands between the side that sends requests (the user) and the real server and passes requests on for it. This lab uses the most common setup, nginx and Spring Boot, and compares calling the server directly with calling it through nginx. The code box has four parts. The first is the address the user calls. The user is on another computer (203.0.113.7), and 192.0.2.10 is the address of the server computer. If the address has no port number, the request goes to port 80, and if it has :8080, it goes to port 8080. A port number is the number of a door given to each program on one computer. The second is the nginx configuration. listen 80 is the line that receives requests on port 80, proxy_pass is the line that passes the received request on to port 8080 of the same computer (127.0.0.1:8080), and proxy_set_header is the line that writes a header onto the request when it is passed on. The third is application.properties, the configuration file of Spring Boot, and the fourth is the controller that receives the request. The controller returns, as text, the address of the peer that connected to it (request.getRemoteAddr()) and the header X-Forwarded-For. In this lab you change the address that is called, the server.address line, and which programs are running, and see what the user receives and whom Spring Boot sees as the peer. nginx is not installed on the computer used to write this lab, so in the run, a small program (Node.js) built to behave as the nginx documentation describes stood in for nginx, and the Spring Boot side ran the code on the screen as it is.

Partly checked against real execution · The Spring Boot side (the HelloController and application.properties on the screen) was actually run with Spring Boot 4.1.1 and twelve combinations were checked (the effect of getRemoteAddr(), X-Forwarded-For, and server.address, verify/net/cmp_proxy_basic.js). nginx is not on the PC used to write this lab, so a Node.js program built to behave as the nginx documentation and source describe stood in for it (proxy_pass, proxy_set_header, and 502 were checked against the documentation and the source)

Concepts in this lab

Proxy server
A proxy server is an intermediate server that stands between the side that sends requests (the client) and the real server, passes the request it receives on to another server, and returns the response to the client. The client connects to the proxy server, and the proxy server makes a separate connection to the real server. So the peer that the real server sees is the proxy server, not the client. nginx in front of Spring Boot is a typical example. Section 3.7 of RFC 9110 divides such intermediaries into a proxy, which the client chooses by its configuration to go through, and a gateway (reverse proxy), which looks like a server and passes requests on to the servers behind it. If the proxy server goes down, a client that connects to its address does not get a response, even though the servers behind it are alive.
Reverse proxy
Why it exists — If slow clients connect straight to an application server, the request processing threads stay tied up with those connections while the clients slowly upload a large request body or slowly take a response. A reverse proxy such as Nginx, in its default configuration, buffers requests and responses and exchanges data quickly with the backend server, so the backend server's threads are not tied up for long by slow connections.
Where it's used today — It is used to split static file requests and /api requests by path and send them to different servers, or to reject too-large uploads at the front with Nginx's client_max_body_size. In Kubernetes, an Ingress controller takes this role.
A server that receives client requests on behalf of internal servers, forwards them to those servers, and returns their responses to the client. The client does not know the actual servers directly. Its roles include distributing requests across several servers, handling TLS, caching, and protecting the internal servers.
nginx proxy_pass and proxy_set_header
Where it's used today — When you put nginx in front of Spring Boot, the most common configuration is to put listen 80; (or listen 443 ssl;) in a server block and to write proxy_pass and a few proxy_set_header lines inside location /.
proxy_pass and proxy_set_header are directives written in a location block of an nginx configuration file. proxy_pass http://127.0.0.1:8080; means that a request that comes into that location is passed on to the server at the given address, and nginx makes a new connection to that server for this. proxy_set_header writes a header onto the request that is passed on. proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; writes the received X-Forwarded-For followed by a comma and the address of the peer that connected to nginx ($remote_addr), or only that address if nothing was received. proxy_set_header Host $host; passes on the name the client wrote in the request as the Host header. If you do not write it, nginx puts the address written in proxy_pass ($proxy_host) into Host and adds Connection: close (documentation of ngx_http_proxy_module).
X-Forwarded-For
Where it's used today — You read this value to record the real user IP in an access log, or to block requests that come too often from one IP. In nginx, the proxy_set_header setting attaches this header and passes it on.
X-Forwarded-For is a request header in which a proxy writes the address of the original client when it passes a request on. The peer that a server behind a proxy sees is the proxy, so the address of the real client is passed on only through this header. When a request goes through several proxies, each proxy appends the address of whoever connected to it at the end, separated by a comma. It is a request header, so a client can also write any value into it; a server must use only the values added by a trusted proxy that it manages (the values on the right), and must not read it at all if it is not behind a proxy. It is a widely used convention, not a standard, and the standard header that does the same job is Forwarded.
502 Bad Gateway
Where it's used today — When the Spring Boot server behind nginx is stopped or still starting, the browser shows the 502 page of nginx. In that case, first check whether the server behind is running and whether the port written in proxy_pass matches server.port.
502 is a status code used when a server acting as a gateway or proxy receives an invalid response from the inbound server it accessed to fulfill the request (RFC 9110 section 15.6.3). When nginx cannot even connect to the server behind it (the connection is refused), it also returns 502 if there is no next server to pass the request to (nginx source ngx_http_upstream.c). The one that makes and sends this response is the proxy server the client connected to, not the real server behind it. So when a client receives 502, it means the client reached the proxy server it connected to, and the problem is between the proxy server and the server behind it.
server.address
Where it's used today — In a setup where Spring Boot and nginx are on the same computer, server.address=127.0.0.1 keeps outside users from calling Spring Boot directly on port 8080 and lets them come in only through nginx. Blocking that port with a firewall is another way.
server.address is a Spring Boot setting that decides on which network address the embedded server (Tomcat) waits for connections. If you do not write it, it waits on all addresses of the computer (0.0.0.0), and if you write server.address=127.0.0.1, it waits only on 127.0.0.1. 127.0.0.1 is the address a computer uses for itself, so only programs on the same computer can connect to that port, and connections from other computers are refused. The port is set with server.port (default 8080).
Origin server
An origin server is a program that can originate authoritative responses for the requested resource, and section 3.6 of RFC 9110 calls it by this name. The Spring Boot application behind nginx is in this place. A proxy server only passes requests on, so the origin server is the one that produces the content of the response. When a proxy server is present, a client may not connect to this server directly, and this server sees the proxy server as the peer that connected to it.

Try these

  • Default settings — The peer that connected to Spring Boot is nginx (127.0.0.1), and the user's address 203.0.113.7 arrives in the X-Forwarded-For header that nginx wrote and passed on.
  • Calling port 8080 directly — Even though Spring Boot is running, the user receives a connection refused error, because Spring Boot accepts only connections that come to 127.0.0.1.
  • Removing the server.address line and calling directly — The peer is the user itself (203.0.113.7), and with no nginx in between to write the header, X-Forwarded-For is null.
  • Stopping Spring Boot — nginx cannot connect to port 8080 and returns 502 Bad Gateway to the user. nginx made this response.
  • Calling directly with Spring Boot stopped — The request does not pass through an nginx that could answer for it, so the user receives a connection refused error, not 502.
  • Stopping nginx — Even though Spring Boot is fine, the user receives a connection refused error. The one door the user uses is port 80 of nginx.

Running with the default settings

  1. The user (203.0.113.7) sends a GET /hello request to the address in the code box. The address has no port number, so it connects to port 80 of the server computer 192.0.2.10. What waits on port 80 is nginx (listen 80). The address the user uses does not contain the Spring Boot port, 8080.
  2. nginx receives the request, and following the line proxy_pass http://127.0.0.1:8080, it makes a new connection to port 8080 of the same computer and passes on the same GET /hello. This connection is separate from the one the user made, and nginx is the side that made it. When passing the request on, following the line proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for, nginx writes the address of the peer that connected to it (203.0.113.7) into the X-Forwarded-For header. The line Host $host passes on the name the user wrote in the request (192.0.2.10) as a Host header, and this lab does not use it in its results. The place nginx connected to is 127.0.0.1, so Spring Boot with server.address=127.0.0.1 accepts this connection too.
  3. The controller of Spring Boot runs. request.getRemoteAddr() is 127.0.0.1, because the one that opened the connection to this server is not the user but nginx on the same computer. The user's address 203.0.113.7 is obtained with request.getHeader("X-Forwarded-For"), a value that nginx wrote.
  4. nginx receives the response of Spring Boot and returns it to the user. What the user received is status code 200 and the body "Connected peer: 127.0.0.1, X-Forwarded-For: 203.0.113.7". The user talked only with the nginx it connected to.

Result of this run

  • Going through nginx splits the connection in two. The user connects to nginx (port 80), and nginx makes its own connection to Spring Boot (port 8080) and passes the request on. So getRemoteAddr() in Spring Boot is not the address of the user but that of nginx (127.0.0.1).
  • The real user's address arrives in the X-Forwarded-For header that nginx wrote with proxy_set_header. The setting that makes Spring Boot read this header and reflect it in getRemoteAddr() (server.forward-headers-strategy) is covered in the in-depth lab "Proxies and reverse proxies".

Code

# The address the user (another computer, 203.0.113.7) calls
# If no port number is written, http goes to port 80
http://192.0.2.10/hello

# nginx configuration (runs on the server computer 192.0.2.10)
server {
    listen 80;
    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

# application.properties (Spring Boot, runs on the same computer)
server.port=8080
# Accepts only connections that come to 127.0.0.1 (the address this computer uses for itself)
server.address=127.0.0.1

// HelloController.java
// HelloController is a name chosen for this example. @RestController and @GetMapping come from
// Spring, and HttpServletRequest comes from the servlet API (jakarta.servlet).
import jakarta.servlet.http.HttpServletRequest;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class HelloController {
    @GetMapping("/hello")
    public String hello(HttpServletRequest request) {
        // The address of the peer that opened a connection to this server
        String peer = request.getRemoteAddr();
        // The X-Forwarded-For header that came with the request (null if absent)
        String xff = request.getHeader("X-Forwarded-For");
        return "Connected peer: " + peer + ", X-Forwarded-For: " + xff;
    }
}

Assumptions of this model

The verification run (verify/net/proxy_basic_probe_boot.js) ran all twelve combinations only on the PC used to write this lab and did not use any external network. The Spring Boot side was actually run. The HelloController on the screen was compiled with JDK 21 with only one package line added, the lines of application.properties on the screen were written out to a file as they are, and the server was started as Spring Boot 4.1.1 (Spring 7.0.9, embedded Tomcat 11.0.24). The only change was replacing the 8080 of server.port with a free port number; the Main class that starts it and the filter that counts /hello requests were added for the run (they are not on the screen). Checking with netstat, the server waited only on 127.0.0.1 with server.address=127.0.0.1, and on 0.0.0.0 (all addresses) without that line. nginx is not on this computer and was not downloaded; a Node.js 24.18.0 program, built by reading the nginx configuration on the screen and behaving as the nginx documentation describes, stood in for nginx. This program does not pass on the Host and Connection of the received request, passes on the other headers as they are, applies the $host (the name written in the Host of the request) and $proxy_add_x_forwarded_for (the received X-Forwarded-For followed by a comma and $remote_addr, or just $remote_addr if nothing was received) of the proxy_set_header lines, and passes the request to the back end as HTTP/1.1 with the default Connection: close added. If it cannot connect to the back end, it returns 502 and the 502 page written in the nginx source. So the nginx side was not run with real nginx; it was carried over by checking against the documentation and the source. What was checked against the documentation is the ngx_http_core_module of nginx.org (the default of listen, server and location, $host, $remote_addr), the ngx_http_proxy_module (proxy_pass; the defaults of proxy_set_header, Host $proxy_host and Connection close; that the Host and Connection of the original request are not passed on; the definition of $proxy_add_x_forwarded_for; and that proxy_http_version defaults to 1.1 from 1.29.7), the nginx source ngx_http_upstream.c (a failure to connect to the back end is handled as an error branch, and if there is no next server to pass to, it ends with 502) and ngx_http_special_response.c (the text of the 502 page), the description of the settings in the Spring Boot 4.1.1 jar (server.address is the network address the server binds to, and server.port defaults to 8080), and section 15.6.3 (502) of RFC 9110. The nginx documentation has no sentence that says "502 if connecting to the back end fails", so this was checked in the source. The last line of the 502 page may have a version number after nginx depending on the server_tokens setting. The user address 203.0.113.7 and the server computer address 192.0.2.10 on the screen are example addresses for documentation, and in the run the user was replaced by 127.0.0.10 and the outside address of the server computer by 127.0.0.2 (both are loopback addresses of this PC). So "calling port 8080 from another computer is refused" was checked as a connection to 127.0.0.2 being refused by a Spring Boot that waits only on 127.0.0.1, and it was not run on a real other computer. The 80 and 8080 on the screen were also free port numbers in the real run, and a program that was stopped was not started, and its port number was replaced by a free port that had just been closed. What was checked against (verify/net/cmp_proxy_basic.js, all 13 cases matched) is what the user received (the status code, the body, or the connection refusal), the getRemoteAddr() and X-Forwarded-For that the controller returned, the number of requests received by the program standing in for nginx and the headers it added, the number of /hello requests Spring Boot received, and whether the code on the screen is the same text that the run read. Tomcat does not put text such as OK on the status line, so the table shows only the status code 200. This lab does not cover HTTPS (port 443) and certificates, server.forward-headers-strategy (which makes Spring Boot read X-Forwarded-For and reflect it in getRemoteAddr()) and forged headers, or 504 for slow responses. The first ones are covered in the in-depth lab "Proxies and reverse proxies", splitting among several servers in "Load balancers and scale out", and keeping copies of responses in "CDN".
