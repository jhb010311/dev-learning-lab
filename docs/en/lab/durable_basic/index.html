Storage and durability

Does committed data stay after the server is turned off?

Why it exists — A program that simply writes data to a file cannot tell how much was saved if the power goes out during writing, and half-written content can remain. A DB that stores to files uses COMMIT as the boundary: after it is turned on again, changes that were not committed are discarded and changes for which COMMIT was reported successful are given back (when the setting writes committed content to disk immediately). So the program only has to check whether COMMIT succeeded.

Where it's used today — Records that must not be lost, such as orders, payments, and sign-ups, are saved by going through to COMMIT in a DB that stores to disk, such as MySQL or PostgreSQL. In Spring, COMMIT is sent when a method with @Transactional ends without an exception. In places where it is fine for data to be erased when the run ends, such as tests, it is common to use H2 only in memory with a jdbc:h2:mem: address.

A database is a program that stores data and gives it back when asked, and it usually stores the data in files on disk (as this lab shows, it can also be set to keep the data only in memory). The variables of a Java program are gone when the program ends, but data that went through COMMIT must still be there even if the database program stops suddenly and starts again. This property is called durability. In the code of this lab, two things decide it (depending on the database, a setting that writes the committed data to disk right away is also needed). One is COMMIT, the statement that makes the changes in a transaction final so that they are kept. The other is where the data is kept: if the connection address starts with the text jdbc:h2:file:, the data is kept in a file on disk, and if it starts with the text jdbc:h2:mem:, it is kept only in memory. In this lab you remove the COMMIT line or change where the data is kept, run the same INSERT, end the database program without any cleanup, start it again, and read the memo table (a name chosen for this lab). (This lab uses H2 in embedded mode, in which the Java program loads H2 and runs it in its own process. So "the database program stops" means that the Java program ends. A database such as MySQL is usually run as a separate program (a server), and in that case it is the database server program that stops. How a database keeps this promise (the log and the buffer) is covered in the in-depth labs.)

Checked against real execution · Ran all 4 combinations on H2 2.4.240 by ending the process without cleanup and opening the database again, and checked against the results; the rules of durability were checked against the MySQL and H2 documentation (cutting the power was not run)

Concepts in this lab

Durability
Durability is the property that the changes of a transaction whose COMMIT succeeded are not lost even after a power failure or a system crash, and it is the D in ACID. The MySQL documentation explains that durability is usually achieved by writing to disk storage, with redundancy in case of a failure during the write. In MySQL it is a property decided together by software settings (such as innodb_flush_log_at_trx_commit) and hardware (such as the write buffer of the storage device and fsync() support in the operating system), so how far it is guaranteed depends on the settings. Changes made before COMMIT are not covered by this promise.
Persistent and in-memory databases
Why it exists — Starting a separate database server for every test and deleting the data from last time is tedious. An in-memory database comes into being with the program and disappears when it ends, so that every run starts quickly with an empty database.
Where it's used today — In a Spring Boot project that uses JPA or JDBC, if you add H2 as a dependency and do not write a database address, Spring Boot creates and uses an H2 in-memory database by itself. The persistent database way is used when a small program that does not have a separate database server leaves its data in a file.
A persistent database stores its data in files on disk, and an in-memory database keeps its data only in the memory of the computer. In H2, you choose by the connection address. An address that starts with jdbc:h2:file:path (file: can be left out) stores the data in a file, and an address that starts with jdbc:h2:mem:name keeps it in memory. A persistent database stays even after the connection is closed, but according to the H2 documentation, the content of an in-memory database is lost when the last connection is closed, and even with DB_CLOSE_DELAY=-1 it stays only while the program (the virtual machine) is alive. The MySQL glossary calls the opposite of an in-memory database a disk-based database.
Commit and rollback
Where it's used today — You use them to apply everything or cancel everything for work that must change several things, such as a bank transfer. Even when you fix data by hand with a DB tool, you open a transaction, look at the result with SELECT, and send COMMIT if it is right and ROLLBACK if it is wrong.
A commit makes all the data changes in a transaction final in the database, and a rollback cancels all of those changes and returns to the state before the transaction started. A transaction ends in one of the two, and a change that has already been committed cannot be undone by a rollback. In Spring, when a method with @Transactional ends normally, Spring commits, and when it ends with an exception, Spring looks at the rollback rules and rolls back. Under the default rule, it rolls back when a RuntimeException or an Error is thrown out of the method, and it does not roll back for a checked exception. Without a transaction, each save statement is committed immediately by auto-commit, which is the default setting of a JDBC connection, so even if an exception occurs later, the earlier save cannot be rolled back.
H2 write delay (WRITE_DELAY)
Why it exists — If every COMMIT waited until everything was written to the file, a program that commits often would become slower by that much. WRITE_DELAY is a setting that puts off writing to the file for a short time, so COMMIT finishes quickly, in exchange for giving up a little durability.
Where it's used today — To reduce the chance of losing committed records when the power goes off in an H2 persistent database, lower it to 0 so that writing is not put off, and if the data can be recreated even if lost, leave it at the default.
WRITE_DELAY is the maximum delay that H2 can put between a COMMIT and writing its content to the file, and it is set in milliseconds. According to the H2 documentation, the default is 500, and you can change it with the command SET WRITE_DELAY number or by adding ;WRITE_DELAY=0 to the end of the connection address, and the setting stays in the database. By default H2 puts off writing committed content to the file, so the H2 documentation says that when the power goes off, a bit more than 1 second of committed content can be lost. Many hard disks also do not obey the write command (fsync), so complete durability, with any setting, depends on the device.

Try these

  • Default settings — In a database that stores data in a file, a row that went through COMMIT is still there after the database program stops suddenly and starts again.
  • Removing COMMIT — A row that was not committed is not there after the restart. The table is still there.
  • A database that keeps data only in memory — Even though COMMIT was done, after the restart even the table is gone.
  • No COMMIT and memory only — The result is the same as with COMMIT. This database disappears as a whole, whether or not there is a COMMIT.

Running with the default settings

  1. Connect to the database. In the address, jdbc:h2:file:./shop means to store the content of the database in a file named ./shop (H2 makes it as a file called shop.mv.db). The WRITE_DELAY=0 setting at the end means to write what was committed to the file right away without putting it off. With the default settings, H2 puts off writing to the file after a COMMIT for up to 0.5 seconds (H2 documentation), so to test a sudden stop we made it write right away.
  2. CREATE TABLE memo: The database creates the memo table, which has two columns, id and text. There is no BEGIN yet, so this statement becomes final as soon as it runs (autocommit). The content that became final is written to the database file on disk.
  3. BEGIN: The database starts treating the statements from now until COMMIT as one transaction. Autocommit is turned off, so changes inside this transaction are not final until they meet COMMIT.
  4. INSERT INTO memo: The database puts the row (1, 'hello') into the memo table. It is a change inside the transaction, so it is not final yet. If you read the memo table on this connection, you see 1 row.
  5. COMMIT: The database makes the transaction final. Because of the WRITE_DELAY=0 setting, it writes the final change to the database file right away. Now the 1 row is in the memory of the program and also in the file on disk. Autocommit is turned on again.
  6. This is not in the code. The database program stops suddenly. The program ends right away without closing the connection or going through a shutdown procedure (in the experiment we ended it with the Java method Runtime.halt). The memo table and rows that were in the memory of the program are all gone. The database file on disk stays. (We tested the case where only the program ends, not a power loss.)
  7. The database program starts again and connects with the same address. The ./shop file stays on disk, so the database opens that file and can read its content. Even though the connection was not closed when it stopped, the file opened without an error.
  8. SELECT * FROM memo: The result is 1 row (1, hello). The row made final by COMMIT was in the file on disk, so it is still there after the database program stopped suddenly and started again.

Result of this run

  • The row that was made final with COMMIT was still there after the database program stopped suddenly and started again. This is because the row was in a file on disk. Unlike memory, which is lost when a program ends, a file on disk stays when the program stops, and COMMIT is the statement that makes a change final so that it is kept in that file.
  • This property, that a change made final by COMMIT stays after a shutdown, is called durability. In this lab we added the WRITE_DELAY=0 setting to the address so that the data is written to the file together with COMMIT. Without it, with the H2 default settings, when we stopped right after COMMIT, none of the five runs had the committed row, and when we waited 1.5 seconds before stopping, it stayed in both runs. How a database keeps this promise (the log and the buffer) is covered in the in-depth labs.

Code

-- Connect to a database that stores data in a file (jdbc:h2:file:./shop;WRITE_DELAY=0), and
CREATE TABLE memo (id INT PRIMARY KEY, text VARCHAR(20));

-- Start: treat everything from here as one transaction
BEGIN;
INSERT INTO memo VALUES (1, 'hello');
-- Final: tell the database to keep the changes made so far
COMMIT;

-- After the database program stops suddenly and starts again, connect with the same address, and
SELECT * FROM memo;

Assumptions of this model

It was run and checked against H2 2.4.240 (JDK 21.0.12.1), and it was checked against H2, not MySQL. For all 4 combinations, it ran the whole SQL on the screen, including the comment lines, exactly as written. It connected with the address written in the comment on the first line, and it sent each comment line to the database together with the statement that follows it. First, a new Java process ran the statements up to the line "After the database program stops suddenly" one statement at a time, and then it ended the process right away with the Runtime.halt method, without closing the connection or running any shutdown procedure (exit code 7). After that, another new Java process connected with the same address and ran the SELECT after that line. The address ./shop of the file database is a file in a folder made separately for each combination. What it checked is the three items of the result table, that is, the rows read after the restart (the number of rows and the values, or the kind of the error), whether the COMMIT line is there, and the files made in the folder. The file database was opened again after the stop without any cleanup, and of the 4 combinations, only the one with a COMMIT on the file database kept its row. The memory database made no file in the folder, and on the restarted connection there was an error that the memo table does not exist (H2 error code 42104, with "this database is empty" in the message). The original text of the error is in the Probe output, and the screen shows only the kind of the error. As the facts the step sentences rely on, it also checked by execution that autocommit is off after BEGIN and on again after COMMIT, that reading on the same connection right before the stop shows 1 row, and that CREATE TABLE is final before BEGIN, so the table stays even after a stop without COMMIT. The code on the screen has no query for this checking, and the column name text of the memo table could be used in H2. An important point: we added ;WRITE_DELAY=0 to the address of the file database in this lab. The H2 documentation (the SET WRITE_DELAY entry on the Commands page) says that it sets the maximum delay between a COMMIT and writing the log to the file in milliseconds, that the default is 500, and that it can be added to the database address as ;WRITE_DELAY=0. With the H2 default settings, without this setting, when the process was ended right after COMMIT on a file database, none of the five runs had the memo table or the row after the restart (the database file was there but empty), and when the process was ended after waiting 1.5 seconds after COMMIT, the row stayed in both runs. So the "it stays if you COMMIT" in this lab is a result observed with the WRITE_DELAY=0 setting. The H2 documentation (Durability Problems on the Advanced page) also explains that by default H2 puts off writing committed content to the file, that if the power goes off, a bit more than one second of committed content can be lost, and that complete durability is hard because hard disks often do not obey fsync. And this lab ended only the process and did not cut the power; because file writes that the operating system has accepted stay even when a process ends, durability when the power goes off was not checked by execution. That a memory database disappears when its last connection is closed (or when the program ends) follows the H2 documentation (In-Memory Databases on the Features page), and in this lab the case where the process ended was checked by execution. The MySQL 8.4 documentation page "InnoDB and the ACID Model" says that durability is a property decided together by the MySQL software and hardware settings, and lists innodb_flush_log_at_trx_commit, sync_binlog, fsync() support, and the write buffer of the storage device as related factors, and the ACID entry of the glossary says that when a commit succeeds, the changes are safe from power failures and system crashes, and that durability usually means writing to disk. We opened these documents directly and checked them, but we did not run to see whether MySQL gives the same result. This lab covers only the outward look of durability, that is, whether data stays after a stop and restart depending on COMMIT and where the data is stored. How the log and the buffer pool keep this is covered in the in-depth labs "Undo and redo logs" and "Buffer pool and pages", and the transaction itself in "Transactions".
