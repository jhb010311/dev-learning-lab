GC and memory leaks

Who reclaims discarded objects, and when?

Garbage collection (GC) is the JVM automatically reclaiming the memory of objects that are no longer used. New objects are created in eden, and when eden fills up, a minor GC picks out only the live objects and moves them. Objects that survive several times are promoted to the old generation, and when the old generation fills up, a full GC runs, which takes much longer. A memory leak is the buildup of objects that are no longer needed but cannot be collected because something still refers to them, and this lab also shows what happens to the heap when there is a leak.

Concepts in this lab

Garbage collection (GC)
This JVM feature finds objects that the program no longer uses and reclaims their memory automatically. Developers do not have to free memory themselves, which prevents errors caused by mistakes in freeing it. In return, the application may pause briefly during a collection, and objects that are still referenced cannot be reclaimed.
Reachability and GC roots
The GC decides whether an object is still in use by asking "is it reachable?". An object that can be reached by following references from starting points that are always alive (GC roots), such as the local variables of running threads and static variables, is treated as live, and an object that cannot be reached is treated as a candidate for reclamation.
Young generation and old generation
This structure divides the heap based on the observation that most objects become useless soon after they are created. New objects are created in the young generation (in eden), and objects that survive several collections of the young generation are moved to the old generation. Collecting only the young generation often, where short-lived objects gather, reclaims a lot of memory at low cost.
Minor GC and full GC
A minor GC (young GC) collects only the young generation; it happens often but usually finishes quickly. A full GC collects the whole heap; it takes a long time and also pauses the application for longer. If full GCs happen often, or memory use does not go down even after a full GC, suspect a memory leak or a heap that is too small.
Stop-the-world (STW)
This means pausing all threads of the application so that garbage collection can be done safely. Request handling stops during this time, so it shows up as response delays. Recent collectors (G1, ZGC) are designed with the goal of keeping these pauses short.
Memory leak
This is a state in which objects that are no longer needed are still referenced from somewhere, so the garbage collector cannot reclaim them. Memory use grows over time and eventually leads to an OutOfMemoryError. Typical causes are data that keeps piling up in a static collection, a cache with no expiration, and ThreadLocal values that are not cleaned up in a thread pool.
StackOverflowError and OutOfMemoryError
A StackOverflowError occurs when method calls go so deep that they exceed the thread's stack space, and the usual cause is recursion with a wrong termination condition. An OutOfMemoryError occurs when memory such as the heap runs short and no more objects can be allocated, and common causes are a memory leak or loading too much data at once.

Try these

  • Default settings — Most objects are discarded quickly. Minor GCs alone keep the program going.
  • With many long-lived objects — More objects are promoted to the old generation, and full GCs start to run.
  • Creating objects faster — Eden fills up sooner, so minor GCs become more frequent.
  • With a larger heap — The number of GCs goes down.
  • Memory leak — Even though GCs run, the old generation does not empty, and the run ends with an OutOfMemoryError.
  • A leak with only a larger heap — This only delays the point of failure.

Result of this run

  • Most objects were discarded quickly, so minor GCs alone were enough. Dividing the heap into generations is efficient when the assumption that "most objects die young" holds.

Code

// Heap: eden 20 slots, survivor 5 slots, old 40 slots

while (running) {                       // one pass = one tick
    for (int i = 0; i < 5; i++) {
        Event e = new Event();           // created in eden
        if (keepForAWhile(e)) {          // 10%
            recent.put(e.id(), e);       // removed 10 ticks later
        }
    }                                    // the rest are discarded here
}

Assumptions of this model

This is a simple model of generational garbage collection in which all objects have the same size and the heap is counted in slots. The condition for promotion is lowered to "survives two minor GCs" (the real default maximum is 15, and the garbage collector adjusts it to the situation). The pause times 1 and 10 only express the relationship that a minor GC is much shorter than a full GC. Real collectors such as G1 and ZGC work differently, for example by dividing the heap into smaller parts and working concurrently with the application, but the principle is the same: the area for new objects and the area for old objects are handled separately, and objects that are still referenced cannot be reclaimed. The slot counts and GC counts are values of the model. However, the same situations were actually run on JDK 21 on this PC with a 64MB heap to check the direction. Creating only objects that are discarded quickly gave 24 young collections and 0 full GCs. Mixing in objects that are held for a long time gave 7 full GCs (average pause: young 2.1ms, full 11.5ms). Continually adding objects to a list that is never cleared ended with an OutOfMemoryError after 37 repeated full GCs. With the heap enlarged to 128MB, the same leak ended with the same error after creating about twice as many objects.
